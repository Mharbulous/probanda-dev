# Writing population checklists

Owned by `/drafting-data` (schema/SQL live here, never in a consuming skill's own files — Database Access Encapsulation). Consulted by `/draft` when it constructs `drafting_data__execute` scripts. Cites `references/schema.sql` as the DDL source of truth; nothing here duplicates a `CREATE TABLE` statement, and SQL text is composed at write time against the live schema, never baked as static statements into any skill's prose.

Every checklist item below exists because a renderer (`source/practice/mcp/src/submission/forms/*.ts`) reads that exact field, or because the work-marker SSOT (`.claude/skills/drafting-data/references/work-markers.md`) keys a work marker off it. A field not listed here is not read by any v1 renderer — leave it NULL rather than guessing a value.

**Renderer builds need an MCP server restart to take effect.** `source/practice/mcp/dist/litigation-mcp.js` is loaded once at spawn (the installed plugin's copy of it, never this repo's file: Claude Code and Cowork serve plugin tools from the installed copy) — a session that rebuilds `source/practice/mcp/src/submission/forms/*.ts` and re-renders through `drafting_forms__render`/`bootstrap` in the same session still exercises the pre-rebuild code until the plugin is repackaged and reinstalled and the app is fully restarted. Don't diagnose that as a renderer bug.

## 0. Shared substance (once per proceeding)

Elicited before any Writing, on the proceeding's first Writing only — every later Writing in the same proceeding reuses this row.

- **`proceedings`**: `forum` (`'CAN/BC/BCSC'`, `'CAN/BC/Vancouver-International-Arbitration-Centre'` or `'CAN/BC/BCCA'` — governs which Writing kinds are even legal, see §2 below), `matter_reference` (free text; stands in for client/matter name if the caller supplies no `ClientContext`), `court_or_centre`, `registry` (BCSC and BCCA: the bare place name, e.g. `Vancouver` — every caption, form and Job Board sentence prints it followed by "Registry", so never store the word; NULL for VanIAC), `file_number`, `style_of_cause`, `courthouse_address` (BCSC hearing-notice line — leave NULL for VanIAC), `rule_24h_consent` (unused by any v1 renderer; leave 0 unless a later ticket needs it).
- **`documents.file_path`**, wherever a `documents` row names its copy on disk (the VanIAC exhibit list prints it): write it in the stored form, relative to the matter root with backslash separators. The form, its conversion helper, and the re-point after a file moves are in `references/document-paths.md`.
- **`parties`**: one row per party. `role` is **not** schema-constrained — it is the forum's own vocabulary — but the default-judgment and consent-order renderers match `/defendant/i` against it, so BCSC defendants must be named literally "Defendant" (or contain that substring), not a synonym. `ordinal` fixes caption order. `is_client` marks whose side the Writing is drafted for (drives applicant/plaintiff fallback logic in every renderer). `is_applicant` — BCSC applications; falls back to `is_client` where a renderer needs an applicant and none is flagged. `to_be_served` — Notice of Application "To:" line. Counsel of record is not a `parties` column: a drafting Writing reads it from case data (next bullet), and the consent-order renderer emits a signature block **only** for parties whose counsel case data names, so an unrepresented party is correctly omitted, not correctly gap-flagged.
- **Party and counsel from case data** (schema v41, party/counsel SSOT; v43 drops the copy). `parties.case_party_id` is the `/case-data` party the row stands for, as `/case-data` reports it, never guessed; NULL until a session links it. Counsel of record and the address for service (`counsel_name`, `counsel_firm`, `counsel_email`, `counsel_phone`, `address_for_service`, as the runtime names them) are court-record state that `/case-data` owns, so they are never elicited and no `parties` column holds them since schema v43: a drafting Writing's render and filed-face emitters read them live from case data through `case_party_id` (the proceeding's parties of record by its file number, or, before it has one, each linked party's own values). `drafting_forms__open_session` returns `parties_drift`, one row per party they cannot be read for: `unlinked`, linked to a party `not_of_record` in the proceeding (with no file number, one case data does not hold), or `unchecked` (`parties_drift_note` says why, including a proceeding with a file number and no case-data database). Such a party prints no counsel or address for service, the mockup marks it, and the filed render and the `emit_*` emitters of a drafting Writing refuse with `parties_drift_gate_failed` while any row stands. **The confirm write**, once the practitioner confirms a row (`/draft` §8): one `drafting_data__execute` script sets the row's `case_party_id`, which is all drafting reads; when the practitioner says case data is wrong, the correction is written to case data through `/case-data` first. It writes nothing else: on a database still at v42, a value the five columns hold is offered back (next bullet), never overwritten here. It does not touch `recipients`: a party-linked recipient takes its values from the party read, not its own columns (§13 "Service list"). For party 3, linked to case-data party 2:

  ```sql
  UPDATE parties SET case_party_id = 2 WHERE id = 3;
  ```

  A sent Writing prints the party rows it was sent with (`parties_snapshot`), which `drafting_data__record_sent` and `drafting_data__record_filed` write from case data in the transaction that sets its `filed_on` (§11, schema v42), so the confirm write reaches drafting Writings only. A Writing that already has snapshot rows keeps them: delete them before setting a cleared `filed_on` again if the parties printed changed in between.
- **Inadmissible evidence** (schema v63). `statements_of_fact.admissibility_note` records a concern, which decides nothing: the fact still drafts on that evidence. `inadmissible_on` and `inadmissible_note` record the practitioner's decision that the link's evidence is inadmissible to prove its fact, written only when the practitioner states it, the note in their words verbatim, never proposed, worded or inferred by a session. Both are set together or not at all. Whether evidence is admissible is a question of law, so a session that is asked goes to `/legal-research` and records only what the practitioner then decides. The Provable Facts page strikes a fact when every link it has carries the decision, unless the fact is on the court record or admitted by every opposing party. The note must hold words: an empty or blank note is refused. For link 7:

  ```sql
  UPDATE statements_of_fact SET inadmissible_on = '<YYYY-MM-DD>', inadmissible_note = '<the practitioner''s words verbatim>' WHERE id = 7;
  ```

  Withdrawing the decision sets both NULL. The decision is about the evidence the link names: a later write that re-points the link's `instrument` or `exhibit_id` sets both NULL in the same statement, unless the practitioner restates the decision for the new evidence.
- **Counsel offers** (party/counsel SSOT, a database at schema v42 or before, whose `parties` rows still hold the five columns). Every value a party row still holds in the five columns that case data does not hold is offered back to the practitioner, so nothing is dropped unseen. `drafting_forms__open_session` returns `counsel_offers` when there is one, beside `parties_drift`, compared trimmed against the same case-data read a drafting Writing uses: one row per party and field of kind `offer`, with `case_data_value` (NULL when case data holds none) and `held_value`; one row per party holding values that is `unlinked` or `not_of_record`, with its `held` values, which is linked first through the confirm write above and then offered field by field; and one `unchecked` row per such party whose case data cannot be read, with its `reason`. Present the offers as one batch table per proceeding, in the shape of `/case-data`'s order-effects approval table: party, field, value in case data, value held here. Each row has three choices, and nothing is written without the practitioner's answer:
  - **apply**: case data should hold the value. Write it to case data through `/case-data`'s own gate (its order-effects approval), naming the instrument the value comes from. The row then disappears, because case data matches.
  - **discard**: case data is right. Set the field NULL here, through `drafting_data__execute`. The row disappears. For party 3's email:

    ```sql
    UPDATE parties SET counsel_email = NULL WHERE id = 3;
    ```

  - **hold**: no write. The row stays, and keeps the matter's database at v42. The v43 hop drops the five columns, and the migrate refuses it, writing nothing, while any offer or `parties_drift` row stands (code `counsel_not_reconciled`, naming each row); a database older than v42 is first taken to v42 so its parties can be linked. `drafting_forms__open_session` then goes on without migrating and returns `migration_refused` with that message, beside `counsel_offers` and `parties_drift`, and lists and renders the database at v42 as usual until every row is decided. Beneath that gate the engine refuses the hop on its own, leaving the database at v42, while a party with no `case_party_id` holds a value in any of the five columns, or a Writing with `filed_on` set has no `parties_snapshot` rows and its proceeding has a party (clear its `filed_on`, §11, and record it again through the tool that writes the snapshot).

## 1. VanIAC submissions package (`kind='submissions_package'`)

Requires `proceedings.forum='CAN/BC/Vancouver-International-Arbitration-Centre'`. Set `round` (`'opening'|'response'|'reply'|'non_participation'`) and `title`.

- **`submissions`**: one row per submission (`contention` — law applied to fact, the position argued for; stored but never rendered as its own paragraph since 2026-08-31 — each linked postulate/proposition gets its own numbered paragraph instead), `ordinal` fixes order. No `disposition` column (retired in the v10 hop) — whether a submission renders here or survives only in the Counsel Brief is now derived from deployment (terms-and-symbols.md's Deployment section). Link into the Writing's rendered document via `filing_submissions(filing_id, submission_id, document, ordinal)` — `document` is `'form'` or `'written_argument'`.
- **Killing a submission** (schema v16): the practitioner reviewed it and rejected it — never delete the `submissions` row. In the same `execute` script, `UPDATE submissions SET killed_on = '<today, YYYY-MM-DD>' WHERE id = N` and `DELETE FROM filing_submissions WHERE submission_id = N AND filing_id IN (SELECT id FROM filings WHERE filed_on IS NULL AND retired_on IS NULL)` for every drafting Writing that deployed it (so it is reserved in the data, not only unrendered). A sent or retired Writing keeps its row: it was sent with the submission, and the v58 guards refuse the delete, aborting the whole script, if the filter is left off. Restoring it: clear the date (`killed_on = NULL`) and, if it should redeploy, re-insert the `filing_submissions` row via §7's ordinal idiom. **Before drafting or proposing a new submission, check the proceeding's existing `submissions` for one already carrying `killed_on` with the same contention — do not re-propose a point already reviewed and rejected.**
- **Legal basis per submission** (optional but drives the 📖/📜/📍 markers): `law_assertions` row (`proposition` — the legal test the submission requires; `dead_end` — 1 renders 🚧, research ran dry), linked via `submission_law(submission_id, law_assertion_id)`. A `law_assertions` row with **no** `statements_of_law` row is the ordinary "not yet researched" state (renders 📖) — do not fabricate an authority to avoid the marker. A `law_assertions` row `requires`-ed by more than one submission (the same legal point supporting two arguments) renders in full — numbered paragraph, excerpt, citation — once, positioned after the first submission that relies on it; each later submission relying on the same assertion renders a numbered cross-reference paragraph instead ("As set out in paragraph N, above, {proposition}" — no excerpt, no citation; ticket 2026-09-01), so a drafting session must not read the absence of a second excerpt block as missing data. Once an authority is chosen: `authorities` row (`kind`, `weight`, `treatment` — NULL treatment renders 📇, "note up"), then `statements_of_law(law_assertion_id, authority_id, pinpoint, excerpt, source, verification)` — `excerpt IS NULL` renders 📜, `pinpoint IS NULL` renders 📍 (independent, both can render). Case excerpts are whole paragraphs; statute excerpts keep the Act's own numbering and indentation. The excerpt must quote exactly what the pinpoint cites; replace omitted parts with "[...]". A partial-sentence excerpt trailing off in "…" is a capture defect, not a style choice — capture the whole paragraph or section. Store the excerpt without surrounding quotation marks; the renderer supplies the verbatim block. `pinpoint` never repeats the citation — store `para. 34`, `paras. 26, 34, 37`, `s. 4`, never `2023 BCCA 182, para. 34`. `source` (`'primary'|'secondary'|'tertiary'`, NULL = not yet rated, schema v9 issue #365) drives two lines. On the *proposition's own line*, the best `source` rung across its read statements (the non-dropped ones: the verified when any exist, else the leads) renders 🥉 only-tertiary or 🥈 only-secondary, and `'primary'` never renders (goal state); 🏅 *unrated* co-renders there whenever no read statement is rated `'primary'` and at least one is unrated — the rung is undeterminable. On the *statement's own line*, 🏅 renders whenever that row is unrated, doctrinal or jurisdictional alike, so a standalone jurisdictional citation needs rating too. NULL is **not** tertiary (#597): an unrated statement reads *unrated*, never *only tertiary*. A submission that needs no legal basis at all (a purely factual submission) gets **no** `submission_law` row and carries 📚 until counsel records that it needs no stated law (§6, schema v60), except a submission that only asks for ordinary costs, which derives no 📚 (the `symbol-table.ts` 📚 row). **Authorities and statements of law are legal content — only populate them from what `/legal-research` or the practitioner supplies, never invented.** `source` is the exception to "never guessed": it is the authority's **class**, a pure function of `authority.kind`, so it is set mechanically and needs no research (practitioner, 2026-09-20, #718):

  | `authorities.kind` | `statements_of_law.source` |
  |---|---|
  | `case` · `statute` · `regulation` · `rule` | `'primary'` |
  | `doctrine` | `'secondary'` |
  | a finding aid — encyclopaedia, digest, headnote, citator summary, blog, AI summary | `'tertiary'` (no `kind` value yields this today) |

  **`source` is set from `kind`, never from what the excerpt cites and never from the deciding court.** A case is `'primary'` for every proposition it is cited for — its own holding and an earlier holding it adopts alike — and a later case citing an earlier one for the same principle is the *stronger* authority for having adopted it, never demoted to `'secondary'`. That is the opposite of the fact side, where each hand between the thing and the forum weakens the account; the two ladders share no vocabulary (terms-and-symbols.md → Axes of reliability, which also lists the nine banned crossing terms).
- **`authorities.weight`** measures whether the tribunal must accept the authority (`binding`/`persuasive` — the old `'doctrinal'` tier value no longer applies here; a doctrinal source is now expressed on the *statement*, via `statements_of_law.source='secondary'`), not source reliability — that is the separate **`statements_of_law.verification`** column (`verified`/`lead`, schema v25, `failed` since v46 and `settled` since v47, below; required on every insert, no default; `'lead'` is the tier-3-lead state, `User_Journeys/broad-sweep-to-verified-authority.md`). Whether a given court's decision is `binding` or merely `persuasive` **before a VanIAC arbitral tribunal** is itself a question of law, not a fact you can read off the court's name — never guess it from a rule of thumb like "SCC/BCCA = binding, BCSC = persuasive." Only `/legal-research` (or the practitioner, directly) sets `weight`; any write without that classification for this forum leaves `weight` NULL (a bulk-population or import pass also writes `verification='lead'` on each statement row), and another row's `weight` is never grounds for a value.
- **Recording a scrutiny return and closing its review**: `references/scrutiny.md`. Since v61 a verified statement needs a pinpoint: a move into `'verified'` with none is refused.
- **Recording whose words an excerpt is** (schema v61): when the excerpt captured is words the judgment attributes to another source (a quotation followed by its citation, "per <judge>" or "[at p N]"), set `excerpt_speaker = '<that source, as the judgment names it>'` in the same write as the excerpt. NULL is the court's own words. It prints a `(quoting <source>)` tag on the mockup, withheld from the forum, and changes neither `source` (still set from `kind`) nor `verification`.
- **Killing an authority** (schema v16): the practitioner reviewed the case and rejected it — never delete the `authorities` row or its `statements_of_law` rows (they stay as the breadcrumb). `UPDATE authorities SET killed_on = '<today, YYYY-MM-DD>' WHERE id = N`; nothing else needs to change in the same script — a killed authority's statements ride the same brief-only cap as `verification='lead'` (excluded from 📖/📜/📍/🥇/🥈/🥉 the same way), so no separate deployment cleanup is needed the way a submission's `filing_submissions` rows are. Restoring it: clear the date. **Before running a research sweep or proposing a new authority for a proposition, check the proceeding's existing `authorities` for one already carrying `killed_on` matching the same `style_of_cause_or_title`/`citation` — pass it to `/legal-research` as an exclusion rather than re-researching or re-adding it.**
- **Omitting a proposition** (schema v64): the practitioner says a proposition of law does not matter to the case. Written only when the practitioner says so, never proposed or inferred by a session. Never delete the `law_assertions` row, its `statements_of_law` rows or its links: they stay as the breadcrumb. `UPDATE law_assertions SET killed_on = '<today, YYYY-MM-DD>' WHERE id = N`. Nothing else changes in the same script. Only the Raw Research page reads the omission, where its card prints struck through. Everywhere else the proposition stays live until the practitioner unlinks it: linked to a submission (`submission_law`), required by an order (`order_sought_requires`, by `law_assertion_id` or through one of its statements as `excerpt_id`), or with a statement cited in a Writing's own text (`filing_law`), it keeps printing on those mockups and on the filed face, with no tag. Restoring it: clear the date. **Before sending a question to `/legal-research`, read every omitted proposition of the proceeding (`law_assertions` with `killed_on` set) and pass each one to `/legal-research` verbatim as a named exclusion. The session compares none of them with the question or with any other proposition.**
- **Recording a statute-currency result** (schema v34): once `/legal-research` relays the statute-currency check's `currency` value for a `statute`/`regulation`/`rule` authority, `UPDATE authorities SET currency_status = '<value>', currency_checked_on = '<today, YYYY-MM-DD>' WHERE id = N`. Any `UPDATE` of that row's `citation` or `style_of_cause_or_title` sets both to NULL, enforced by a trigger since v35, so record the fresh result in a later statement than the rename. The full contract is SKILL.md → CRUD guidance, "Statute currency is a stored, relayed result".
- **Recording a provision's currency result** (schema v53): once `/legal-research` relays the result for a provision a statement of law pinpoints on that authority, `INSERT INTO provision_currency (authority_id, provision, currency_status, checked_on, current_to, amended_on, amendment_checked_on, in_force_on) VALUES (N, '<the statement's pinpoint, verbatim>', '<value>', '<today, YYYY-MM-DD>', '<"current to" date>', <newest amendment's effective date after it, or NULL>, <date that amendment was checked, or NULL>, <the provision's in-force date, or NULL>) ON CONFLICT (authority_id, provision) DO UPDATE SET currency_status = excluded.currency_status, checked_on = excluded.checked_on, current_to = excluded.current_to, amended_on = excluded.amended_on, amendment_checked_on = excluded.amendment_checked_on, in_force_on = COALESCE(excluded.in_force_on, provision_currency.in_force_on)`. `in_force_on` (schema v61) is the date the publisher's own page shows the provision came into force, relayed with the result; NULL when it shows none, and a later result without one keeps the recorded date. 🕰️ reads it. One row per provision, so "Rule 8-1 amended; Rules 9-6, 3-4 and 14-1 untouched" is four rows. `'current'` is refused without the "current to" date and while a recorded amendment is unchecked: record `'amendment-unchecked'` until it is checked. The full contract is SKILL.md → CRUD guidance, "Statute currency is also recorded per cited provision".
- **Recording a legislation record**: `/legal-research` relays one record per enactment, `citation | title | path | sha256 | currency_marker | currency | official | key | provisions`, however many of its provisions were named; record one `provision_currency` row for each provision it lists. Its `path`, unless `none`, is the authority's locator: `UPDATE authorities SET url_or_locator = '<path>' WHERE id = N`, which "Locating an authority's own text" then returns. Its `currency` is recorded as "Recording a statute-currency result" above. Its `currency_marker`, written `YYYY-MM-DD`, is the `current_to` of every `provision_currency` row recorded from that record, as "Recording a provision's currency result" above. `sha256` has no column: it stays in the filed file's header and the folder's manifest.
- **`order_sought`**: `wording`, `amount` (numeric — the Written Argument's Rule 24(j) cap paragraph sums `amount` across every row this Writing deploys (`filing_orders`) that is not crossed out (`crossed_out_on IS NULL`); omitting it silently understates the total, it does not gap-flag), plus a separate **`order_sought_requires`** row per jurisdictional basis: `basis_state` (`'needed'|'filled'|'dead_end'`, **NOT NULL with no DEFAULT — every `order_sought_requires` insert must supply it explicitly or the insert fails**). `'needed'` renders the 🏛️ jurisdictional-basis marker, `'dead_end'` renders 🚧; only use `'filled'` once `excerpt_id` points at a `statements_of_law` row (FK enforced) — that row's `law_assertion_id` is left NULL (a standalone jurisdictional citation, not a doctrinal proposition), `authority_id` set to the authority for the tribunal's power to grant this order, `pinpoint`/`excerpt` captured as usual. **Jurisdiction statements are legal content — only populate them from what `/legal-research` or the practitioner supplies, never invented** (same rule as the doctrinal legal-basis guidance above). Link the order into the Writing's rendered document via `filing_orders(filing_id, order_sought_id, document, ordinal, wording_override?)`. `wording_override` is the text this one Writing prints instead of the shared `wording`. Set it whenever an order written for one kind of Writing is reused in another: Form 8 wording states a judgment ("The Defendants shall pay…"), while a Notice of Application asks for one ("An order that the Defendants pay…"). Renderers print whichever text they are given, word for word.
- **Witness statements** (one per witness giving evidence on this Writing): `witnesses` row, then a `documents` row for the statement itself (`instrument='witness_statement'`, `deponent=<witness id>`, `execution` — NULL renders 🖋️ "sign it", but only once ≥1 paragraph is linked to a statement of fact; an unsigned statement with nothing drafted yet renders the statement-level 🧩 below instead, never 🖋️), linked into the Writing via `filing_documents(filing_id, document_id, ordinal, role='witness_statement')`. `statement_paragraphs(document_id, ordinal, text)` — one row per numbered paragraph, `document_id` pointing at that same witness-statement document. Link each paragraph to the witness's own statement of fact via `paragraph_statements_of_fact(statement_paragraph_id, statement_of_fact_id)` (composite key, no `id` column) — a paragraph links to the *statement of fact*, not the fact itself (closes the double path); an unlinked paragraph renders 🧩. A witness with **no** `statements_of_fact` row at all renders a derived statement-level 🧩 *no facts attributed to this witness*, and any row attributed to the witness but not yet linked to a paragraph of this statement lists in a trailing *Facts attributed to this witness, not yet in this statement* subsection — one line per fact, `facts.postulate` plus its posture note plus its rung (🗣️/✍️/📌/🧷; never 🖋️, since unlinked means not yet written in this instrument) — rendered for the human, withheld from the filed face (build #329, decision #320).
- **`facts`**: only needed here as the target of a `statements_of_fact` row a paragraph links through (the Written Argument itself doesn't read `facts` directly — the Notice of Application does, see §2).
- **Evidence Index**: `documents` rows (`label`, `document_date`, `description` — NULL `description` renders 🏷️) linked via `filing_documents(filing_id, document_id, ordinal, role)`, numbered in citation order by `ordinal`. `role='witness_statement'` rows are excluded from the Evidence Index — those are their own rendered documents, not exhibits. **Tendered by** (issue #330/#333/#339): a document is tendered either by a witness (set `statements_of_fact.exhibit_id` on the statement tendering it) or by a party's admission of its foundation fact (insert an `admissions` row with `exhibit` set to the document — supply `proceeding_id`, `fact_id` = the foundation postulate, `party`, `method`; `UNIQUE(fact_id, party, method)` means one row per party per method on that postulate). Either clears 👤 *no witness* on the exhibit's own Evidence Index line (👤 and its spent-marker prefix apply only to role='evidence'/'other' rows — #398; other roles never carry the marker) and lists the tendering witness or admitting party (as "*name* (admission …)") in the Tendered by cell — but only while the admission's derived ladder state is a genuine tender or still-live work (issue #345: a denied/refused/no-knowledge/struck admission tenders nothing, drops out of the Tendered by cell, and its event marker renders instead as a prefix on 👤). `admissions`' other columns (`instrument`, `response_due`, `response`, `answer`, `struck_on`, ...) drive that derivation (issue #344/#345, `terms-and-symbols.md`'s admission-ladder table) — record real values when in hand, leave NULL otherwise; an admission is never held in reserve — the table carries no deployment pointer, every row counts (unlike `facts`/`submissions`/`order_sought`, whose reserve status is derived from deployment, not stored).
- **`opposing_points`** (a response or reply round only, build #359): one row per point the exchanged opposing package advances — `proceeding_id`, `component` (which document/section it's from, in the opposing package's own words, e.g. "Opposing written argument, Submission 3"), `pinpoint` (its numbering there), `verbatim_words` (quoted character-for-character from the read opposing package — never paraphrased or reconstructed from memory), `ordinal` via §7's scalar-subquery idiom scoped to `proceeding_id`. Leave `answered_by_submission_id` NULL when the point is written — it renders ↩️ *rebuttal needed* until a responsive `submissions` row answering it exists, at which point set it to that row's `id`. The table carries no `filing_id`/round column — it is proceeding-scoped, read as one running inventory across every responsive round on the proceeding, not reset per Writing.
- **Rebuttal links** (schema v65, any round): when the practitioner says a submission answers a counter-argument, insert `submission_rebuts_opposing_points(submission_id, opposing_point_id)` for a raised point or `submission_rebuts_anticipated_points(submission_id, anticipated_point_id)` for an anticipated one; one submission may answer several points and one point may have several answers. The links only group arguments on the Arguments view page. They are advisory, neither complete nor exhaustive: they never set or clear `answered_by_submission_id` or ↩️, and a point with no link is not unanswered. When a spent `anticipated_points` row is replaced by its `opposing_points` row, insert the same submissions into `submission_rebuts_opposing_points` for the new row, then delete the old row's `submission_rebuts_anticipated_points` rows before the row itself, in the same script. Killing a submission leaves its rebuttal links in place: the page ignores a killed submission, and restoring it restores its links.

## 2. BCSC Notice of Application (`kind='notice_of_application'`, `subkind` NULL)

Requires `proceedings.forum='CAN/BC/BCSC'` and `courthouse_address` set (renders literally if NULL, so fill it).

- **`hearing_details`** — exactly one row per Writing (`filing_id` is UNIQUE): `proposed_hearing`, `hearing_date`, `hearing_time`, `time_estimate_minutes`, `associate_judge` (1 = within the jurisdiction of an associate judge, 0 = not within, NULL = not yet determined — the default since schema v20, #451). It drives Form 32's jurisdiction sentence, "This matter is [not] within the jurisdiction of an associate judge.", printed after the time estimate — get this right, it is a real procedural distinction, not cosmetic. Never write 0 or 1 in place of an answer the practitioner has not given: while the value is NULL (or the Writing has no `hearing_details` row), the mockup shows `Associate judge jurisdiction: not yet determined ⬜` in the sentence's place (work-markers.md ⬜), and both the filed face and `drafting_forms__emit_form32` refuse until it is set. A lenient `emit_form32` (the publish route) prints a placeholder in the sentence's place instead, and returns it as a warning for the document's NOT FINAL cover page. No loose thread is needed — the ⬜ line is the reminder. Which value is correct is a legal question for `/legal-research`.

  **Recording the proposed hearing.** Form 32 fixes no hearing date: it says the hearing is "on a date to be set by Notice of Hearing of Application" and prints the applicant's proposal, "The applicant(s) propose(s) that the matter will be heard on …". `proposed_hearing` holds that proposal as free text, as the practitioner gives it: a date, a date range or an assize. Never compute one here. It prints on the mockup and the filed face, and the filed face refuses without it. It does not meet the `hearing-date` criterion.

  INSERT INTO hearing_details (filing_id, proposed_hearing) VALUES (7, 'the week of November 2, 2026')
    ON CONFLICT (filing_id) DO UPDATE SET proposed_hearing = excluded.proposed_hearing;
  ```

  **Recording the hearing date.** `hearing_date` and `hearing_time` are the hearing actually fixed, for this Writing by the Notice of Hearing of Application. Record the date and time the practitioner gives, as given: never compute one here (deadline arithmetic is `practice:docket-clerk`'s job). One upsert, so a Writing with no row yet gains one and an existing row keeps its other columns. The write moves the revision like any `hearing_details` write, and a pre-filing gate run before it reads stale. It meets the `hearing-date` completion criterion.

  INSERT INTO hearing_details (filing_id, hearing_date, hearing_time) VALUES (7, '2026-11-04', '9:45 a.m.')

Marlowe*; it names the mockup file and the Part 4 line), `affidavit_number` (asked of the practitioner once, never inferred, per the Form 109 style guide), `execution` NULL until actually sworn (renders ✒️ *swear it* once ≥1 paragraph is linked), `file_path` (the best copy `assemble-affidavit` reads) — linked via `filing_documents(filing_id, document_id, ordinal, role='affidavit')`.   - **Exhibit-only paragraph**: linked to a foundation statement of fact. `facts.postulate` is the identification fact (*Document 1.03 on the Defendants' List of Documents is the First Amending Agreement dated …*). The statement carries `witness_id` = the deponent, `instrument` = the affidavit the paragraph belongs to, `exhibit_id` = the exhibited document, `interviewed=1`, `exhibit_excerpt` = the document's identifying text verbatim (its title and date as printed, or the List of Documents description as printed) and `exhibit_pinpoint` = where that text sits (the page bearing the title and date, or the List of Documents entry the paragraph quotes); `excerpt` stays NULL. Fill these columns rather than exempting the statement from 📑/📌/🧷 — an exemption would be an SSOT edit.

  - **Pinpoint** (`statements_of_fact.pinpoint` = *para N*) is written last, once paragraph order is settled.
  - **A sworn affidavit** (`execution` set) is not revised. A change is a further affidavit. Once sworn, re-check each `court_record` and `instrument` link to it against the sworn copy. When you set `execution`, also set `exhibit_letters` to the sworn copy's exhibit letters (`A-J`, or `A-J, L` when letters are skipped), and leave it NULL only when the sworn exhibits are unknown.

## 3. BCSC Requisition — Default Judgment (`kind='requisition_default_judgment'`, `subkind='default_judgment'`)

Two drafts render off one Writing: the Form 17 requisition and the Form 8 draft judgment. `subkind` must agree with the kind (`requisition_default_judgment` ↔ `default_judgment`, `requisition_consent` ↔ `consent`); the renderer keys on `kind`. **A `requisition` Writing with NULL `subkind` passes the schema CHECK constraint but throws `ValidationError` at render — `subkind` is mandatory in practice even though the column allows NULL.**

- **Checklist lines on the Form 17**: `filing_documents` rows with `role='order'` (draft judgment attached) and `role='affidavit'` (affidavit of service/non-delivery) — each missing role renders its ⬜ "not yet attached" line. No supporting-materials list beyond these two roles.
- **Checklist attachment** (the "Attach the missing order or affidavit" job): an existing document, already filed or already made, attached to clear a ⬜ line. The renderer reads only the `filing_documents.role`, so the `documents` row records the copy and nothing more. Write `proceeding_id`, `label` (the document's own title, e.g. *Affidavit of Service #1 of A. Marlowe*), `description` and `file_path` (stored form, §0). Leave NULL `instrument`, `deponent`, `execution`, `signed_at`, `affidavit_number`, `exhibit_letters`, `served_on` and `document_date`, unless the practitioner gives a value; never infer a sworn date, deponent or affidavit number. Never set `instrument='affidavit'`: that marks the row as an affidavit drafted here, and §2's recipe would then render an empty affidavit mockup wherever the document is also selected with `role='affidavit'`. `is_best_copy` keeps its default unless the practitioner says. Then the `filing_documents` row: `role` `'affidavit'` or `'order'`, `ordinal` by §7, `provenance` NULL (the Form 17 has no Part it prints in). Both inserts are guarded, so a rerun writes nothing twice. For filing 7, proceeding 2:

  ```sql
  INSERT INTO documents (proceeding_id, label, description, file_path)
    SELECT 2, 'Affidavit of Service #1 of A. Marlowe', 'Affidavit of service of the notice of civil claim and of non-delivery of a response', '<stored file_path>'
    WHERE NOT EXISTS (SELECT 1 FROM documents WHERE proceeding_id = 2 AND file_path = '<stored file_path>');
  INSERT INTO filing_documents (filing_id, document_id, ordinal, role)
    SELECT 7, d.id, (SELECT COALESCE(MAX(ordinal), 0) + 1 FROM filing_documents WHERE filing_id = 7), 'affidavit'
    FROM documents d WHERE d.proceeding_id = 2 AND d.file_path = '<stored file_path>'
      AND NOT EXISTS (SELECT 1 FROM filing_documents WHERE filing_id = 7 AND document_id = d.id);
  ```

  A job outlined from the `unchosen` Proposal holds `documents` in its scope for this write (§6a). §2's drafted-affidavit recipe is unchanged and is for an affidavit drafted for the Writing, not one attached to a checklist.
- **Form 8 operative terms**: `order_sought.template_key` — a **renderer-enforced closed set, not schema-constrained** (bare TEXT column): `sum_certain`, `damages_to_be_assessed`, `delivery_or_assessed_value`, `assessed_value_for_operative`, `interest_as_claimed`, `interest_coia`, `costs_fixed`, `costs_to_be_assessed`. Any other string renders `🏷️ unrecognized template_key "…"`. If an answer fits no listed value, say so and ask which to use — never silently substitute one. `template_values` is a JSON-text column; the keys it must carry depend on `template_key`: `amount` (numeric) for `sum_certain`/`interest_as_claimed`/`costs_fixed`; `description` (string) for `delivery_or_assessed_value`; no keys needed for the other four. For `interest_as_claimed`, never compute `amount` by inference — invoke `/calculate` with `court-interest-calculator` for statutory Court Order Interest Act interest, or with `contract-interest-rates` for a contractual interest term, and store the total that skill reports. The principal and interest dates it needs are matter facts, elicited like any other field here; only the arithmetic is delegated. Rows this Writing deploys (`filing_orders`) that are not crossed out (`crossed_out_on IS NULL`) render as ordered operative paragraphs ("THIS COURT ORDERS"/"THIS COURT FURTHER ORDERS"); use `alternative_to` to chain a fallback order to its parent (renders as its own top-level order paragraph marked "in the alternative", its marker following its own served or struck state like any other order) — **an alternative row must be referenced only via `alternative_to`, never also joined into `filing_orders` directly, or it renders twice** (once as the primary chain, once as its own top-level order).

The excerpt and pinpoint markers each split by basis — 📜 and 📍 for an authority, 📑 and 📌 for an exhibit, 💬 and 🧷 for testimony — so a statement of fact owing both locators renders `📌 🧷` on the one line, and a collapsed Job Board card shows at a glance which kind of source the work needs.

**The unless-admitted guard** silences 💬, 📑, 📌 and 🧷 on a statement of fact exactly where it silenced 📍 before the split: a fact admitted by the party it is being proved against, or proved by the court's own record, needs no excerpt or locator from a witness. It never silences the excerpt and pinpoint owed on an admission instrument's own response, or the 📌 owed on a `facts.court_record` link with no `court_record_pinpoint` — every proof path still ends at a pinpoint.

None of this is a checklist to *clear before writing* — an accurate `'needed'`/NULL state that reflects real unfinished work is correct data, not a defect. The defect is a field left unset that *should* have a value already in hand (a signed statement recorded as unsigned, a known pinpoint omitted).

## 6b. Citations in the text (`noting-up`)

Every type file in `/draft`'s tree declares `noting-up` (`shared/declared-layout.md` §6), so a Writing that cites anything carries the criterion "Note up all cited authorities". Its members are 📇 on an authority's line, which the note-up job clears (§6, §6a), and each citation in the Writing's text that no `authorities` row tracks, which the citation scan finds.

**What the scan reads.** On each mockup render the runtime reads the filed face of every document that goes to the forum or the recipient: the venue document and Written Arguments, never the Counsel Brief or the Job Board. It skips a fenced block and a line opening `>`, which hold an excerpt's own words, not the Writing's.

**What it finds.**

- A neutral citation, with or without a pinpoint: `2019 BCCA 123`, `2019 BCCA 123 at para 4`, `1997 CanLII 400`.
- A reporter citation whose year is in brackets or parentheses, with or without a pinpoint: `[2008] 1 SCR 190`, `(1990), 74 DLR (4th) 321`.
- A statute or regulation citation: `RSBC 1996, c 238`, `SBC 2012, c 13`, `BC Reg 168/2009`, `SOR/98-106`.
- A case name in italics: an italic run in the text, `*Smith v Jones*` or `_Smith v Jones_`, that names two parties joined by `v` or `v.`, or opens `Re`. An italic name followed directly by its citation is one citation. A short form with no `v`, such as `*Smith*`, is not found.

**What tracks a citation.** A live (not killed) `authorities` row of the Writing's proceeding: by citation first (case, periods and commas ignored, the row's `citation` holding the found citation whole, parallel citations included), then by style of cause (`style_of_cause_or_title`, letters and digits only, `v.` read as `v`).

**What it raises.** Each untracked citation, once per Writing, prints a line at the head of the venue document's mockup, `📇 Cited but not tracked: <citation or name>`, rendered for the human and withheld from the filed face, and is an unmet item of `noting-up` on the Job Board, `cited but not tracked: <citation or name>`. The pre-send hold reads it from the render's inventory, as it reads every held criterion (§13 "Sent write"). It clears when the authority is recorded (§0) with the statement of law that relies on it, linked to the Writing as its kind links statements, after which 📇 asks for the note-up as for any authority. Killing the authority does not clear a citation still in the text: take the citation out of the text.

The scan never states law and never fetches anything: it only matches text to rows. It never refuses the filed render. Because it computes what `filings.authority_confirmed_on` attested, a Writing whose layout declares `noting-up` is outside the `authority-confirmed` check (§13 "Authorities cited").

A Writing created before its type declared `noting-up` keeps its stored layout. Its mockup prints the scan's lines, but its card counts them only after a re-snapshot (`drafting_data__resnapshot_writing`), which runs only while the Writing is drafting and only on the practitioner's instruction.

## 7. Ordinal auto-assignment

Every join row above carries a NOT NULL `ordinal` with no schema default or auto-increment (design doc §1: ordering is by explicit `ordinal`, never rowid) — `/draft` must supply a value on each `INSERT`. When appending to the end of a sequence, compute it with a scalar subquery in the same `INSERT`, never by counting rows in a separate query and carrying that count in mind across statements:

```sql
INSERT INTO filing_submissions (filing_id, submission_id, document, ordinal)
VALUES (7, 12, 'form',
        (SELECT COALESCE(MAX(ordinal), 0) + 1 FROM filing_submissions WHERE filing_id = 7 AND document = 'form'));
```

The scope column to filter on is each table's own parent: `proceeding_id` for `parties`; `filing_id` **plus** `document` for `filing_submissions`/`filing_orders`/`filing_facts` (each advocacy document — `'form'`/`'written_argument'` — numbers its own pointer list separately, per terms-and-symbols.md's Deployment section); `filing_id` alone for `filing_documents` (no `document` split there); `filing_rhetoric` takes no append subquery, because its ordinal is a position on its host part's scale (§15); `document_id` for `statement_paragraphs`. `drafting_data__execute` takes a `sql_script` string only — no bind parameters — so the scope id is a literal in both the `VALUES` list and the subquery. Do not write it as `last_insert_rowid()` across several child inserts: after the first child row it refers to that child, not the parent.

**When the subquery is used, one `INSERT` per row — never a multi-row `VALUES` list.** `drafting_data__execute` runs a script's statements sequentially inside one transaction, so a second `INSERT` in the same script sees the row the first one added and computes the next ordinal correctly — but a single `INSERT ... VALUES (...), (...), (...)` evaluates every row's subquery against the same pre-statement snapshot and assigns the same ordinal to all of them. Several rows into the same table+scope in one `execute` call are separate consecutive `INSERT` statements. (A multi-row list with explicit literal ordinals is fine.)

The subquery handles append only. Deleting a row leaves a gap — harmless, every renderer orders by `ordinal` relatively. Inserting at position *N* needs a shift in the same script before the `INSERT`, e.g. `UPDATE filing_submissions SET ordinal = ordinal + 1 WHERE filing_id = 7 AND document = 'form' AND ordinal >= 3;` then the new row with `ordinal` = `3` as a literal. Reordering rewrites each affected row's ordinal explicitly.

This is arithmetic, not schema — no new MCP tool. `drafting_data__execute` stays a generic connection-discipline primitive; the idiom above is composed at write time by `/draft`, same as every other statement in this checklist.

## 8. Revision discipline

`drafting_data__migrate` seeds `db_meta.value='0'` for `key='revision'`, and **the database moves it from there — no script needs to** (schema v21, [#607](https://github.com/Mharbulous/CoClerk/issues/607)). Every non-exempt table carries `AFTER INSERT`, `AFTER UPDATE` and `AFTER DELETE` triggers (`rev_<table>_ins|upd|del`) that run the bump themselves, so the #290 review model (mockup staleness = its stamped revision vs. current `db_meta.revision`; regeneration archives the superseded copy only when they differ) no longer rests on anyone remembering. Write no `UPDATE db_meta … key = 'revision'` statement of your own; one left in an older script is harmless, just redundant.

Revision advances **by row, not by script**: a script inserting three rows moves it three times. Only equality is ever compared, so this shows up in archive names and nowhere else.

**Exemption (schema v15, ADR 0009):** thirteen tables carry no triggers — the job tables `tickets`, `ticket_steps`, `ticket_scope`, `ticket_blocks`, `ticket_conflicts`, `seeds`, `ticket_proposals`, `proposal_rejections` and `ticket_answers` (schema v52), plus the review tables `review_approvals` and `review_points` (schema v27), the on-the-fly revision audit table `paragraph_revisions` (schema v57, `paragraph-revision.md`) and the board pointer table `board_attachments` (schema v67, §14). A write confined to these thirteen tables never bumps `db_meta.revision`, even though it is an `INSERT`/`UPDATE` — bumping on a job claim, a step tick, a conversion, a rejection, a saved answer, an approval, a discussion point or an attachment would archive every mockup in the Writing and stale the gate on ordinary session bookkeeping the practitioner never asked to review. Approving or discussing changes no substance. See `.claude/skills/drafting-data/SKILL.md` "Job and scrutiny operations" for the write mechanics. A script that writes both a job table and a substance/filing table in the same `execute` call moves revision for its substance rows alone — the same outcome the old end-of-script convention produced. `db_meta` carries no trigger either, so the bump cannot recurse.

**Not exempt:** setting or clearing `submissions.killed_on` / `authorities.killed_on` (schema v16) or `law_assertions.killed_on` (schema v64) is an ordinary substance `UPDATE` — the trigger moves revision for it like any other write in this section, unlike the job-table exemption above.

## 9. Document-pointer elicitation (WA-only default)

Design settled in #402, built in #410. For a Notice of Application, Application Response, or requisition, a newly drafted item deploys to the Written Argument (`document='written_argument'`) by default; reaching the venue form as well needs an explicit practitioner choice (one exception: a Notice of Application's orders — table below), written as a second pointer row (`document='form'`) alongside the first. `document='form'` alone is never written through ordinary elicitation — every form deployment carries a Written Argument pointer too. This is why `looseThreadMarker` (🧵, form∧¬WA) is never triggered by new drafting; it stays a genuine signal only on legacy data and later drift (below).

**Note on §2 and §5's own wording:** where those sections write `document='form'` in a join description (§2 Part 2, §5 Parts 4–5), that names what the *form renderer reads at render time* — it is not the write-time default. The write-time default for a newly drafted item is `document='written_argument'`, per this section.

**Which kinds ask, and about what:**

| Kind | Facts | Submissions | Orders |
|---|---|---|---|
| Notice of Application (§2) | ask | ask | both, no ask — the court is asked only for what Part 1 lists, so every order sought reaches the form and the Written Argument together; to hold one back, deploy it nowhere |
| Application Response (§5) | ask | ask | N/A — this kind has no `order_sought` of its own; its stance on the applicant's orders lives in `filing_positions`, which carries no `document` column and isn't part of this elicitation |

| VanIAC submissions package (§1) | exempt entirely — its venue document IS the Written Argument; both slots already read `document='form'` | | |
| BCCA stay response (§10) | exempt entirely — same reason as VanIAC: the response book's written argument IS the venue document; every pointer reads `document='form'` | | |
| BCCA respondent's factum (§12) | exempt entirely — the factum IS the venue document; every pointer reads `document='form'` | | |

**Mechanics.** Default (Written-Argument-only): one `INSERT` with `document='written_argument'`, ordinal via §7's `(filing_id, document)`-scoped subquery. "Both": two separate `INSERT` statements — never a single row or a combined flag — one per `document` value, each computing its own ordinal against its own `(filing_id, document)` scope per §7 (§7's own rule against a multi-row `VALUES` list applies here too: each `INSERT` is its own statement). For `filing_facts` specifically, `part` is `NOT NULL` on **both** rows if both are written — supply the kind's own value (`'part2'` for a Notice of Application, `'part4'` for an Application Response) on the Written Argument row exactly as on the form row; there is no shared or NULL-able `part` for a WA-only fact. A reconciliation or elicitation script that writes a substance row moves the revision through §8's triggers like any other substantive `execute` call.

**Legacy reconciliation.** The v9→v10 migration backfilled every pre-existing pointer row as `document='form'` with no `document='written_argument'` sibling — so a Writing migrated forward from before v10 lights 🧵 on every deployed line, live data on at least one matter today, not a hypothetical. The repair is mechanical: form placement was intentional under the old regime and stays correct, so add the missing `document='written_argument'` row for that item — never delete or alter the existing `document='form'` row. `/draft`'s session flow (step 2) is where this gets offered to the practitioner, on re-entering a Writing whose rendered mockup shows 🧵. Only the Notice of Application and Application Response renderers compute 🧵 at all — a requisition's own Form 17/Form 8 never do, so this reconciliation trigger structurally never arises there.

**Facts have no direct Written Argument render surface.** `renderWrittenArguments` reads facts only through `submission_facts` (a submission's own argument body) — never directly from `filing_facts`. A `filing_facts` row pointing a fact at `document='written_argument'` is a deployment/accounting pointer only: it clears 🂡 *reserved* and settles 🧵 accounting, but by itself puts nothing on any rendered page. A fact becomes practitioner-visible only two ways — deployed to the form (Notice of Application Part 2 / Application Response Part 4), or linked into a submission's argument (`submission_facts`) that is itself deployed. A fact pointed only at the Written Argument with neither renders nowhere — correct data reflecting real unfinished linkage, not a defect. On a Notice of Application or Application Response, a submission's linked fact that is also deployed to the form's facts part is not re-printed under the submission: the contention line names its Part 2 / Part 4 paragraph numbers in a `supporting fact paragraphs` comment. Since schema v59 the database places every fact a submission on a drafting Writing's form rests on in that part, last, with its `document='written_argument'` pointer row when the Writing has none for the fact, on the `submission_facts` insert or on the `filing_submissions` form insert, whichever comes second. Each placed row moves the revision, so mockups re-render, and a placed form row clears a recorded pure-law decision (Part 2 / Part 4 "Pure law" above). Removing a placed fact from the form, or changing its `filing_id`, `fact_id`, `document` or `part`, is refused while it stays attached to a submission on that form: detach it first, which also drops it from that submission's argument in the Written Arguments. Detaching a fact or killing a submission removes nothing from the facts part. Part 3 / Part 5 never prints fact text: a linked fact missing from the facts part (a database held below v59, or a Writing whose kind changed) is named `NOT PLACED` in the same comment, and the filed face of a drafting Writing refuses until it is placed. A sent or retired Writing renders as it was sent.

Attached exhibits for the table of contents are derived from `statements_of_fact.exhibit_id` rows whose `instrument` is the affidavit's document id — nothing separate to populate for the TOC itself.
- **Part 2 (written argument)** — paragraphs number consecutively across its four internal parts (e-CI §2.2). *Statement of Facts:* `facts` + `filing_facts(document='form', part='part2', ordinal)` — `'part2'` is this kind's own slot value (`'part4'` stays §5's). Same fact-side markers as every kind (statements need `pinpoint`, `excerpt`, `interviewed`, `instrument` to render clean). *Issues:* derived from `filing_positions` — nothing separate to populate. *Analysis:* `submissions`/`filing_submissions(document='form')` + the §1 legal-basis chain; the argument must state our position on the merits, irreparable harm, and balance of convenience (e-CI §2.1 (e)–(g)) — that coverage lives in the contentions themselves. *Order(s) Sought:* `order_sought` + `filing_orders(document='form')` (e.g. "The application is dismissed, with costs."); `crossed_out_on` strikes inline as everywhere else.
- **Part 3 (table of authorities, optional)** — derived: distinct authorities cited by deployed submissions, alphabetical, **excluding** any whose `id` appears as an `authority_id` in `opposing_authorities` for this proceeding (schema v13) — the delta e-CI §1.2 requires ("including new cases and sections of enactments that have not been referenced in the application book"). **`opposing_authorities` (schema v13)** — one row per entry in the *opposing* party's own filed application book's table of authorities, transcribed verbatim, anchored to the `documents` row for that book (`document_id`), `ordinal` matching its position in that book's table, `style_of_cause_or_title`/`citation` verbatim, and `authority_id` set to the matching row in our own `authorities` table where one exists (nullable — an opposing-only authority is still correctly recorded, it just never participates in the exclusion). Same seeding seam as `opposing_orders`: read the served book directly, confirm the transcribed list with the practitioner before writing. If no `opposing_authorities` rows exist yet for the responded-to document, the mockup renders the full cited list plus a 🕵️ note that the delta is unverified — this is expected until that book has been read, not a defect.
- **Formal limits the mockup reminds about** (comment lines, stripped from any filed face): written argument **max 5 pages** stay-only (10 if joined with leave — not this kind), Arial 12, 1.5 spacing, ≥2.5 cm margins; file and serve at least 2 business days before the hearing (deadline arithmetic is `practice:docket-clerk`'s job, not this schema's).

## 11. Writing lifecycle and retirement (schema v19, v32)

Seven states per Writing that needs forum parts — drafting → filed → heard → decided → entered → appeal period expired → retired. **Nothing stores the state**; it is derived per render (`source/practice/mcp/src/submission/forms/lifecycle.ts`) from four dates on `filings`, the Writing's `hearing_details.hearing_date`, and an appeal deadline the caller supplies. A reply or rebuttal is a sibling Writing (`round = 'reply'`), never a state of the Writing it answers.

**Derivation, in order — the first match wins:**

| State | Condition |
|---|---|
| Retired | `filings.retired_on` set |
| Appeal period expired | the caller-supplied appeal deadline is earlier than today (this is the one state that offers retirement) |
| Entered | `filings.entered_on` set |
| Decided | `filings.decided_on` set |
| Heard | the Writing's `hearing_details.hearing_date` is not NULL and not later than today |
| Filed | `filings.filed_on` set |
| Drafting | none of the above |

**A Writing that needs no forum parts** (`needs_forum_parts = 0`, §13) has three states: Retired (`retired_on`) → Sent (`filed_on`, labelled *Sent*) → Drafting. The derivation ignores the hearing date, `decided_on`, `entered_on` and the appeal deadline for it, and the schema refuses all three dates on it (v32 guard triggers: `decided_on`, `entered_on`, a `hearing_details` row, and a switch to `needs_forum_parts = 0` while any of those exists). A venue-kind letter needs forum parts, so it keeps `decided_on` and the full derivation.

**Appeal period expired always outranks Entered**, whether or not `entered_on` is set: BCCA appeal time runs from the date the order was pronounced (decided), not the date it was entered, so entry neither resets nor extends the appeal clock.

The NULL guard on the hearing date is load-bearing: VanIAC and requisition Writings may never carry one, and a missing date is "not heard", never "heard today".

**The appeal deadline is never stored here.** Deadlines are on `/drafting-data`'s "not stored, deliberately" list, and this one is no exception: `/draft` looks it up through `practice:docket-clerk` and passes it to `drafting_forms__render` as `appeal_deadline` (`YYYY-MM-DD`) for that one call. Omit it and the state simply stays underived — `drafting_forms__bootstrap` never passes one, so a board rendered by bootstrap never claims an appeal period expired.

**Write idioms.** All four dates follow v16's `killed_on` convention (named `dropped_on` until v26) — a DATE, set = the act happened and when, NULL = it has not, cleared to undo.

**`filed_on` is set through a tool, never by an update** (schema v42, party/counsel SSOT). A general Writing's Sent date is the Sent write's (§13). Any other Writing's filing date is `drafting_data__record_filed` `{db_path, filing_id, filed_on}` (`YYYY-MM-DD`): in one transaction it writes the party rows the Writing is filed with (`parties_snapshot`: names, roles and flags from `parties`, counsel and the address for service read from case data) and then sets `filed_on`. A Writing that already has snapshot rows keeps them. It refuses, writing nothing, `invalid_filed_on`, `not_found`, `writing_retired`, `already_filed`, `general_writing` (use the Sent write), `parties_drift` while a party's counsel or address for service cannot be read from case data (§0), and `revision_moved` when the database changed during the call. The v42 trigger `guard_filings_parties_snapshot` refuses any other statement that sets `filed_on` while the Writing has no snapshot rows and its proceeding has a party. Clearing a `filed_on` set in error stays an update, like every write of the other three dates:

```sql
UPDATE filings SET filed_on = NULL WHERE id = 7;   -- undo a filing date set in error
UPDATE filings SET decided_on = '2026-09-02' WHERE id = 7;
UPDATE filings SET entered_on = '2026-09-19' WHERE id = 7;
UPDATE filings SET entered_on = NULL WHERE id = 7;   -- undo
UPDATE filings SET retired_on = '2026-09-08', retirement_reason = 'appeal_expired'
  WHERE id = 7
    AND NOT EXISTS (SELECT 1 FROM tickets WHERE filing_id = 7 AND status = 'wip');
UPDATE filings SET retired_on = '2026-09-25', retirement_reason = 'delivered'
  WHERE id = 8
    AND NOT EXISTS (SELECT 1 FROM tickets WHERE filing_id = 8 AND status = 'wip');
UPDATE filings SET retired_on = NULL, retirement_reason = NULL WHERE id = 7;   -- recovery
```

That `NOT EXISTS` is what refuses a retirement on a Writing another session is working; `/drafting-data` §9a carries the rest of the retirement script, which puts the same clause on every statement, and its confirm-read. The recovery line takes no such clause — recovery reopens a Writing and has no equivalent precondition.

**Setting `filed_on` freezes that Writing's exhibits (schema v24, #712).** Three guard triggers refuse every insert, update and delete on a filed Writing's `filing_documents` rows. The only order that works is therefore **draft → link the exhibits → set `filed_on`**; linking one afterwards aborts with `a filed filing's exhibits do not change (#712)`. That is the freeze doing its job, not a defect: a VanIAC package's `Ex. N` is the document's position in one proceeding-wide ordered list derived at render time, so if a filed round's rows could still move, a later round's numbers would drift away from the paper already delivered. Clearing a `filed_on` set in error is an `UPDATE` on `filings`, which the guards do not touch, so the Writing reopens and its exhibits become editable again.

**A registry rejection is not a lifecycle state** (ADR 0023 D5). The re-file is the same Writing, never a new one. If `filed_on` was set, clear it with the undo idiom above, which also reopens the Writing's exhibits for the re-file.

**Two drafts in flight in one proceeding.** Both derive their numbers after the frozen prefix of filed rounds, ordered among themselves by Writing id. So changing the earlier draft's exhibits shifts the later draft's numbers. That is correct — a draft's numbers follow its ordinal until it is filed — but it surprises anyone who expects a number to be fixed from the moment it first renders. Nothing is wrong; file the earlier round to fix its numbers.

`retirement_reason` is a closed set: `'appeal_expired'`, `'appeal_exhausted'` (terminal), `'decided'` (retired on the practitioner's instruction once decided, with no finding that appeal rights were exhausted — schema v18, 2026-09-10; an appeal of a BCCA single-justice interlocutory refusal is the exception, not the rule, and the same recovery idiom above reopens the Writing if one is pursued), `'settled'`, `'abandoned'`, `'adjourned_generally'`, `'other'` (early retirement, only on the practitioner's explicit instruction), `'delivered'` (a Writing recorded as sent that asks for nothing — schema v32, ADR 0024 D5 as reconciled on #1047; since ADR 0042 D8 nothing offers it when a Writing is recorded as sent, and it is written only when the practitioner asks to retire a Writing for that reason). It is meaningful only alongside `retired_on` and is cleared with it. Every write in this section is an ordinary substance write — §8's triggers move the revision for it. The retirement write also supersedes the Writing's own open jobs in the same script (`/drafting-data` §9a, which has the session read for a foreign `wip` job **first** and stop before writing anything if it finds one, **and** puts a `NOT EXISTS` clause on every statement in the retirement script so that one appearing between the read and the write refuses the retirement rather than letting it land).

**A Writing with a draft attached to its board is not retired** (schema v67, ADR 0042 D4). Before the retirement write, read the attachments its board shows (§14, "Read a board's attachments"). For each one, the practitioner says which other board it moves to, any live Writing's or a pre-filing proceeding's board in the matter, or that it is detached; write each answer by §14's move or detach, then the retirement. Never move or detach one on the session's own choice. The v67 trigger `guard_filings_retire_attached` refuses the `filings` statement, and with it the whole retirement script, while an attachment names the Writing, or while the Writing is the last live one in its proceeding and an attachment there has no Writing.

**Retirement payload reads.** The retiring session hands the Writing's research to `/case-data`, and it reads that research through `drafting_data__query` like any other read — the law assertions, statements of law and authorities the Writing deployed, plus the `opposing_authorities` it answered. Nothing else may open this database (SKILL.md's Anti-Patterns). Exclude what the practitioner already rejected: `killed_on IS NOT NULL` rows and `law_assertions.dead_end` rows are not research anyone should inherit.

**Recovery check.** Before creating a new Writing, look for a retired Writing in the same proceeding that the new one would duplicate — same `kind`, same `round`, same `subkind`:

```sql
SELECT id, title, retired_on, retirement_reason FROM filings
  WHERE proceeding_id = 1 AND retired_on IS NOT NULL
    AND kind = 'notice_of_application' AND round IS NULL AND subkind IS NULL
  ORDER BY retired_on DESC;
```

A hit is offered as a recovery, never applied silently. Recovery clears the two retirement fields (above) and nothing else: `filed_on`/`decided_on` and every superseded job stay exactly as they were.

**What the renderers do with a retired Writing.** `drafting_forms__render` refuses `mockup` mode on one — `filing_retired: true`, a note, nothing rendered and nothing written, so the mockups stay as they stood at retirement; `filed` mode is unaffected. `drafting_forms__bootstrap` lists a retired Writing (recovery has to find it) with empty `paths`, its `retired_on`/`retirement_reason`, and `lifecycle: "retired"`, and skips rendering it — it does not throw. The Job Board carries a `State` meta row on every Writing and, in the appeal-period-expired state alone, a "ready to retire" notice. The `State` row reads *Sent* for a sent Writing that needs no forum parts, and a sent Writing stays on the board until the practitioner retires it (ADR 0042 D8).

**A Job Board with no Writing** is a `filings` row of the reserved kind `task-board`, written only by `drafting_data__create_job_board`, on a proceeding that already has a Writing, and never by `execute`. It derives none of the states above: it is Open, or Closed once `retired_on` is set. Closing it is the retirement write with `retirement_reason = 'other'` (`/drafting-data` §9a), and the recovery line reopens it. A closed one has no page and is listed under Retired on the Litigation Strategy page as "Closed <date>". `drafting_data__record_sent`, `drafting_data__record_filed`, `drafting_data__resnapshot_writing`, `drafting_forms__pre_filing_check` and a filed render refuse it.

## 12. BCCA Respondent's Factum (`kind='bcca_factum'`, `subkind` NULL)

Requires `proceedings.forum='CAN/BC/BCCA'` (schema v22, #648). The respondents' factum on an appeal (Court of Appeal Rules R. 25(2)); no prescribed form exists, so its parts follow the court's respondent's factum template and the factum completion instructions (R. 25(4); findings in `Engineering/bcca-appeal-books-inputs/research-findings-647.md` §1 and §5, and `research-findings-439.md` §2). Like §10, the factum IS the substantive venue document: every pointer row reads `document='form'`, no Written Arguments companion renders, and §9's elicitation is exempt. Draft-folder code `FACTUM`. The filed face is `drafting_forms__emit_bcca_factum`, filled into the court's template by `/publish` with `publish-bcca-factum`.

- **Cover** — the same columns as §10's cover bullets: `proceedings.registry`, `file_number`, `under_appeal_judge`/`under_appeal_court`/`under_appeal_pronounced`, `access_restrictions`; `parties` in notice-of-appeal order with `role` `Appellant`/`Respondent` and `lower_court_role`, and counsel of record and the address for service for both sides from case data (§0); `is_client` on our respondents.
- **Chronology (`filing_chronology`, schema v22)** — one row per critical event relevant to an issue on appeal: `filing_id`, `event_date` (`YYYY-MM-DD`), `event`, `ordinal` (§7 idiom scoped to `filing_id`). Renders as the template's Date / Event table.
- **Opening Statement (`filing_prose`, `slot='opening_statement'`, schema v22)** — one row per Writing (`UNIQUE(filing_id, slot)`); paragraphs separated by a blank line. Not paragraph-numbered. The mockup's page budget flags it past one page.
- **Part 1 — Statement of Facts.** First the respondents' position on the appellants' statement of facts: `filing_prose` `slot='facts_position'` (numbered paragraphs, from 1). Then any other facts: `facts` + `filing_facts(document='form', part='part2', ordinal)` — `'part2'` is the slot label this kind shares with §10, not a part number. Each fact's source is `facts.court_record` (a `documents` row for the appeal record, appeal book or transcript) + `court_record_pinpoint` (e.g. `Appeal Record, Vol. 1, p. 12`). Same fact-side markers as every kind.
- **Part 2 — Issues on Appeal.** One numbered paragraph per deployed submission's `contention`, in `filing_submissions` order. The appellants' points in issue are `opposing_points` rows (§0), `verbatim_words` from the appellants' factum; set `answered_by_submission_id` on each once a submission answers it. An unanswered point renders ↩️ in a mockup-only "Points not yet answered" listing. A submission answering no point is one of the respondents' other points.
- **Part 3 — Argument.** `submissions`/`filing_submissions(document='form')` and the §0 legal-basis chain, rendered as in §10's Analysis. An enactment reproduced briefly in the argument is a statement of law's `excerpt`.
- **Part 4 — Nature of Order Sought.** `order_sought` + `filing_orders(document='form')`; include the costs disposition as an order (the template requires one). The template's "The respondent seeks an Order:" and "All of which is respectfully submitted." are numbered; the order wording between them is not. Place of signing: `filing_prose` `slot='signing_place'` (the city). The date is not stored: `/draft` passes it to the emitter at assembly. The name authorizing filing is the client party's counsel of record, read from case data (§0), or the client party's own name if none (no signature block, R. 79(4)).
- **Appendices: List of Authorities** — derived: verified, non-killed authorities behind Part 3's law assertions, alphabetical, with each paragraph number that cites them. Page numbers fill in Word. Nothing separate to populate.
- **Appendices: Enactments** — derived: the `excerpt` of each statement of law whose authority is `kind` `'statute'` or `'regulation'`. Authorities recorded as `'rule'` are listed in a mockup-only note and left out of the filed appendix — and out of the Book of Authorities — unless re-recorded as `'regulation'`. They stay on the List of Authorities either way. Which kinds the book carries, and why, is `publish/subskills/publish-bcca-book/references/bcca-book-contract.md` (#813).
- **Formal limits the mockup reminds about** (a mockup-only page budget, never a refusal): Parts 1–4 at most 30 pages; the Opening Statement at most one page.

## 13. General Writings (schema v30)

A Writing is any legal writing `/draft` drafts, and every `filings` row is one; the kinds in §1–§12 are Writings that need a forum. This section holds the columns every Writing carries beyond those kinds, and the proceeding's service list. The layout contract the columns follow is `shared/declared-layout.md`.

**Creating a Writing.** Call `drafting_data__create_writing` (SKILL.md, Operation Routing) with the proceeding, the tree key and the kind. The kind must name exactly one row of the folder's kinds index by itself, by its file stem or an alias, because a re-snapshot resolves the stored kind with no recipient: resolve the user's phrase to that row's identifier first, since a shared alias refuses `kind_unresolved`. Under `_NoVenue`, pass `recipient` too: it must equal that row's recipient (`recipient_mismatch`) and never picks among rows. It writes the `filings` row, `layout_snapshot`, `needs_forum_parts` and the signer in one INSERT, and returns `filing_id`. The `title` names the Writing only and never holds the style of proceeding or the parties' names, which the Job Board prints from `proceedings.style_of_cause`: a title ending in ` - <style of proceeding>` is refused `title_holds_style`, nothing written, and the refusal names the trimmed title to pass instead. On the proceeding's first Writing the same transaction moves the drafts attached to the proceeding's own board onto the new Writing's board and returns their count as `attachments_moved` (§14): say in one line that they moved with the board, when any did. A script never inserts a `filings` row. Then, through `drafting_data__execute`, write the Writing's recipients by "Default recipients" below, which runs exactly one idiom, or neither for a Writing addressed to a person off the forum default, and write the Writing's prose rows.

- **`filings.needs_forum_parts`** (`1` or `0`): the type file's `needs_forum_parts`, true or false, written at creation and never guessed. An insert that omits it reads `1`. Guard triggers hold the fact:
  - a Writing with `needs_forum_parts = 1` cannot be inserted on, moved onto, or switched to `1` on a proceeding whose `forum` is NULL;
  - a proceeding's `forum` cannot be cleared while a Writing with `needs_forum_parts = 1` sits on it;
  - a Writing with `needs_forum_parts = 0` may sit on a forum-less proceeding, and moves on and off one freely.
- **`filings.layout_snapshot`**: the stored layout, one JSON text with five members: `{"layout": <the type file's layout block>, "venue": <the venue.md block, or null under _NoVenue>, "passage_hashes": {<rule_ref>: <sha256>}, "type_file": <the type file's knowledge path>, "venue_file": <the venue.md knowledge path, or null>}`. The two paths are what the filed render reads again to check each cited item's confirmation. Only the runtime writes it. A composing script never writes or edits it. The v30 migration filled it for every Writing that existed then, from `/draft`'s shipped type file and `venue.md`, each block copied verbatim, with `passage_hashes` empty because no shipped block cites a `rule_ref`, and without the two path members. Writing it is a `filings` update, so §8's trigger moves the revision: that is how the stored layout enters the render stamp. It is written at creation (`drafting_data__create_writing`) and by the dedicated re-snapshot write (`source/practice/mcp/src/submission/writing-snapshot.ts`) only, both runtime writes, and only while the Writing is drafting: a v32 trigger refuses any change to `layout_snapshot` or `needs_forum_parts` once `filed_on` or `retired_on` is set. Re-snapshot moves the revision and re-runs the needs-forum guard and the layout validation.
- **Signer.** `filings.signer_key` is a firm roster key, for a type whose `signer` is `lawyer` (the default); its default is this machine's `person` when that person is a lawyer. `filings.signer_party_id` is the signing party's `parties.id`, for a type declaring `signer: party`, such as a release signed by the client. A CHECK allows at most one of the two. `filings.signer_snapshot` stays NULL until the Writing is sent: an unsent Writing reads its signer's details live, and sending snapshots them.
- **Sent date: `filings.filed_on`**, the existing delivery date. For a Writing that needs no forum it records the day the Writing was sent, and it freezes the Writing's exhibits exactly as §11 describes. There is no separate sent-date column. Once `filed_on` or `retired_on` is set, v37 guard triggers also refuse every insert, update and delete of the Writing's `filing_law`, `filing_prose` and `filing_clauses` rows, so its cited statements of law, prose and clause selection are written before the Sent write, never after it (#1215). v58 guards do the same for its `filing_facts`, `filing_submissions` and `filing_orders` rows, so its facts, submissions, orders sought and each order's `wording_override` are settled before the Sent write too. The v44 guards `guard_filing_recipients_frozen_ins`/`_upd`/`_del` do the same for its `filing_recipients` rows, so its recipients and their roles and order are settled before the Sent write too (#1307), and a row can neither join nor leave a sent or retired Writing. The statement that first sets `filed_on`, by the Sent write or `drafting_data__record_filed` (§11), also fills each NULL `filing_clauses.wording_override` of the Writing with its clause's current `clauses.wording` (v38 trigger `snapshot_clause_wording_on_send`, #1227), so a later edit to a shared clause changes only drafting Writings. The same statement records each of the Writing's recipients in `recipients_snapshot` (v44 trigger `snapshot_recipients_on_send`, #1307; "Service list" below), and a recipient already recorded for the Writing keeps its row, even one removed and added back while a `filed_on` set in error was cleared: delete its `recipients_snapshot` row before setting `filed_on` again if its values changed in between. Setting `retired_on` alone snapshots nothing. Setting `filed_on` on a Writing already retired is refused by the v37 guard whenever a selected clause has no override, so record the Sent date before retiring, or recover the retirement (§11) first. A `filed_on` cleared in error leaves the filled overrides, and that Writing follows shared edits again only once they are set back to NULL. Everything else a sent Writing's mockup shows about its clauses stays live: the markers, the killed and currency tags, and the inventory items, which name the shared wording. A `needs_forum_parts = 0` Writing takes no hearing, decision or entry date (§11). A general Writing's Sent date is written by the Sent write below, never by `drafting_data__record_filed`.
- **`filings.sent_copy_id`**: the `documents` row holding the copy as sent (ADR 0024 D6), allowed on every kind. It is never linked through `filing_documents`, whose rows are exhibits.
- **Form copy (`form-source`).** A Writing whose stored layout has a `form-source` part (a venue's stock `unstructured` type) links the saved copy of the published form whose fixed wording it copies: the practitioner's saved file as a `documents` row (`label` naming the form, `file_path` the file's path), joined to the Writing by a `filing_documents` row with `role = 'other'` and its `ordinal` by §7. The part prints the lowest-ordinal such row as `<!-- form copy: document_id N -->` and nothing else. With none, it prints a gap, counted by `open-items`, and the filed render refuses `unwritten_gate_failed` naming `form-source`. Link nothing else to such a Writing with `role = 'other'`. The link freezes once the Writing is sent, as its exhibits do (§11).
- **Addressee and sender** are the Writing's own text. Prefill from `parties` or `recipients` is optional and confirmed, never automatic. Who receives the Writing is its `filing_recipients` rows.
- **Prose rows (`filing_prose`, slot open text since v33).** A general Writing's own text is one row per slot, `UNIQUE(filing_id, slot)`, written by an ordinary insert or update. A `slot:<name>` part of the stored layout reads the row whose `slot` is `<name>`, its paragraphs separated by a blank line and numbered as the part's `paragraph_numbering` says. The `addressee` and `sender` parts read the rows `slot='addressee'` and `slot='sender'`, printed line for line and never numbered. A row whose slot the layout does not declare is ignored. A declared slot with no row shows on the mockup as a gap, and the filed render refuses naming it. A row holds only wording that will be printed: each of its lines is checked at render, and a line that breaks a rule carries `🧩 <!-- format: <rules> -->` on the mockup, counted by `open-items`. The filed render refuses with `prose_format_gate_failed`, naming each line, on `bracket` (a placeholder in brackets, pre-filing check C2's pattern, so `[sic]` passes), `tbd` (a bare `TBD`, `TODO` or `TBC`), `note` (a line opening `Note:` or `Draft note:`) and `emoji` (an emoji the symbol table does not hold). `underscores` (three or more underscores) is flagged and never refused, because a blank underline is the placeholder a Writing leaves.

### Sent write

A general Writing (its stored layout's `renderer` is `general`) is recorded as sent through `drafting_data__record_sent` (SKILL.md, Operation Routing), ADR 0024 D6's "record as sent". A bespoke Writing records its filing date through `drafting_data__record_filed` (§11). Only an active roster lawyer records a Writing as sent: the runtime reads this machine's `person` from the firm profile and refuses a staff key (`not_a_lawyer`), an unset one (`person_unset`) and an inactive lawyer (`not_active`). Pass the Sent date as `sent_on`, a calendar date written `YYYY-MM-DD` (`invalid_sent_on` otherwise), and the copy as sent, either `sent_copy_path` (a `.eml`, `.pdf` or `.msg` file) or `sent_copy_text` (pasted text). A Writing none of whose `slot:<name>` parts has a prose row with a paragraph, and none of whose `terms` parts has a selected clause, has no stored text to check the copy against, and is refused `no_stored_text` before anything else runs. A Writing any of whose parties' counsel or address for service cannot be read from case data is refused `parties_drift` next (§0), before the hold, writing nothing. The call then runs three steps, and a refusal at any of them writes nothing, bar the Pre-send gate job the hold leaves:

1. **The pre-send hold**, on every general Writing, a venue's `letter` included (#1236). The runtime reads the inventory of the Writing's latest render from its render manifest and never renders: it refuses `render_first` when that render is older than the database revision or there is none. While a held criterion the type declares (`primary-authority`, `excerpts`, `noting-up`, `recipients`) is unmet on that inventory, or the universal `currency` check, read live from the database on every such Writing, or the universal `authority-confirmed` check after it (an unsent Writing that needs no forum parts and whose type declares `primary-authority` and not `noting-up`, with `filings.authority_confirmed_on` still NULL; §13 "Authorities cited"), is unmet (`/drafting-data` §14a), it writes the `Pre-send gate` job, one step per unmet criterion (`/drafting-data` §14a), and refuses `held`, unless `send_anyway` carries the practitioner's own words, verbatim, which it records as each open step's WAIVED form. `counsel-review` never holds sending. A venue's `letter` is held on the criteria its type declares (the venue letter types declare the three authority criteria, not `recipients`), and a bespoke Writing never reaches this write.
2. **The accuracy check.** The stored text is, in part order, each paragraph of a `slot:<name>` part's prose row and each clause of a `terms` part, in `filing_clauses` order, as its `wording_override` when set, else its wording (the text the `terms` projection prints, without its numbering, markers or killed tag). `references/scripts/sent_copy_compare.py` checks the copy contains each one, whitespace and curly quotes aside: a `.eml` and pasted text by the standard library, a `.pdf` by PyMuPDF. It refuses `sent_copy_mismatch`, naming each paragraph or clause the copy lacks: correct the prose rows or clauses to what was sent, or pass the copy that was sent. A `.msg` cannot be read without an external package, so it is recorded by path and not compared, and the result says so.
3. **One transaction.** A `documents` row for the copy (`label` `Sent copy — <title>`, `document_date` the Sent date, `description` naming the check that ran and the recording lawyer, `file_path` the copy's path, NULL for pasted text); the party rows the Writing was sent with (`parties_snapshot`, schema v42: names, roles and flags from `parties`, counsel and the address for service read from case data), unless it already has them; `filings.sent_copy_id` pointing at the copy; `filings.signer_snapshot`, the lawyer signer's roster entry or the signing party's id, name and role (a Writing with no signer is refused `invalid_signer`); and `filed_on`, the Sent date, which freezes the exhibits (§11) and moves the revision. It never writes `layout_snapshot` or `needs_forum_parts`, which the v32 layout-freeze trigger refuses in the statement that sets `filed_on`. The body and the recipients stand as their stored rows, the ones the check just compared. The same transaction carries the `Pre-send gate` job's writes (`/drafting-data` §14a): its steps rewritten, or the job created with them, each open step waived when `send_anyway` is given, and the job completed. It also closes the Writing's live `Deliver` job (`/drafting-data` §3b): both steps stamped `done_at`, since a recorded sent copy is the evidence that the send happened, and the job `completed` with its lock cleared. A `Deliver` job already completed, superseded or shelved (`/drafting-data` §10a) is left as it stands, and a Writing with none writes nothing extra. The result's `deliver` carries the closed job's `ticket_id`, null when none. A revision that moved since the hold read the inventory refuses the transaction as `render_first`, and a gate job that changed since the hold read it, so that it can no longer be completed, as `pre_send_gate_changed`.

It retires nothing, and recording a Writing as sent never offers retirement (ADR 0042 D8): the Writing stays on its board until the practitioner asks to retire it (§11). `comparison` says which check ran, and `note` says when a `.msg` was not compared.

### Service list

- **`recipients`**: one row per entry on the proceeding's service list, which holds each party's address for service (its counsel of record, or the party itself when it has none) and the forum's own addressees, and one per person off that list whom a letter is addressed to. `proceeding_id`; `name`; `capacity`, in the practitioner's own words (`counsel for the Respondent`, `the arbitrator`), NULL until the practitioner gives it, never guessed; `email`; `address`; `party_id`, the party this recipient is or acts for, NULL for the forum and anyone else not a party's (schema v43: a row with `party_id` NULL must have a `name`, and a party-linked row holds no `name`, `email` or `address`, so its entry is written with `party_id` and `capacity` alone; on a database held at v42, where `name` is NOT NULL, write the party's own name there, which the runtime never reads and the v43 hop clears); `ordinal` by §7's idiom scoped to `proceeding_id`; `forum_default` (schema v39, #1234), `1` (the default) when a Writing addressed to the forum copies the row by default, which is every service-list entry, the forum's own addressees and party counsel included, and `0` for a person a letter is addressed to who is not on the service list, such as a witness, an expert, a records custodian or an insurer. There is no closed list of who takes `0`: `capacity` says who they are. A represented party's own people are not entered: they are reached through counsel. `parties` is not extended, because its rows print in captions and cover pages. A row with `party_id` set takes its name, email and address from the party read, not its own columns (party/counsel SSOT): the Writing's party rows, read from case data while it drafts (§0) and from `parties_snapshot` once it is sent. Its name is the party's counsel of record, or the party's own name when it has none; its email counsel's email; its address the address for service, each left out where none is held. It holds no `name`, `email` or `address` of its own: schema v43 keeps all three NULL on a party-linked row, and the v43 hop cleared them on every such row. `capacity` stays the practitioner's words. On a drafting Writing, a party-linked recipient whose party is not one of its proceeding's fails the render, naming the recipient. A sent Writing never reads `recipients` (schema v44, #1307): `recipients_snapshot` records, for each of its recipients, the `capacity`, the `party_id` and, for a row with no party, the `name`, `email` and `address` it was sent with, so editing a row here, or pointing it at another party, changes only drafting Writings, and the row stays editable for later drafts. A party-linked recipient of a sent Writing takes its name, email and address from `parties_snapshot` by the recorded `party_id`. On a sent Writing whose recorded `party_id` its party rows lack, in practice one sent before the v44 hop whose snapshot took the `party_id` the row held at the hop (a party added after the send) prints a 🏷️ *not recorded* line in its place on the mockup, rendered for the human and withheld from the filed face.
- **`filing_recipients`**: a Writing's recipients. `filing_id`; `recipient_id`, once per Writing (`UNIQUE`); `role`, `'to'`, `'cc'` or `'bcc'`; `ordinal` by §7's idiom scoped to `filing_id` plus `role`. Frozen once the Writing's `filed_on` or `retired_on` is set ("Sent date" above).
- **On a general Writing's face**, after its last part: one `To:` line per `'to'` row, then one `cc:` line per `'cc'` row, each in `ordinal` order and reading `name — capacity (email | address)`, an absent field left out. `'bcc'` rows are rendered for the human under the mockup's "Blind copies" heading and withheld from the filed face. A Writing whose stored layout declares the `recipients` goal criterion and has no `'to'` row, a cc-only one included, prints the line `🧩 no To recipient` in their place, rendered for the human and withheld from the filed face. It never refuses the filed render: the Job Board and the pre-send hold carry it.

**Default recipients** (ADR 0024 D3). The addressee decides the default, so no purpose is stored. On a Writing with no `filing_recipients` rows yet, run exactly one of the two idioms below, once, then show the practitioner the list. A Writing addressed to a person who is not on the forum default, which is a letter created with `recipient` `witness` or `expert`, runs neither idiom: insert that person's `recipients` row with `forum_default = 0`, or use the one the proceeding already holds for them, and the Writing's `'to'` row for it, then show the practitioner the list. Its `name`, `capacity`, `email` and `address` are the practitioner's own words, never guessed: ask for any not given. Every default is written as `'to'`; the practitioner moves any of them to `'cc'` or `'bcc'`, and every later change is an ordinary insert, update or delete until the Writing is sent or retired, when the v44 guards refuse it ("Sent date" above).

A Writing addressed to the forum defaults to the proceeding's whole service list, the rows with `forum_default = 1`, less any client-side person:

```sql
INSERT INTO filing_recipients (filing_id, recipient_id, role, ordinal)
SELECT 7, r.id, 'to', ROW_NUMBER() OVER (ORDER BY r.ordinal)
  FROM recipients r
 WHERE r.proceeding_id = (SELECT proceeding_id FROM filings WHERE id = 7)
   AND r.forum_default = 1
   AND NOT EXISTS (SELECT 1 FROM parties p WHERE p.id = r.party_id AND p.is_client = 1);
```

A Writing addressed to a party (here party 3) defaults to that party's counsel, which is the party itself when it has none:

```sql
INSERT INTO filing_recipients (filing_id, recipient_id, role, ordinal)
SELECT 7, r.id, 'to', ROW_NUMBER() OVER (ORDER BY r.ordinal)
  FROM recipients r
 WHERE r.proceeding_id = (SELECT proceeding_id FROM filings WHERE id = 7)
   AND r.party_id = 3
   AND NOT EXISTS (SELECT 1 FROM parties p WHERE p.id = r.party_id AND p.is_client = 1);
```

Two rules hold over both idioms:

- **A without-prejudice offer never defaults to the forum.** Never run the forum idiom for one, whatever it is addressed to. It is addressed to a party, and the party idiom never picks a recipient with no party. A forum copy is added by hand only on the practitioner's instruction.
- **No client-side person by default.** Neither idiom picks a recipient whose party has `is_client = 1`. One is added by hand only on the practitioner's instruction.

### Clauses (schema v31)

A Writing with numbered operative clauses (a release, an undertaking, a settlement agreement) draws them from the proceeding's clause rows. Each row records where its clause comes from.

- **`clauses`**: one row per clause. `proceeding_id`; `wording`; `basis`, `'express'` or `'implied'`.
  - An **express** clause is taken from a document in the proceeding (the offer, the acceptance, a proposed form): `document_id` is that `documents` row and is required, `pinpoint` is the locator into it, and `excerpt` is its passage verbatim. `pinpoint` and `excerpt` stay NULL until captured, never guessed. `excerpt_id` must be NULL.
  - An **implied** clause is one the offer and acceptance carry without stating. `excerpt_id` may cite the `statements_of_law` row it rests on, and is NULL when it rests on none. `document_id`, `pinpoint` and `excerpt` must be NULL: its locator is the cited statement's own `pinpoint`.
- **`filing_clauses`**: a Writing's selected clauses, as `filing_orders` is for orders sought. `filing_id`; `clause_id`, once per Writing (`UNIQUE`); `ordinal` by §7's idiom scoped to `filing_id`; `wording_override`, NULL to print `clauses.wording`, set when this Writing words the clause differently, and filled with the shared wording when the Writing is sent ("Sent date" above).

Both tables are substance, so every write moves the revision (§8).

**Work markers.** These field values drive four work markers and the ⛔ event marker, which `work-markers.md` admits and the `terms` projection renders on the clause line. 📍, 🔬 and ⛔ read the cited `statements_of_law` row's fields or its authority's, never the clause's own: an implied clause's own `pinpoint` and `excerpt` are NULL, and it has no verification or treatment. ⛔ silences 📍 and 🔬 on that line. An implied clause with `excerpt_id` set whose cited statement's authority has `killed_on` set takes none of these markers, and its clause text carries ` (killed <date>)`. 🧐 is not among these markers: it still renders beside ⛔ or the killed tag while the clause is unapproved, since neither is a work marker and the clause line is not the authority's own. There 🧐 asks counsel to confirm the overruling as well as the wording, and an overruling after approval re-raises it, while a later kill does not (`work-markers.md` row 🧐; `review.md` Snapshot fields).

| Field values | Marker |
|---|---|
| `basis = 'express'`, `excerpt IS NULL` | 📑 excerpt needed: the source passage verbatim |
| `basis = 'express'`, `pinpoint IS NULL` | 📌 pinpoint missing: the locator into the source document |
| `basis = 'implied'`, `excerpt_id` set, that `statements_of_law` row's `pinpoint IS NULL` (the cited statement's field), its authority neither killed nor overruled | 📍 pinpoint missing: the locator into the authority |
| `basis = 'implied'`, `excerpt_id` set, that `statements_of_law` row's `verification = 'lead'` (the cited statement's field), its authority neither killed nor overruled | 🔬 scrutinize: confirm the lead's fit and ratio; co-renders with 📍 |
| `basis = 'implied'`, `excerpt_id` set, that `statements_of_law` row's authority has `treatment = 'overruled'` (the cited statement's authority's field) and is not killed | ⛔ not good law, an event marker rather than a work marker: the only one of these markers the line takes, bare, with no 📍, no 🔬 and no 🏛️ or 📖 reopen prefix, because routing is counsel's decision |

### Authorities cited (schema v36)

A case or enactment a general Writing's own text cites is a statement of law linked to that Writing (#1214). Which cases a Writing links is `/draft`'s rule.

- **`filing_law`**: a Writing's prose-cited statements of law. `filing_id`; `statement_id`, a `statements_of_law` row of the Writing's proceeding, once per Writing (`UNIQUE`). A guard trigger refuses a link across proceedings, on insert and on update. There is no ordinal: the mockup lists the linked statements by statement id. Deleting the row unlinks the statement and leaves it in place.
- **The write contract.** A prose-cited statement is recorded as a lead: `verification = 'lead'`, `law_assertion_id` NULL (it needs no proposition), and `pinpoint`, `excerpt`, `source` and `doubt` NULL until captured, never guessed. Its `statements_of_law` insert and its `filing_law` insert are one `drafting_data__execute` script, which runs as one transaction, so no render sees the statement without its link. When the authority is new, its `authorities` insert opens the same script. A statement already recorded, one a submission requires say, is linked by the `filing_law` insert alone.

```sql
INSERT INTO statements_of_law (proceeding_id, law_assertion_id, authority_id, verification)
VALUES ((SELECT proceeding_id FROM filings WHERE id = 7), NULL, 4, 'lead');
INSERT INTO filing_law (filing_id, statement_id) VALUES (7, last_insert_rowid());
```

`filing_law` is substance, so every write moves the revision (§8).

- **Authority confirmed** (schema v40, #1231). `filings.authority_confirmed_on` (a date, NULL until set) records that the Writing links every authority its text cites, or cites none. Nothing infers it from prose: a session sets it. The write that records a letter's statement of law sets it in the same script (`UPDATE filings SET authority_confirmed_on = '<today, YYYY-MM-DD>' WHERE id = 7;`), and a letter that cites no case sets it once when it is written. Every Writing that existed at v40 reads NULL, so an unsent one is held until a session sets it, and the mockup says so (below). The pre-send hold reads it live after `currency` (`/drafting-data` §14a), for an unsent Writing that needs no forum parts; a venue's `letter` is outside it. A sent Writing is never held on it: `record_sent` refuses one already sent, and v37 freezes its `filing_law`. A Writing whose layout declares `noting-up`, as every shipped letter and memo type does, is outside it too: the citation scan (§6b) computes whether its text cites an authority no row tracks, so no session sets the column for it.

**On the mockup.** Under the heading *Authorities cited*, after the `To:` and `cc:` lines, first, while `authority_confirmed_on` is NULL on an unsent Writing that needs no forum parts and declares `primary-authority` and not `noting-up`, a plain line with no glyph saying the authority is not confirmed (so `open-items` does not count it, and the heading prints even with no linked statement), then one line per linked statement: the authority's citation, with ` (killed <date>)` when the authority is killed, then the statement-line markers a doctrinal statement line prints (📜 📍 🔬 📇 🏅 👃, or ⛔, with 👃 when doubted, for an overruled authority; `work-markers.md`), then the statement's own 🧐 once no work marker is left on the line. A lead prints there, because the section reaches no sent face. A killed authority's line prints no marker, 🧐 included. The whole section is rendered for the human and withheld from the sent face. It stays live after sending: v37 freezes which statements a sent Writing links, but not the statements or their authorities, so noting-up done later, an overruling say, shows on the sent Writing's mockup (#1227). Its markers count toward the declared `primary-authority`, `excerpts` and `noting-up` criteria, so the pre-send hold reads them.

## 14. Board attachments (schema v67)

A client letter (`draft/references/letters.md` section 10) and a reply on the reply route (`draft/references/reply.md`, ADR 0040) are not Writings: no `filings` row, no job, no mockup. Each is attached to one Job Board by one `board_attachments` row (ADR 0042), a client letter by its folder, which holds its review draft and its send copy, and a reply by its file. The row holds the board and the path and nothing else. Never write a title, a status or any of the draft's text into this database: the Job Board reads a client letter's counsel's-review status from its review draft's first line each time it renders, and prints no other line of it.

- **`proceeding_id`** and **`filing_id`**: the board. `filing_id` names a live Writing's board, or an open Job Board with no Writing by its id. NULL names the proceeding's own board, which a proceeding has only while it has no Writing, live or retired (ADR 0018). When the proceeding gets its first Writing, `drafting_data__create_writing` sets `filing_id` on every such row to the new Writing in the same transaction and reports them as `attachments_moved`: the proceeding's board becomes that Writing's, so each draft stays on one board. A row with NULL in a proceeding that has a live Writing can only come from a hand-written insert; it shows on the proceeding's lowest-id live Writing's board alone, never on two, until it is moved to a Writing.
- **`path`**: the folder or file, in `documents.file_path`'s stored form, relative to the matter root with backslash separators (`document-paths.md`, whose `stored_form` helper converts it, with `matter_root` from `drafting_forms__open_session`): `0. DRAFT\CL Advice re costs`, `0. DRAFT\2026-10-08 ET Smith re hearing.md`. `UNIQUE`: a draft is on one board at a time.
- **`kind`**: `'client_letter'` or `'reply'`.
- **`attached_on`**: the date attached, `YYYY-MM-DD`.

Every value below is a literal composed into the script, each `'` doubled (§7's no-bind rule). The table is revision-exempt (§8): attaching moves no mockup. The Job Board pages show a change at their next write, so after each write here render the board under `draft_dir`: `drafting_forms__render` with the board's `filing_id` or, for a pre-filing board, `proceeding_id`, naming `Work_board` in `documents`.

**The matter's boards.** Before attaching or moving, read every live Writing and every proceeding with no Writing:

```sql
SELECT id AS filing_id, proceeding_id, title FROM filings WHERE retired_on IS NULL ORDER BY proceeding_id, id;
SELECT id AS proceeding_id, forum, file_number FROM proceedings p
  WHERE NOT EXISTS (SELECT 1 FROM filings f WHERE f.proceeding_id = p.id) ORDER BY id;
```

Ask the practitioner which board, naming a Writing's board by its title and a pre-filing proceeding's by its forum and file number. The default offered is the board of the Writing the session holds, the Writing of the job it holds. A matter with no proceeding at all gets a forum-less proceeding first, an ordinary `proceedings` insert with `forum` NULL (ADR 0024's superseding note on D9), and the draft goes on that proceeding's board. A proceeding whose Writings are all retired has no board at all, so attach the draft to a board of another proceeding, or recover one of its Writings (§11) and attach it there. A matter is one database, so every board read here is in the same matter.

**Attach**, once, when the draft is first saved:

```sql
INSERT INTO board_attachments (proceeding_id, filing_id, path, kind, attached_on)
  VALUES (1, 7, '0. DRAFT\CL Advice re costs', 'client_letter', '2026-10-08');
```

A `UNIQUE` refusal on `path` means the draft is already attached: read its row and say which board holds it. Never attach it twice.

**Move**, only when the practitioner asks, to any other board of the matter, the row's id from the read below:

```sql
UPDATE board_attachments SET proceeding_id = 1, filing_id = 8 WHERE id = 3;
```

When the folder or file itself is renamed or moved on disk, or a reply is saved as a new ` vN` version, the same kind of update sets `path` to the new stored form, the board unchanged: `UPDATE board_attachments SET path = '0. DRAFT\2026-10-08 ET Smith re hearing v2.md' WHERE id = 4;`.

**Detach**, only when the practitioner asks. The files stay in `0. DRAFT`:

```sql
DELETE FROM board_attachments WHERE id = 3;
```

**Read a board's attachments**: a Writing's board shows the rows naming it and, only when it is the proceeding's lowest-id live Writing, the rows of its proceeding with no Writing; a pre-filing proceeding's board shows every row of the proceeding:

```sql
SELECT id, filing_id, path, kind, attached_on FROM board_attachments
  WHERE proceeding_id = 1
    AND (filing_id = 7 OR (filing_id IS NULL AND 7 = (SELECT MIN(id) FROM filings WHERE proceeding_id = 1 AND retired_on IS NULL AND kind <> 'task-board')))
  ORDER BY id;
```

`drafting_forms__board_card`'s `attached` lane prints the same rows with each one's state on disk.

**Guards** (v67). Each refusal writes nothing; quote it in one line and ask the practitioner for another board:

- `guard_board_attachments_live_ins`/`_upd`: a retired Writing has no board.
- `guard_board_attachments_proceeding_ins`/`_upd`: a row names a Writing of its own proceeding.
- `guard_board_attachments_pre_filing_ins`/`_upd`: a proceeding with any Writing, live or retired, has no board of its own, so `filing_id` NULL is refused there.
- `guard_filings_retire_attached`: the retirement precondition (§11).

## 15. Rhetorical paragraphs (schema v71)

A rhetorical paragraph is a numbered paragraph of persuasion from the record that fits no other type, for example a characterisation of the other side's pleading (root `GLOSSARY.md`, "Rhetorical paragraph"). The database refuses none for a missing link: every link is optional, and a paragraph with none is valid. It is proceeding-scoped substance, like a submission, and each new table carries §8's revision triggers.

**The paragraph.** `states_law` and `states_fact` are NOT NULL with no default. The drafting session records whether the wording states law and whether it states fact, as 1 or 0. No trigger resets either one, so a revision that changes what the wording states sets them in the same script (`paragraph-revision.md` §1):

```sql
INSERT INTO rhetorical_paragraphs (proceeding_id, wording, states_law, states_fact)
  VALUES (1, 'The Response to Civil Claim does not deny the delivery date.', 0, 1);
```

**Links**, each optional and any number, each one `INSERT` per row:

```sql
INSERT INTO rhetorical_paragraph_submissions (rhetorical_paragraph_id, submission_id) VALUES (4, 12);
INSERT INTO rhetorical_paragraph_opposing_points (rhetorical_paragraph_id, opposing_point_id) VALUES (4, 3);
INSERT INTO rhetorical_paragraph_facts (rhetorical_paragraph_id, fact_id) VALUES (4, 9);
INSERT INTO rhetorical_paragraph_law (rhetorical_paragraph_id, law_assertion_id) VALUES (4, 2);
INSERT INTO rhetorical_paragraph_record (rhetorical_paragraph_id, document_id, pinpoint, excerpt)
  VALUES (4, 15, 'para 7', 'The Defendant admits paragraph 7.');
```

A record cite needs its `document_id`; its `pinpoint` and `excerpt` may be NULL. The links are advisory, never coverage. A rhetorical paragraph linked to an opposing point does not answer it, so ↩️ stays until a submission answers it (`opposing_points.answered_by_submission_id`). A link to a submission adds nothing to that submission's argument, so 🧾 and 📚 read `submission_facts` and `submission_law` alone. No link to a rhetorical paragraph clears any marker on any other row.

**Placement.** One `filing_rhetoric` row places the paragraph on one advocacy document of one Writing: `document` is `'form'` or `'written_argument'`, as in §9, and `part` is `'facts'`, `'submissions'` or `'orders'`. Its `ordinal` is a position on the host part's own ordinal scale (the `filing_facts`, `filing_submissions` or `filing_orders` ordinals of that Writing and document). The paragraph prints immediately after the host item with that ordinal, and after that item when the two are equal. Ordinal 0 prints first in the part, and an ordinal past the last host item prints last. Several rhetorical paragraphs on one ordinal print in id order. The paragraph is numbered in the part's own sequence, on the mockup and the filed face alike. If the host item at that ordinal is removed, the paragraph prints after the next lower one: nothing is hidden. Placing it moves no host ordinal:

```sql
INSERT INTO filing_rhetoric (filing_id, rhetorical_paragraph_id, document, part, ordinal)
  VALUES (7, 4, 'form', 'facts', 3);
```

| Kind | `facts` | `submissions` | `orders` |
|---|---|---|---|
| Notice of Application (§2) | Part 2 | Part 3 | Part 1 |
| Application Response (§5) | Part 4 | Part 5 | not printed |
| VanIAC submissions package (§1) and BCSC Written Arguments | not printed | the Submissions | numbered, just before the relief paragraph |
| BCCA stay response (§10) | Part 1 | Part 3 | Part 4 |
| BCCA respondent's factum (§12) | Part 1, after the facts position | Part 3 | numbered, just before the order paragraph |
| General Writing (§13) | not printed | the legal basis | just before the orders sought |

A placement in a part its kind does not print is listed in the Counsel Brief with `(not printed: <kind> has no <part> part)`. A placement in the form's facts part counts as content in that part, so it clears a recorded pure-law decision, as a placed fact does (§2 and §5, "Pure law"). A sent or retired Writing's placements are frozen, as its other pointer rows are.

**On the mockup** the line carries ` (rhetorical)`. It carries ` (states law, no authority linked)` while `states_law = 1` with no `rhetorical_paragraph_law` row, and ` (states fact beyond its record)` while `states_fact = 1` with neither a `rhetorical_paragraph_record` row nor a `rhetorical_paragraph_facts` row. These are plain text, not markers (`work-markers.md` rule 5): they never block a render and never hold back 🧐. The line then carries 🧐 until counsel approves its current wording (`review.md`), and the trace `<!-- rhetorical_paragraph_id N -->`. The filed face prints the wording and its record citations only: every tag, marker and trace is rendered for the human and withheld from the forum.

**Reserve.** A rhetorical paragraph deployed by no document of any Writing of the proceeding is held in reserve 🂡, as a submission is. One deployed only on another Writing is listed under that Writing, marker-free. The Counsel Brief lists each one under *Rhetorical paragraphs*.

**Abandon** a paragraph only on the practitioner's word, by deleting its placements, links and row in one script. Its `paragraph_revisions` history stays:

```sql
DELETE FROM filing_rhetoric WHERE rhetorical_paragraph_id = 4;
DELETE FROM rhetorical_paragraph_submissions WHERE rhetorical_paragraph_id = 4;
DELETE FROM rhetorical_paragraph_opposing_points WHERE rhetorical_paragraph_id = 4;
DELETE FROM rhetorical_paragraph_facts WHERE rhetorical_paragraph_id = 4;
DELETE FROM rhetorical_paragraph_law WHERE rhetorical_paragraph_id = 4;
DELETE FROM rhetorical_paragraph_record WHERE rhetorical_paragraph_id = 4;
DELETE FROM rhetorical_paragraphs WHERE id = 4;
```
