Read when: calling `drafting_forms__render`, `drafting_forms__board_card`, `drafting_forms__open_session`, `drafting_forms__bootstrap`, `drafting_data__set_board_goal`, `drafting_data__record_viewed`, `drafting_data__resnapshot_writing` or `drafting_forms__pre_filing_check`, locating render output or the board files, reading or writing the rules position tables, or working on a migration or the bundle's schema ceiling.

# Drafting tool contracts

## `drafting_forms__render`

Writing → mockup + conditional archive copy, stamped with `db_meta.revision` (§5); memoised by render stamp (ADR 0017): when the Writing's stamp matches its render manifest, nothing is re-rendered and no mockup is rewritten, and a named document's markdown still returns. Under `presentation_dir` or `draft_dir` it also rewrites the matter's pages, the Milestone pages, the Litigation Strategy page and the view pages ("Board files" below), returns `view_page_paths` (every view page, `{name, filing_id, path}`), and reports any old page files it moved to `TRASH` as `moved_to_trash` (`trash_skipped` for any it could not move). A successful mockup render carries `background_job` (see `drafting_forms__bootstrap` above). Returns each document's `markdown` inline as well as its path ([#337](https://github.com/Mharbulous/CoClerk/issues/337)) — read that text to interpret work markers, and present the practitioner the file (`shared/present-files.md`), never its contents. Each mockup is written into the Writing's own folder in the matter's `0. DRAFT` ("Render output" below), the only copy, and its `path` is there. With `draft_dir` ([#689](https://github.com/Mharbulous/CoClerk/issues/689)) or `presentation_dir` ([#466](https://github.com/Mharbulous/CoClerk/issues/466), ADR 0012, never both) it returns `markdown` only for documents named in `documents`; every other document carries `markdown_chars`, its length, in place of its text. To read a document's work markers, name its `document_type` in `documents`. The server finds the Writing's folder itself; two or more candidates refuse (`presentation_dir_ambiguous`) before any write, naming each, and `presentation_dir` then names the one to use. A folder an older build named with a type's code is kept when it holds a file the renderer did not write, and the response carries `writing_folder_rename` `{from, to}`: offer the practitioner the rename, which only `file-manager` makes. One returned document is always the Milestone (schema v15, ADR 0009) — this Writing's jobs and loose threads not yet outlined, never delivered to the filed face. Only when `Work_board` is named in `documents` does it return `board_summary` in place of `markdown`: the short summary of this Writing's section of the board as fixed-grammar text, its matter, client, revision, linked to-do, its `Goal: <description> (<status>)` line (the board's statement of goals, `none` when none is stored) and unmet and met completion criteria, or its `State:` line when it has no criteria to list (the lanes, the criteria with their counts and what a card holds are `drafting_forms__board_card`'s). Either way the entry carries `board_changed` and `board_moves` (compared against the last section a render reported, never against a page) and, when the pages were written, `path` (its Milestone page). Read the summary and the card to build the job widget, never the page (`shared/html-pages.md`) and never a query. With `proceeding_id` in place of a Writing it renders a pre-filing proceeding's section alone, returning `board_summary` and, with `draft_dir`, `milestone_path`, `milestone_paths` and `matter_board_path`. Optional `session_token` is this session's own identity from `drafting_forms__bootstrap` — pass it and the response echoes it back; this tool mints none (`references/jobs-common.md` §1). Optional `appeal_deadline` (`YYYY-MM-DD`, schema v17) is the caller's own `lawyer:docket-clerk` lookup, never stored — it is what lets the Milestone derive the appeal-period-expired state. A **retired** Writing refuses mockup mode outright (`filing_retired: true`, no mockup written, its `board_summary` returned; under `presentation_dir` or `draft_dir` only the matter's pages, its page moved to TRASH) — `references/filing-checklists.md` §11

## `drafting_forms__board_card`

`{db_path, filing_id or proceeding_id, client_name?, client_no?, matter_no?, jobs?, lanes?, key?, loose_threads_from_jobs?, draft_dir?}` — read-only: writes nothing, moves no revision, writes no page. At least one of `jobs` (job ids on the section), `lanes` (`goals`, `criteria`, `live`, `proposed`, `completed`, `rejected`, `loose_threads`, `attached`, `court_file`; `goal` is still accepted for `criteria`, and is never the statement of goals; `attached` needs `draft_dir`, the one session entry returned, and `court_file` needs `draft_dir` and `filing_id`), `key` and `loose_threads_from_jobs` (job ids: the `loose_threads` lane holding only the loose threads those jobs surfaced, its heading `## Loose Threads (<k> of <n> from Job #<N>)`); none, an empty `loose_threads_from_jobs`, a job id not on the section, an unknown lane, `criteria` or `proposed` on a proceeding with no Writing, or a `proceeding_id` that has a Writing is refused. It builds the section as the matter pages do, from the inventory the Writing's last render saved, so it reads what the latest render read. Returns `{filing_id or proceeding_id, revision, rendered_at, card}`, `card` in a fixed grammar: each job asked for, in board order, as its `live` line without the tags, then `  kind: <kind> · priority: <N>` (with ` · locked: <locked_at> · holder: <tag> · last activity: <stamp>` on an In Progress job, the last activity being the latest of its lock, its done steps, the loose threads captured from it and the answers saved for it, which the `live` lane's idle tag also measures from), `  intent:`, `  keys:` with each key's `(now: …)`, `  scope: … · waits on: … · either-or: …`, `  steps:`, `  loose threads:` (each open loose thread captured from the job) and `  answers:` (each answer `research_filing__save_answer` recorded against it, from its `6. LAW` segment on, with when it was saved) (a superseded job its `  superseded by: … · reason: …` line in place of that detail; a Bring Forward job ends `  bring forward: <bf_on>`, a completed job ends `  completed: <completed_at>`, a shelved one `  shelved: <rejected_at>`); then each lane asked for under its `## ` heading (`goals`: `## Goal (<status>)`, the status `confirmed`, `inferred`, `declined` or `none`, then the board's statement-of-goals description on its own line, then the statement verbatim, its line breaks and indentation kept, when there is one, on every kind of board; `criteria`: the `🎯 Completion criteria:` line and each criterion in board order as `- <glyph> <id>: <text>`, with ` (after …)` on a deadline that follows others, its counts and its ` — items`, the counts being `(unmet <u>, met <m>, total <t>)` on an inventory criterion, `(<n> open)` on the gate while a step or a job is open, and none on any other. An inventory criterion is built from the markers the mockup still prints, so an item the practitioner fixed leaves it: `met` counts the items the practitioner shelved and `total` the items still flagged or shelved, never every item the criterion ever covered; `live`: Ready, In Progress, Bring Forward, Blocked and Superseded, each under `## <lane> (n)` with each job's collapsed line and tags (`eligible:` and `dispatch:` on a Ready job, `idle` on an In Progress one, measured to this call's `rendered_at`, `BF <date>` on a Bring Forward one, the day its work may start and never a deadline), then ` · general` on a General Job, which ends its line here, in every other lane and in `jobs`, and on no Writing Job (`references/jobs-integrity.md` §11), `dispatch choice:` after Ready, the counts of Completed and Shelved between Blocked and Superseded, then the counts of Loose Threads and Proposed, then `🧹 lapsed keys:` when any; `proposed` and `rejected`: each Proposal's `- <glyph> <title>` and `  key:` lines, `rejected` after the shelved jobs' lines; `completed`: each job's line; `loose_threads`: each `- loose thread` line; `attached`: `## Attached (n)` and each draft attached to the board (schema v67, `references/filing-checklists.md` §14) as `- attachment <id> · <client letter or reply> · <stored path> · attached <date>`, then ` · no Writing: shown on this proceeding's lowest-id live Writing's board` on a row of the proceeding with no Writing, which shows on that one board only, then ` · missing`, ` · not in the draft folder`, ` · unreadable (<error code>)`, or on a client letter ` · review: <status>`, the rest of its review draft's first line after `Counsel's review: `, `no review draft` when none, each file named when several; no other line of the file is read); `court_file`: `## Court File (n)` and each affidavit the Writing relies on, matched by number and deponent code against the file names in the matter's `COURT FILE` folder (with several, the one naming the proceeding's file number), as `- <label> · court file: <file name>` or `· court file: none found`, then ` · mismatch: court file shows <status> <date>; drafting data shows <unsworn or made <date>>` when they disagree; only file names are read, and the Milestone page draws each mismatch as one card in a Court File lane; then `key`: the live job holding it, else the Proposal under its lane's heading, else `(no job or Proposal carries <key>)`

## `drafting_forms__open_session`

`{matter_root, client_name?, client_no?, matter_no?, filing_id?}` ([#591](https://github.com/Mharbulous/CoClerk/issues/591)) — SKILL.md's Configuration path rule as one call: proves `matter_root` host-side, reads `probanda.json` → `case_data_dir` → `submission.sqlite` **read-only** (a missing, unreadable or legacy pointer refuses, `pointer_unusable`, naming `/matter-data`; it never heals or rewrites), looks the matter up by the folder's leading token (never fatal: `matter_lookup.found: false` + one-line `note`; a caller's own client fields win), reports `blocking` [{`code`: `practice_config_unreachable`, `message`, `remedy`}] when the case data root resolves neither from the per-user `probanda.json` nor from the firm's `0. CASE DATA` folder beside the matter folder (found from the matter-data folder, in either layout), which is exactly when `create_writing` would fail, its `remedy` naming `/practice-data`'s `config_status` and `config_set_root` repair (`/draft` section 6 takes no job then; nothing is written), migrates a database that is behind (same copy-aside backup as `migrate`; reports `migrated: {from, to, backup}`), finds the matter root's one `0. DRAFT*` folder ([#651](https://github.com/Mharbulous/CoClerk/issues/651); two or more refuse, `draft_dir_ambiguous`; none leaves `milestone_paths` and `matter_board_path` null and sets a one-line `matter_board_note` saying no page was written), then runs `bootstrap` and, with that folder, opens `filing_id`, or the first live Writing, or the first pre-filing proceeding, as `drafting_forms__render` with `draft_dir` would (presentation copies and the matter's pages written once), returning that board as `opened` (`board_summary`, the short summary `render` describes, `board_changed`, `board_moves`, `filing_retired`), with `milestone_path` (the opened Writing's or proceeding's Milestone page), `milestone_paths` (every Milestone page), `view_page_paths` (every view page, `{name, filing_id, path}`, none presented at the fast open) and `matter_board_path`, so no separate render is needed to open a session; with nothing to open, or when that render refused (`open_refused` with its code and message), the matter's pages are still written, and `milestone_path` is the page the refused render tried to open, or null with nothing to open (`milestone_paths` then empty). Returns everything `bootstrap` returns plus `db_path`, `matter_root`, `matter_lookup` (whose `client_name`/`client_no`/`matter_no` every later `render` passes) and, when the folder exists, `draft_dir` ([#689](https://github.com/Mharbulous/CoClerk/issues/689)), which every later `render` passes too. No database at the derived path refuses — creating one stays `migrate`'s job. When it opened a Writing it also returns `court_file_affidavits`, read-only: each affidavit the Writing relies on with its `court_file` match (file name, date, status marker) or null for none found, `court_file_made_on` (the newest `SIGNED`, `AFFIRMED` or `SWORN` name's date) and `mismatch`, the board item's text, or null. It also returns `parties_drift` and, when there is one, `counsel_offers` (`references/filing-checklists.md` §0); when its migrate is refused `counsel_not_reconciled` it goes on at v42 without migrating, lists and renders it as current, and returns `migration_refused` with the refusal

## `drafting_forms__bootstrap`

schema check, Writing list with lifecycle and each live Writing's `render_state` (`fresh`/`stale`/`never`, from the render manifest alone), whatever mockup paths are already on disk — **renders nothing, returns no content** (ADR 0017; a retired Writing is listed with empty `paths` and no `render_state` — schema v17). `filings` comes back in the order to present them; present that order as given. A Milestone with no Writing is listed there with `milestone_only: true`, no paths and no `render_state`, and `open_session` opens it only when its `filing_id` is passed. Start every drafting session here (usually through `open_session`), not with a query battery (ADR 0005), then call `drafting_forms__render` on the one Writing being worked to read its markers ([#337](https://github.com/Mharbulous/CoClerk/issues/337)). Optional `draft_dir`, the matter's `0. DRAFT*` folder itself: bootstrap also writes the matter's pages there and returns `milestone_paths` (every Milestone page, `{filing_id, proceeding_id, path}` in page order), `view_page_paths` (every view page, `{name, filing_id, path}`) and `matter_board_path` (all three null without it), with `moved_to_trash`/`trash_skipped` as `render` reports them; it returns no board content. Bootstrap starts the background render job for every live Writing not `fresh`, when all three client identity fields were given, and returns `background_job`; nothing waits on it. Also carries on success `session_token` — a fresh identity minted for this session, used as `tickets.locked_by` and passed to every later `render` — `bootstrapped_at`, this session's start stamp (a lock older than it belongs to another session, `references/jobs-common.md` §1), and `legacy_workboard_artifact_url`: a hosted Work Board URL the matter still records from the retired artifact design, or null (`references/jobs-closeout.md` §13)

## `drafting_data__set_board_goal`

`{db_path, filing_id or proceeding_id, status, statement?, description?, session_token}` — one write, on any kind of board: `filing_id` for a Writing's board or a Milestone with no Writing, `proceeding_id` for a pre-filing proceeding's board (one with a Writing refuses `proceeding_has_writing`). `status` is `confirmed` (the practitioner approved the statement), `inferred` (the session's own wording after the practitioner declined: shown in italics as "Inferred, not confirmed", never relied on as confirmed) or `declined` (the practitioner declined and nothing is inferred yet: no `statement`). `statement` is the whole text, stored verbatim with its line breaks and indentation, required for `confirmed` and `inferred`. `description` is the line the closed card shows; omitted, the stored one stays, else the board's default (`<Writing title> Drafting`, a Milestone with no Writing's own title, or `Proceeding <id>`). A confirmed write passes the practitioner-words gate: the statement is an unbroken run of one practitioner turn, or the one fenced code block in the session's reply before the practitioner's last turn, character for character, and that turn is a bare yes. An inferred or declined write passes without approval. It replaces the board's row (see "Statement of goals" below), removes the rows of boards that no longer exist (`stale_keys_removed`) and moves no revision; re-render to show it. Read it back as `board_summary`'s `Goal:` line or `drafting_forms__board_card`'s `goals` lane, never by query. Refusals write nothing: `invalid_board`, `invalid_session_token`, `invalid_status`, `invalid_statement`, `invalid_description`, `not_found`, `proceeding_has_writing`

- **Statement of goals** (no schema change, 2026-10-14): one `db_meta` row per Milestone, never a table. Key `board_goal:filing:<id>` for a Writing's board or a Milestone with no Writing, `board_goal:proceeding:<id>` for a pre-filing proceeding's board. Value: JSON `{description, statement, status, approved_at, session_token, updated_at}`: `status` one of `confirmed`, `inferred`, `declined`; `approved_at` set only for `confirmed`; `statement` null only, and always, when `declined`; `description` null means the board's default. Timestamps are local `YYYY-MM-DDTHH:MM`. Job process state: `db_meta` has no revision trigger, so it moves no revision and archives no mockup. Written only by `drafting_data__set_board_goal`, never by `drafting_data__execute`. A row whose board no longer exists (its `filings` row gone, or its proceeding now has a Writing) is never read, since no section is built for it, and the next write removes it. Every Milestone page draws it as the card labelled Goal, above the Completion Criteria card, which keeps its own name.

## `drafting_data__record_viewed`

`{db_path, paths}` — right after a view page or a Writing's mockup copy is presented as a file card, the PC paths presented, in the order presented; never a Milestone or the Litigation Strategy page. Each path is matched by its file name, and by its folder where several Writings' documents share the name, and moved to the front of its board's order, so the last path ends up first. It writes the board's viewed order (see "Viewed thumbnails" below) and nothing else, moves no revision and does not rewrite the page: the order shows the next time the page is written. Refusals write nothing: `invalid_paths`, `not_a_strip_item`, `ambiguous_path`

- **Viewed thumbnails** (no schema change, 2026-10-22): one `db_meta` row per Milestone, never a table. Key `board_viewed:filing:<id>` or `board_viewed:proceeding:<id>`, by the board's survivor (docs/ADRs/0010). Value: a JSON array of item keys, most recently viewed first: `view:<page name>` for a view page, `doc:<filing id>:<file name>` for a Writing's document by its render manifest's file name. It holds an order and no time. Written only by `drafting_data__record_viewed`, never by `drafting_data__execute`, and it moves no revision. Every Milestone page draws its viewed thumbnails first, in this order, then the never-viewed ones, and dashes a view page's tile only while it has never been viewed. A retitle that renames a document's file drops its key, so its tile reads never viewed again. A merge does not carry the absorbed board's row over.

## `drafting_data__migrate`

**Refused** on the v43 hop, which drops the drafting database's copy of counsel of record, while any counsel offer or `parties_drift` row stands: code `counsel_not_reconciled`, naming each row, nothing written (a database older than v42 is first taken to v42 so its parties can be linked); decide each by `references/filing-checklists.md` §0, then migrate again

## `drafting_data__resnapshot_writing`

`{db_path, filing_id, jurisdiction?}` — the dedicated re-snapshot write, run only on the practitioner's explicit instruction and only while the Writing is drafting: a sent or retired Writing refuses `writing_not_drafting`, and the v32 layout-freeze trigger refuses the same write at database level. It resolves the stored kind again from `/draft`'s knowledge tree with no recipient, validates the layout, records each cited passage hash, and rewrites `layout_snapshot` and `needs_forum_parts` in one write, which moves the revision and re-runs the needs-forum guard. The tree key is the proceeding's `forum`; on a proceeding with no forum, pass `jurisdiction: {country, jurisdiction}`, the writer's, which the caller passes and never infers (`jurisdiction_required`). Refusals write nothing: `invalid_filing_id`, `not_found`, `writing_not_drafting`, `invalid_forum`, `jurisdiction_required`, `kind_unresolved`, `invalid_layout`, `projection_not_built`. Returns `filing_id`, `needs_forum_parts`, `type_file` and `revision`

## `drafting_forms__pre_filing_check`

`{db_path, filing_id, package_dir}` — deterministic, read-only checks of the package folder's documents against each other and this Writing's Evidence Index rows ([#615](https://github.com/Mharbulous/CoClerk/issues/615), ADR 0016): C1 exhibit numbering, C2 unresolved placeholders (signed documents flagged high), C6 exhibit file sanity; C3–C5 report `n/a` until built. Every finding quotes the offending line with its document and page. Writes nothing — the gate reports, a job fixes. The check list is `references/pre-filing-checks.md`; the gate job and waiver idiom are `references/jobs-gate.md` §14; `/draft` step 9 runs it. `package_dir` must lie beneath the matter's `0. DRAFT*` folder; PDF text needs `pypdf` on the host Python (its absence is a hard error, never a pass)

## Render output

**Render output** ([#297](https://github.com/Mharbulous/CoClerk/issues/297); location decided by `docs/Specs/2026-10-22_writing-file-names-hide-internal-codes-spec.md` §9): `drafting_forms__render` and the background render job write each Writing's mockups into its own folder in the matter's `0. DRAFT*` folder, the one beside the matter's own `0. CASE DATA` that holds `submission.sqlite` (`docs/ADRs/0013-per-matter-case-data-inside-the-matter-folder.md`). One folder per Writing, named after the document: `0. DRAFT\<Writing title>\`, e.g. `0. DRAFT\Notice of Hearing of Application\`. Each mockup is named after its document (a Writing on a stock type by its own title), and that one file is the only copy: nothing is kept beside the database, which holds only the databases. Revision-triggered archive copies go in an `archive\` folder inside it, named `<document name> @rev<N> <time>`. The Writing's folder is recorded when first rendered and kept on a retitle; a folder name another Writing holds gets ` (2)` after it, never an id; no folder or file name carries a type's code, a stock type's name or a Writing id. A matter with no `0. DRAFT*` folder beside its case data has no mockup until one exists, and a matter whose case data is still under the firm root is relocated first (`/matter-data` relocate). The tools write and reach the files host-side; the practitioner opens the returned paths directly. A *session* never reads these files itself, so `drafting_forms__render` returns each document's `markdown` in its response ([#337](https://github.com/Mharbulous/CoClerk/issues/337)) — the tool response is host-side, so no session file read is needed. `bootstrap` returns no markdown: it renders nothing. `/draft` step 6 renders with `draft_dir`, which also rewrites the matter's pages and returns markdown only for the documents named. The renderer never overwrites a file it did not write (no render revision stamp), and never touches a Word document or PDF in the folder. An older build kept the mockups in `<case data>\mockups\Filing <id>\` and a copy in `0. DRAFT\<CODE> <title>\`: the next render or bootstrap moves that tree into the Writing's folder, renames the coded folder when it holds only the renderer's files (else returns `writing_folder_rename` for the practitioner), and reports `mockups_moved`. Both tools also take optional `client_name`/`client_no`/`matter_no` frontmatter values — no schema column backs client identity, so when omitted `proceedings.matter_reference` stands in for all three.

## Board files

**The board-first bootstrap's files** (ADR 0017), each named once here:

- **`render-manifest-<id>.json`**, one per Writing in `0. DRAFT\Drafting records\`, the matter's one folder of drafting bookkeeping: the render stamp, the Writing's folder and each mockup's hash. `render` and bootstrap's `render_state` compare against it. The `filing-checklists.md` §8 revision bump is what moves the stamp.
- **`Litigation Strategy.html` and the Milestone pages**, in the matter's `0. DRAFT*` folder: one self-contained `Litigation Strategy.html` per matter at its top (ADR 0021), one `Milestone.html` in each live Writing's own folder, and at the top one `Milestone <id>.html` per open Milestone with no Writing and one `Milestone - proceeding <id>.html` per pre-filing proceeding (ADR 0033 and its 2026-10-05 amendments; spec 2026-10-22). The Litigation Strategy page: the matter's open to-dos lead it, read server-side through `/practice-data`'s `open-tasks` by `matter_no`, each with its BF date as a plain date and never its deadline, and with its Writing's line beneath it when its Writing reference resolves. Below them, one line per Writing and pre-filing proceeding: name, lifecycle state, mockup status, jobs in progress. A letter recorded as sent and not retired is not among those lines or their count: it sits in the "Sent, awaiting response" lane, collapsed by default, as one row of addressee, subject and sent date, and its Milestone page and its retirement are unchanged. A Milestone page holds one board's section, its Writing's or its proceeding's, and a merged board's page every board merged into it, drawn as one board, in its survivor's folder (or named by its id) even when the survivor is retired, while any of its sections is live (`docs/ADRs/0010-milestones-organized-by-goals.md`); a retired Writing has none; a General Job (a job with no Writing) is on every Writing's page in its proceeding, its card tagged General, and never on the page of a Milestone with no Writing, which holds only the jobs and loose threads that name it and has no view page. Its strip ends with a card per draft attached to the board (schema v67): its date, registry code and pending-job count, opening to its name and stored path in plain text, never a link, with a client letter's review status read from its first line at the write, a path with nothing at it shown as missing, and one that cannot be read shown as unreadable with its error code. Beside each board's page, its view pages when it holds a live Writing, `<page name>.html` in a Writing's folder, reading every Writing on the board (`shared/html-pages.md`; ADR 0033, 2026-10-07 amendment), under its own marker. All are written by `bootstrap` given `draft_dir`, by `open_session` (through its opening render, or its own page write when nothing opens), by every `render` given `draft_dir` or `presentation_dir`, a Writing's or a proceeding's, and by the background render job after each Writing. Each write is atomic (a temp file, then a rename over the page). A page is overwritten only when it carries that page's marker; a file at any page's path without it fails the render, naming it, before any page is written. Never archived and never copied beside the database. A write moves every old page file the generator wrote in the `0. DRAFT*` folder and its immediate subfolders (a retired Writing's page, a proceeding's once it has a Writing, a page under an older name, the old single `Job Board.html`, a numbered copy, a per-Writing or `Pre-filing proceeding <id>` board copy, a `Matter Board.html` or `Work Board.html`) into the matter's `TRASH`, reported as `moved_to_trash`, any it could not move as `trash_skipped`.
- **`matter-pages-state.json`**, in `0. DRAFT\Drafting records\`: what `board_changed` and `board_moves` compare against (the last section a foreground render reported for each Writing or proceeding), and the last to-dos read, which the background job reuses for the Litigation Strategy page.
- **`workboard-status.js`**, beside the Litigation Strategy page: the background render job's progress, which only that page reads. Written temp-then-rename.
- **The job's lock and status mirror**, host-local under `%LOCALAPPDATA%\Coclerk\submission-locks` beside the data lock (`render-job.lock`, `render-job.status.json`), outside the synced matter tree. The mirror is what `background_job` reports.

## Schema notes

`references/schema.sql` is the canonical current schema — generated by dumping `sqlite_master.sql` from a database freshly migrated via `references/scripts/migrate_engine.py`, with `references/scripts/regen_schema.py`, never hand-edited. It must match a live migrated database byte-for-byte; if it doesn't, `migrations.sql` changed without regenerating it, and it must be regenerated before this skill is trusted.

**Shape** (design doc §1–§2): `Matter → Proceeding → Filing → sections/join rows`, with substance (parties, facts, documents, witnesses, authorities, relief, submissions, opposing points) **proceeding-scoped and shared** — stored once per proceeding, selected and ordered into a Writing through a join row (`filing_relief`, `filing_facts`, `filing_submissions`, `filing_documents`). All ordering is by explicit `ordinal` columns, never rowid or timestamp.

**Not stored, deliberately**: deadlines (`lawyer:docket-clerk`), matter/client identity beyond `matter_reference` (`practice_data__matter_lookup`), review state other than job process state (`references/jobs-common.md`), solicitor-client communications and legal advice (§3 / ADR 0004). The Writing lifecycle (schema v19) does not breach the deadline clause: the four lifecycle dates it stores (`filings.filed_on`/`decided_on`/`entered_on`/`retired_on`) record acts that have happened, not dates by which something must, and so does `facts.procedural_on` (schema v77), the date a procedural step happened, from which nothing is computed, and `ticket_steps.wait_until` (schema v78) is the minute to check an external process, never a deadline or time remaining; the one genuine deadline the derivation consults — the appeal deadline — is supplied per render call as `drafting_forms__render`'s `appeal_deadline` parameter and is **never written to this database**.

- **`paragraph_statements_of_fact` is a pure link table** — composite primary key (`statement_paragraph_id`, `statement_of_fact_id`), no `id` column of its own, unlike every other table's integer primary key.
- **CHECK-constrained enum columns are closed sets** — see `references/schema.sql` for the exact values (`interviewed`, `kind`/`tier`/`treatment`/`disposition` on `authorities`, etc.). `proceedings.forum` and `filings.kind` are open text since v28 and v29, validated against `/draft`'s knowledge tree rather than by the schema. `parties.role` is deliberately **not** constrained — it is the forum's own vocabulary (Plaintiff/Defendant/Petitioner/Respondent/Applicant/Claimant/Respondent), not a neutral enum (design doc §2.1).
- **Migrations are additive and self-contained.** A future hop in `references/migrations.sql` must end by stamping `db_meta.schema_version` to its own target version — the runner applies the hop's SQL verbatim and does no stamping of its own (see the header comment in that file). The 27 → 28, 28 → 29 and 29 → 30 hops are engine-assisted: 27 → 28 reads `temp.forum_tree_keys`, which the engine builds from `/draft`'s venues index, 28 → 29 is preceded by an engine refusal check, and 29 → 30 reads `temp.filing_layouts`, which the engine builds from `/draft`'s type files and `venue.md` files (see the module docstring of `references/scripts/migrate_engine.py`).

## The rules position and serve log

- **The rules position and serve log** (schema v73, rules-DAG spec §4.5–§4.8): four process-state tables with no revision triggers, written only by `rules__move`, `rules__branch` and `rules__provisional` and read by them and `rules__lifecycle`; never write them with `drafting_data__execute`. Paths are node ids, root first, joined by spaces, and every timestamp is local `YYYY-MM-DDTHH:MM:SS`.
  - `session_position` (`session_token`, `branch`, `path`, `session_facts`, `in_force`, `updated_at`), keyed (`session_token`, `branch`): `branch` is `'main'` or the label of the one open side branch, `session_facts` the kept `unattended` and `host` as JSON, and `in_force` the rules the branch's last block left in force, as JSON `[[rule_id, [conditional facts]], ...]`. No row exists before a session's first move.
  - `job_position` (`job_id` → `tickets.id`, cascading on delete, `last_in_bounds_path`, `went_out_of_bounds_to` → `out_of_bounds_visit.id`, `updated_at`): the held job's latest in-bounds path, served to a session that takes the job over, and the visit that took its holder out of bounds since, if any.
  - `rule_served` (`id`, `rule_id`, `node`, `path`, `session_token`, `served_at`, indexed on `rule_id`): one row per rule whose text a move or branch sent. A rule is verified once two distinct session tokens were served it from its current node.
  - `out_of_bounds_visit` (`id`, `session_token`, `from_path`, `turn_summary`, `provisional_rules`, `visited_at`): one row per move onto the map's out-of-bounds node, with the path left. `turn_summary` and `provisional_rules` stay NULL until `rules__provisional` writes them, once per visit: the summary as given, and the rules-improviser's rules as JSON `[{id, door, act, text}, ...]`.

## The bundle's schema ceiling

**The bundle states what schema it can read** ([#812](https://github.com/Mharbulous/CoClerk/issues/812)). `source/lawyer/mcp/scripts/bundle.mjs` reads `TARGET_SCHEMA_VERSION` out of `references/scripts/migrate_engine.py` at build time and bakes it into the bundle, the same way it bakes the build stamp. A migration is applied only when its target is at or below that baked number, so a hop that has landed in this tree but has not been packaged cannot reach a client matter database.

Two environment variables sit behind it, both read from the server's environment and therefore settable only by restarting the server — never by a tool argument, which the very session being guarded could set:

- `COCLERK_SUBMISSION_ALLOW_UNBUILT_SCHEMA=1` — the deliberate escape hatch for in-progress schema work. Migrations past the bundle's ceiling are applied anyway, and every response says so. **Every database migrated this way stays unrenderable until a matching bundle is built and installed.**
- `COCLERK_SUBMISSION_BUNDLE_SCHEMA_VERSION` — a test seam that states the ceiling when there is no baked one. It loses to the baked value, so on a real bundled server it does nothing.

Every `bootstrap` and `open_session` response carries `schema_target_version`, `bundle_schema_version` and `schema_source_ahead`, with a `schema_note` when they diverge, whether or not a migration was attempted. When a migration is due but would exceed the ceiling, `migration_withheld` is true, `migration_required` is false, and nothing is migrated.

`scripts/check_plugin.py` (bundle-schema-ceiling) fails while the migration source's target differs from the bundle's baked version, so a split cannot ship unnoticed.
