# HTML pages

Shared doctrine for every litigation skill. It is not a skill: it has no `SKILL.md` and is never wrapped. It ships inside the `skills/shared/` tree of the installed litigation `.plugin`. Decision record: `docs/adr/0033-plugin-html-pages-are-human-interfaces-never-read-by-agents.md`.

> Every HTML file the Probanda plugin produces is a human interface for viewing data held in the plugin's databases, generated deterministically from that data. An agent never views, reads, greps, parses, scripts over, authors or requests a screenshot; however, an agent may present the html to a human user for them to view, staging it first where presenting needs that, and an agent may view screenshots provided by a human user on the user's own initiative. The only exception is developing/debugging the generator, in Claude Code. Agents review via markdown mockups and database data. One Litigation Strategy page per matter, and one Work Board page per board, a merged board's drawing every board merged into it as one board, each at a fixed path: in its Writing's own folder, or by the board's id when it has no Writing, and one Practice Board for the whole practice, so the user always sees the latest version.

- **The pages.** `<matter>\<DRAFT>\Litigation Strategy.html`, and one Work Board page per section (ADR 0033, 2026-10-05 amendments): `<matter>\<DRAFT>\<Writing folder>\Work Board.html` per live Writing, in the Writing's own folder named after the document (spec 2026-10-22), `<matter>\<DRAFT>\Work Board <id>.html` per open Work Board with no Writing, and `<matter>\<DRAFT>\Work Board - proceeding <id>.html` per pre-filing proceeding, where `<DRAFT>` is the matter's one `0. DRAFT*` folder. A merged board (`docs/ADRs/0010-milestones-organized-by-goals.md`) has one page, where its survivor's page goes, drawing every board merged into it as one board: one Completion Criteria card and one set of lanes, each job drawn once and naming its Writing. That card names no Writing: one state, its Writings' least advanced, one wording per criterion, and an item two Writings share printed once, while board_card and board_summary still name each Writing; it keeps that name while any of its sections is live, even after the survivor retires. Each is named by its database id, so a retitle never moves a page. A retired filing has none, and the next write moves its old page to `TRASH`. A General Job (a job with no Writing, `filing_id` NULL) is on every Writing's page in its proceeding, its card tagged General so a second page's copy never reads as a duplicate. A Writing Job (a job tied to one Writing) is on that Writing's page alone, untagged. The page of a Work Board with no Writing holds only its own jobs, and a closed one has none. No Work Board page lists or counts loose threads. A Work Board page carries the matter's dates in a Key dates card, closed until clicked, below the Completion Criteria card, and a filing's completion-criteria card carries the dates of the deadlines linked to it, all read from the practice database at each write (ADR 0013, 2026-10-04 amendments). The server writes every page, each as a whole new file swapped in at once, at session entry when the matter has a draft folder, on every render given `draft_dir` or `presentation_dir`, and after each filing the background render finishes. No other copy of a page exists: none beside the database, none in a presentation folder, no numbered copy. A write moves older page files the server wrote into the matter's `TRASH`.
- **View pages** (ADR 0033, 2026-10-07 amendment). Beside them, each view page below, one per board holding a live Writing, beside its Work Board page: `<matter>\<DRAFT>\<Writing folder>\<page name>.html` (on a survivor with no Writing, `<page name> - Work Board <id>.html` or `<page name> - Work Board - proceeding <id>.html` at the folder's top): a read-only view of that board's Writings' data, one Writing's unless boards were merged, a merged Material Facts or Procedural History page listing each Writing's facts in turn, the survivor's first, each fact once, written with the other pages by the same writes, in the same way, under its own marker. A Work Board with no Writing has no view page. A retitle never moves it; a retired filing has none, and the next write moves its old one to `TRASH`. Session entry and every render that writes the pages return every view page as `view_page_paths` (`[{name, filing_id, path}]`). A filing's Work Board page draws a tile for each of that filing's view pages after its Writings' tiles, naming the view page, with no link. One line per view page:
  - **Procedural History**: the procedural facts the filing uses (`facts.procedural_on` set, schema v77): the steps of the litigation process itself, such as a filing, a service and its method, or procedural correspondence, in the order they happened, each with its date. Each shows how it will be proven, in the same three classes and with the same checkboxes as Material Facts. The date is a step that happened, never a deadline. This page is not the matter's `ProceduralHistory.md` (`shared/procedural-history.md`).
  - **Material Facts**: the facts the filing uses that are not procedural (`facts.procedural_on` NULL), in the order the filing states them, each in ordinary text when provable (on the court record, admitted, or proved by evidence in hand that the practitioner has not recorded as inadmissible), faded when not yet in evidence, and struck through with the recorded decision shown when every piece of its evidence is recorded inadmissible. An admissibility concern alone shows as a flag. Two checkboxes show the faded and struck facts.
  - **Legal Research** (Raw Research before 2026-10-31 and Legal Memos before 2026-11-01, whose old pages the next write moves to `TRASH`): four folder tabs on one panel, in the order Legal Memos, Propositions, Statutes, Cases, with no All tab and the last tab remembered. A research memo Writing or case brief Writing has no board of its own, so no Work Board page and no view pages: saved under a job it is listed here on that job's board and, a memo, drawn as a thumbnail on that board's Work Board, and a job on one is drawn with the proceeding's General jobs.
    - **Propositions**: every proposition of law recorded for the board's proceeding, placed in a Writing or not, with its statements (citation, pinpoint, excerpt, verification, note-up status) and the submissions linked to it, each authority line with a noting-up badge (Not noted up, Case noted up: negative treatment only, or Statute level: in-force check done). Classes come from recorded data alone: in use on this board's Writings in ordinary text, undecided faded and shown by default, and not relevant (omitted, or its authority killed) struck through and hidden by default. Two checkboxes and a search filter them. A statement only a memo or brief cites, with no proposition, is that Writing's own item and is left out.
    - **Statutes**: each statute, regulation and rule the board's Writings rely on, then the proceeding's other live ones, with its currency, the date it was last checked, each recorded provision's own check, and whether it has been noted up for cases. Nothing records that note-up yet, so it reads Not noted up. Opening a card hides the rest of the tab until it is closed or Back to all is pressed, as on Cases.
    - **Cases**: each case the board's Writings rely on (a case authority behind a statement in use on one of them), one row per case, then each brief or live request for a case they do not rely on. A row is Briefed when a case brief file names the case's neutral citation or a brief job for the case saved it, with its date, its current version, the earlier ones and a link to the file, Requested when a live brief job names the case, and Not briefed otherwise. Each row also shows Not noted up, or Noted up: negative treatment only once a result is recorded, because the record does not say how far the check went. Opening a card hides the rest of the tab until it is closed or Back to all is pressed. Requests are made in a session, never on the page. A session reads the same list through `drafting_forms__board_card`'s `briefs` lane.
    - **Legal Memos**: every legal memo linked to the board, from the matter's `6. LAW` folder or recorded by a job, every saved version of a memo one card, in status lanes (Completed, In Progress, Shelved, Loose Threads, which holds memos with the status started or no job) with a folder filter, a source filter and a search. A memo is linked when a job drawn on the board saved any version of it, or when no live job drawn on any board with a Legal Research page saved any version, which puts it on every board under Loose Threads. The matter's Loose Threads page lists the same memos, started or with no job, under its Legal Memos tab. Each card shows the saving jobs' questions verbatim as its issue, the facts their scope names, its status from those jobs, its date, its current version and the earlier ones, its source (research memo, Westlaw Deep Research report or note-up record), its folder, and a link to the memo file itself, absent when the file is no longer there. A session reads the same list through `drafting_forms__board_card`'s `memos` lane.
    - The file links open a file by its absolute path, never a page, so "Cards only, no link" does not bar them; whether one opens from a card preview is untested.
  - **Arguments**: the submissions and counter-arguments the drafting database records for the filing's proceeding, in four kinds. Submissions are the live submissions some filing of the proceeding deploys, this filing's first. Counter-arguments are the opposing points raised and the points the practitioner anticipates. Rebuttals are the live submissions held in reserve; this is not ↩️'s "rebuttal needed". Killed are the submissions the practitioner reviewed and rejected (`killed_on` set), in kill-date order, each showing its kill date. Each submission, rebuttal and killed submission shows the law and then the facts linked to it. A counter-argument lists the live submissions and rebuttals the practitioner has linked to it (schema v65, many-to-many), so a rebuttal linked to two counter-arguments shows under both. The links are advisory, neither complete nor exhaustive, so a counter-argument with no link is never called unanswered. Folder tabs sit on one panel: All stacks Submissions, Counter-arguments and Rebuttals (the last two only with cards), and each other tab shows its section alone. Each section numbers its cards 1..N in page order, and each card's statement ends in a tag with its number ("Submission #N", "Rebuttal #N", "Killed #N", "Raised #N" or "Anticipated #N"). A heading's number button lists only that card until clicked again. A statement click opens or closes its card, one open per section. While the practitioner has it open, a session may point it at one card with `drafting_forms__focus_view_page` (section and number as the card's tag shows them): the page asks the data server's listener every 2 s and moves to that card's tab, lists every card in that section and opens that one. The page acts on a pointer only once, and on page load only if the pointer is under 30 s old.
- **The Loose Threads page.** `<matter>\<DRAFT>\Loose Threads.html`, one per matter beside the Litigation Strategy page, returned as `loose_threads_path` by session entry and every render that writes the pages, never in `view_page_paths`: the matter's snipped work, by kind. The folder tabs are All, Jobs, Ideas, Propositions, Legal Memos, Correspondence, Arguments and Work Boards. Threads come from the matter's own store (`drafting-data/references/jobs-run.md` §8): an idea under Ideas, and the other kinds under Propositions, Correspondence, Arguments and Work Boards. Work with a record or file of its own stays where it is and shows as a read-only card under "Left where they are", naming its record, linking its file or Work Board page where it has one, and holding no copy: a shelved job (Jobs), a killed proposition, or one resting only on a killed authority (Propositions; an undecided one stays on the Legal Research page alone), a memo with status started or no job (Legal Memos), a retired letter that did not go out (Correspondence; a live letter is on no tab), a killed submission (Arguments), a closed Work Board with no Writing (Work Boards). Inside a tab a status filter picks Ranked, Unranked, Deferred or Resolved. Ranking applies to ideas only, so Ranked and Unranked are offered only on All and Ideas, and a thread of another kind reads Open. The ranked come first by rank, ties by id, and the unranked follow by id, under an Unranked heading that reads them as captured since the last ranking. Ranking never drops a loose thread. Resolved lists every thread that was discarded or suggested or outlined into a job that is not deleted, newest first, each with how and when: a discarded one as a red struck line with a Restore link that copies an instruction to paste into a session and writes nothing, a suggested one as a plain line, and an outlined one naming the job by number and title with the date the job was created. On the All tab with no status picked, a "Show/Hide Resolved Threads" checkbox (☐ off, ☑ on), left of the All groups switch, or at the right of the tab row when nothing is ranked, shows them, and it is off by default. Each open thread is a collapsible card. A ranked card's visible text is the job description the ranking restated it as, ending in its rank tag and a tag with its group's short name in the group's colour (Practitioner decisions, Tooling, Housekeeping, Research, Authority mismatch, Evidence mismatch, Miscellaneous). Opened, it shows the original loose thought verbatim, then the one-line reason the ranking gave it, then its id, who surfaced it and where it came from. An unranked card, and one ranked with no job description, shows the loose thought verbatim, collapsed or opened, ending in its rank tag (a "?" while unranked). The Ranked heading carries an All groups switch that, turned off, shows one toggle chip per group present with its count of ranked threads, and a status button at the top right of each open thread reads Ranked, Unranked, Open or Deferred. A deferred thread shows under Deferred and with no status picked, and the header counts it as Deferred, not Ranked or Unranked. Each resolved line ends in an inert Resolved label. Clicking the status button defers the thread indefinitely, and clicking Deferred brings it back: the page posts it to the data server's localhost listener, which writes the deferral to the store, and on success the card moves to its new section and its label changes. The header's counts stay as rendered until the page is next written. On load the page checks the listener; when it does not answer, the buttons stay disabled and one line reads "Buttons need the Claude desktop app running." A failed click shows its error on the card. A session reads the ranks, the job descriptions and the deferrals only through `loose_threads__read`.
- **The Practice Board.** `<case_data_root>\_board\Practice Board.html`, in its own folder beside `_practice`, which holds practice.db: the open work of every matter in the practice, billable or not, except a matter whose status is exactly `test`. Its internal name is `practice_board`, never `Work_board` (the Work Board's document type). Four panels, in order: Overdue, Due today, Coming up (the next 14 days) and Other open work. Each card is a deadline, an event (an anchor) or a to-do, and names its matter, client, matter status and, when it is not billable, says so. Items are placed by their stored date against today's date, and no date is derived and no day count drawn. A to-do is placed by its `deadline_date`, and its BF date is a plain label (ADR 0021 D2). A to-do with no deadline date is in Other open work. A provisional alternative (`scenario_label`), a review-flagged deadline and a conflicted event draw flagged, as an unconfirmed date, never as a plain due date, and the header counts the conflicted dates. Met and dismissed deadlines and occurred events are not on it, and a not_applicable deadline drops off once its one-shot notice has fired. Only `practice_data__render_practice_board` writes it, on request, and returns its path and panel counts, never a date. Present it as a file card by `practice_board_path` (`shared/present-files.md`), staged alone first on a remote-device-only host. To stage it, never connect `_practice` or the case data root folder itself, because `_practice` holds practice.db and its hash key: connect only `_board`. It names each matter in plain text and links to no page.
- **One design template.** `mcp/src/templates/practice-board/board.css` is the design SSOT for every board page except the Work Board: the Litigation Strategy page, every view page, and any board page added later. A new board page is built from it. An existing page moves onto it when it is next revised, which includes replacing hardcoded colours with the template's tokens. The Work Board is exempt: it is the prototype and test bed, and keeps its own copy (`templates/milestone/workboard.css`, which `WORKBOARD_CSS` in `workboard-assets.ts` is built from, plus its own block in `templates/milestone/milestone.css`). Design changes are developed on the Work Board first. To promote one that has proved itself, copy it into `board.css` in its own commit that names the change. The two copies differ between promotions by design.
- **Rendered for the human, generated from the databases.** A page holds nothing the databases do not. A session that read one would spend its tokens twice on data it already reaches directly.
- **A page can write, a session still never reads it.** A page button that changes data (today only the Loose Threads page's Defer) writes through the data server's localhost listener on 127.0.0.1, port 47615 unless `page_api_port` in probanda.json names another, and only with the token the render embedded for that database and proceeding. The listener runs inside each session's data server, so the buttons work while a Claude session is open. A session learns what a button wrote from the store, through `loose_threads__read`, never from the page. The listener also serves the Arguments page the card a session last pointed it at (`POST /focus`, a file per filing beside probanda.json). The session learns nothing back, not even whether the page moved. The housekeeping approval page is served the same way by the file-manager server, on its own fixed port (`page_ports` in `practice-data/operations/configuration.md`), so a page already open keeps working when that server restarts or another session's server holds the port. Every page server is built on `source/lawyer/mcp/src/local-page/`; a new page uses it and adds no listener of its own.
- **What a session uses instead.** The board: session entry's `opened.board_summary` (the filing or proceeding `drafting_forms__open_session` opened), or `drafting_forms__render` naming `Work_board`, or rendering a pre-filing proceeding by its id, returns `board_summary`, fixed-grammar text for that one filing or proceeding, with `board_changed` and `board_moves`. The summary is short: the matter, the client, the revision, the linked to-do, and the unmet and met completion criteria. The lanes (each job as the page's collapsed card text with its dispatch, eligible and idle tags), the completion criteria in board order with their counts, a job's keys, plan, scope and steps, the members of Completed, Shelved and Proposed, the drafts in Attached (ADR 0042), and the criterion items come from `drafting_forms__board_card`, which is read-only and reads the same inventory as the latest render. Those two are the only board content a session reads. The page paths and the filing list: session entry (`drafting_forms__open_session`) returns `milestone_path` (the opened filing's or proceeding's page), `milestone_paths` (every Work Board page), `view_page_paths` (every view page), `matter_board_path`, `loose_threads_path` and the filings in order. Everything else, a view page's data included: `/drafting-data`'s read tools, and the markdown mockups through the render response.
- **No screenshot requests.** An agent never requests a screenshot of a page. A screenshot the practitioner sends on their own initiative may be viewed. A session never reads page content any other way.
- **Cards only, no link.** The pages reach the practitioner only as file cards. A session gives no link to any page and relays none. No page links to another page either: a page that names another page says, in plain text, to ask a session for it, because a link on a previewed card resolves against the preview's web origin and opens an external browser.
- **Present each page by its path.** The session presents one page as a file card at the fast open, the opened filing's or proceeding's Work Board page, by the path session entry returned (`milestone_path`). When a render or completion reports the board changed, it presents the page at that result's `milestone_path` again. Otherwise a Work Board page is presented only when a different filing is opened or the practitioner asks to see a Work Board, and on that request the session presents that page's path in session entry's `milestone_paths` first, every page whose `filings` title matches when several do, and only then renders that board with `draft_dir`, naming `Work_board`, to open it (session entry with its `filing_id` when no session is open, presenting the `milestone_path` it returns). The card tool is the one `shared/present-files.md` chooses from the tool list: `mcp__cowork__present_files` when it is listed, else `SendUserFile` when that is. It is given the PC path and nothing else, so the card opens the file itself, not a copy, and the call returns no page content. No tool refreshes a card already open: presenting it again is the refresh. On the `SendUserFile` route, on a remote-device-only host, where `SendUserFile` takes staged paths only, stage that page in one `device_stage_files` call in the round trip right after session entry returns, which may share that round trip with the lapse-cleanup and intake writes, and call `SendUserFile` on the returned path. Before that first staging, unless the session context already shows the matter folder connected, check that `get_device_info`'s `connectedFolders` covers it; when it does not, the one `device_request_folder_access` call for the matter folder goes first (`/draft` section 6, Matter folder), so the first staging succeeds. Staging this early puts the card up two round trips sooner when the intake writes jobs. When the intake's re-render, or any later render or `drafting_data__complete_job` result, reports `pages_written` true and `board_changed` true, stage and present the page at that result's `milestone_path` again, alone. The card is a copy frozen at staging, so restaging is the only refresh. Staging copies the page into the session, which sends its Client Information off the User's Machine (Commandment 3), so stage only the page being presented, and know that the staged copy stays with the session until the session is deleted. The staged copy is a page: never read, grep, parse or script over it, and never reach it through a wildcard or a folder-wide search. Staging a page solely so its card can be presented is presenting, not reading. On every other host staging stays forbidden. On every host the Litigation Strategy page is presented only when the practitioner asks, as a card by `matter_board_path`, staged alone first on a remote-device-only host (`/draft` section 11, View pages). A view page is never presented at the fast open: it is presented only when the practitioner asks for it by name, as a card by its path in the latest `view_page_paths`, staged alone first on a remote-device-only host (`/draft` section 11, View pages). The one exception: after the loose-thread ranking the practitioner asked for, the session presents the Loose Threads page as a file card by that render's `loose_threads_path`, staged alone first on a remote-device-only host, since the request to rank is the request for the page. Right after presenting a view page or a Writing's mockup copy, the session calls `drafting_data__record_viewed` with `db_path` and the PC paths it presented, never a staged path, so the Work Board's thumbnails put the most recently viewed first and a view page's tile stops being dashed (`/draft` section 11). It never makes that call for a Work Board page or the Litigation Strategy page. If presenting fails, say so in one line. A session never opens a page in a browser tool. `drafting-data/hooks/milestone-card-gate.py` is the backstop for this rule: after `drafting_forms__open_session`, and after a `drafting_forms__render` or `drafting_data__complete_job` that reports `pages_written` and `board_changed` true, it names the page to present, and it blocks the end of the turn once while that page has no later `mcp__cowork__present_files` or `SendUserFile` call naming its file name. It reads only the results' fields and the session's tool calls, never a page.
- **A file the server did not write.** A render refuses to overwrite a file at any page's path that does not carry that page's marker, and names it. Say so and stop. Never open, move or rename that file: what happens to it is the practitioner's call.
- **Templates are not pages.** A board's template files (`.html`, `.css`, `.js` under `mcp/src/templates/<board>/` and `mcp/src/housekeeping/templates/`) are generator source, and any session may read them. A page generated from them, previews included, stays off limits.
- **The one exception.** Developing or debugging the generator, in Claude Code, in the plugin's source repository, whose `.claude/settings.json` sets `COCLERK_HTML_DEV=1`. No Cowork task and no regular skill run is ever the exception.
- **A change the practitioner wants to a page.** Offer `/lawyer:suggestion`, which files it in the Suggestion Box. Never look for, clone or edit the generator, and never edit the installed plugin.
- **The hook is the backstop.** `drafting-data/hooks/html-pages-gate.py` refuses a tool call that names a page: a file read or write, a grep aimed at one, a shell command naming one, or a device tool given one (a folder request by its path only, never its reason), except `device_stage_files` given exactly `Litigation Strategy.html` (or the legacy `To Do List.html`), `Practice Board.html`, `Work Board.html`, `Work Board <id>.html`, `Work Board - proceeding <id>.html` or a view page's `<page name>.html` or `<page name> - Work Board <id>.html`, case aside, or a page under its name before 2026-10-09 (`Work Board - filing <id>.html`, `<page name> - filing <id>.html`), or a preview of a current page, `<page name> preview <n>.html`. It knows each view page by the name listed in its `VIEW_NAMES`, so a new view page adds its name there. It matches names only, so a page reached through a variable or a wildcard passes it. This doctrine is the rule.
