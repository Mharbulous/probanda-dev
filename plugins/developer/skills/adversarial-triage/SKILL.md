# Adversarial triage

Maintainer-only. It ships in the `developer` plugin, which is never public and installs only on Brahm's machines, and runs in a Claude Code session opened in the probanda-dev checkout, often driven from Brahm's iPhone through Remote Control. Every path below is relative to that checkout's root. Spec: `docs/Specs/2026-10-18_suggestion-triage-spec.md`.

Preconditions: the session's working directory is the probanda-dev checkout (`git remote get-url origin` names `Mharbulous/probanda-dev`; otherwise say this skill runs only there, and stop), `POOL_SECRET_KEY` is set in the environment (`node cloud/suggestions/tools/triage.mjs list` prints `set POOL_SECRET_KEY first` when it is not: tell Brahm and stop), and `env -u GH_TOKEN gh auth status` succeeds.

**The suggestion** means its title and body (the pain point), its items in order (`item_list`), its context lines and comment, and, when the row has them, its older `items` and its previews' labels, `chosen` flags and reasons. Each item of `item_list` is one part. A preview's `html` and the row's `mockup_html` go to Brahm as a file card, never to an agent.

## Rules for the orchestrator (you)

- You make every write: the notes files, the cap, the issue, the status, the commit. No agent writes anything.
- You read no source and give no opinion on the suggestion. You relay.
- **Blinding.** Never send a hat the other hat's notes, this file, or the scoring before step 5. Never send the oracle either hat's notes.
- **Notes.** A hat's notes for step N are the output of `python scripts/triage_notes.py show .claude/adversarial-triage/<hat>.md N`. Put them at the head of every message to that hat, under the heading `Your notes for this step`. Empty output means no notes.
- **Relay as it arrives.** Dispatch both hats in the background. Show each reply to Brahm, in full and labelled, as soon as its completion notification arrives, so the faster agent's text shows first. Do not wait for the second before showing the first.
- One agent per hat for the whole triage: dispatch each once at step 2, then resume it with `SendMessage` at every later step. The oracle likewise: dispatch at step 6, resume at step 7.
- Every message to an agent names the step and the word limit.
- Nothing you file or send names a person, entity, matter or account.

## Steps

1. **Pick.** When Brahm named a `suggestion_id`, run `node cloud/suggestions/tools/triage.mjs show <suggestion_id>`; otherwise run `node cloud/suggestions/tools/triage.mjs list` and take the oldest row. If none is `submitted`, say so and stop. Save the row as JSON to a file outside the checkout, for the verbatim guard (step 7). When the row has an `issue_number`, intake has filed it: that issue is the one step 7 writes to. Run `node cloud/suggestions/tools/triage.mjs set-review <suggestion_id> [<issue_number>]`. Write a face-value summary of at most 1000 characters: what it asks for, as written. Show the summary with the row's `suggestion_id`, `skill`, `plugin_version` and `source`.
2. **Arguments.** Dispatch `developer:black-hat` and `developer:white-hat` in parallel (`run_in_background: true`), each with the summary, the full title and body, and its step-2 notes. Black-hat: the best case for doing nothing, 500 words or fewer. White-hat: the best case for implementing, 500 words or fewer, free to argue for a better variation. Show each as it arrives.
3. **Critiques.** Send each hat the other's argument and its step-3 notes. Each returns a critique of 300 words or fewer. Show each as it arrives.
4. **Replies.** Send each hat the other's critique and its step-4 notes. Each replies in 300 words or fewer. Show each as it arrives.
5. **Concessions.** Send each hat the other's reply, its step-5 notes and, for the first time, the scoring: −1 per contested point lost, 0 per point conceded now, +1 per tie, +2 per point won. Each names the points it concedes. Show each as it arrives.
6. **Judgement.** Dispatch `developer:suggestion-oracle` with the summary, the title and body, both arguments, critiques, replies and concessions, and the scoring. It reads `.claude/adversarial-triage/human-guidance.md` itself. Show its decision in full and forward it to both hats.
7. **Notes and decisions, at once.**
   - In the same message that forwards the decision, ask each hat for the full new text of its notes file (3000 characters at most, `<stepN>` tags allowed), in the background. As each arrives, write it to `.claude/adversarial-triage/<hat>.md` exactly as returned, then run `python scripts/triage_notes.py cap .claude/adversarial-triage/<hat>.md`.
   - Meanwhile resume the oracle: the parts are the suggestion's items, exactly as the row's `item_list` gives them, one part per item, never merged or split (design decision 20; it may recommend part of an item). Ask for three options each (implement as proposed, implement with its modification, reject), with its recommendation and a one-line reason a practitioner could read (and, for reject, one of the decline categories in `cloud/legal-commons/supabase/functions/suggestion-set-status/shape.ts`), and add a plain explanation of the feature the suggestion concerns: what the page or tool is and what the user sees today. Present one part per message. Every part message is self-contained, because twenty debate messages bury step 1 and Brahm often answers from an iPhone, where a question card shows without the earlier context. Each one carries, in this order: the suggestion's full title and body verbatim, its `skill`, `plugin_version` and `source`, the oracle's explanation of the feature, then the part, the options side by side, the recommendation marked, and the question. Wait for Brahm's answer before the next part.
   - Each answer is a decision on that item with a reason, the oracle's or Brahm's own: one line of plain words, at most 200 characters, quoting none of the submitted text, and for a decline one of the categories. Write the reason to a file outside the checkout and run `python scripts/check_verbatim.py --suggestion <row.json> <file>`; reword on a failure. Then record it: `node cloud/suggestions/tools/triage.mjs set-item <suggestion_id> <item> approved --reason "<reason>"`, or `... declined --reason "<reason>" --category "<category>"`.
   - After the last answer, send the decisions to the oracle; it writes the implementation plan.
   - **Paraphrase, never quote** (design decision 16). Write the issue text (the plan, with one `### Item <n>` section per approved item holding its Item, Check and Plan; a `### Decisions` list giving every item, one line each, as `- Item <n>: approved. <reason>` or `- Item <n>: declined (<category>). <reason>`, the form the implementer's `scripts/select_approved_items.py` reads; and the line `Suggestion <suggestion_id>`) to a file outside the checkout, in words that paraphrase the suggestion, and run `python scripts/check_verbatim.py --suggestion <row.json> <file>` over it; on a failure, reword the located line and run it again. Never write what the guard fails.
   - If Brahm approved any item: when the row has an issue, post the text as a comment headed `## Agent Brief` (`env -u GH_TOKEN gh issue comment <n> -R Mharbulous/probanda-dev --body-file <file>`), then `env -u GH_TOKEN gh issue edit <n> -R Mharbulous/probanda-dev --remove-label needs-triage --remove-label ready-for-human --add-label ready-for-agent --add-label cloud`. When it has none, `env -u GH_TOKEN gh issue create -R Mharbulous/probanda-dev --title "Suggestion: <a short paraphrase>" --body-file <file> --label suggestion,ready-for-agent,cloud`, and immediately after it returns the number, run `node cloud/suggestions/tools/triage.mjs set-issue <suggestion_id> <n>`.
   - If Brahm declined every item: when the row has an issue, comment with each item's reason (guarded) and close it, `env -u GH_TOKEN gh issue close <n> -R Mharbulous/probanda-dev --reason "not planned"`. File nothing otherwise.
8. **Commit.** Once both notes files are written and capped: `git -C <repo root> commit -m "Adversarial triage notes after <suggestion_id>" -- .claude/adversarial-triage/black-hat.md .claude/adversarial-triage/white-hat.md`, then `git pull --ff-only` and `env -u GH_TOKEN git push`. Then say the triage is done, with the issue link if one was filed.

Executing the plan issue is outside this skill.
