# Suggestion triage

Maintainer-only. It ships in the `developer` plugin, which is never public and installs only on Brahm's machines, and runs in a Claude Code session opened in the probanda-dev checkout, often driven from Brahm's iPhone through Remote Control. Every path below is relative to that checkout's root.

Preconditions: the session's working directory is the probanda-dev checkout (`git remote get-url origin` names `Mharbulous/probanda-dev`; otherwise say this skill runs only there, and stop), `POOL_SECRET_KEY` is set in the environment (`node cloud/suggestions/tools/triage.mjs list` prints `set POOL_SECRET_KEY first` when it is not: tell Brahm and stop), and `env -u GH_TOKEN gh auth status` succeeds. Run every `gh` call as `env -u GH_TOKEN gh`.

You relay. You read no source and give no opinion on the suggestion. Only Brahm approves or declines an item (design decisions 17 and 20). Nothing you file or send names a person, entity, matter or account.

**Paraphrase, never quote** (design decision 16). Brahm sees the submitted text in this session, but nothing written to GitHub or recorded as a reason quotes it. Before any comment, issue edit or reason is written, put it in a file outside the checkout and run the verbatim guard, `python scripts/check_verbatim.py --suggestion <record.json> [--suggestion <record.json> ...] <file>`, with the record of every suggestion it concerns. On a failure, reword the located line and run it again; never write what the guard fails.

## Steps

1. **Pick.** Take the issue or `suggestion_id` Brahm names. Otherwise run `gh issue list -R Mharbulous/probanda-dev --label suggestion --label ready-for-human --state open --json number,title,createdAt,labels` and take the oldest that does not carry `withdrawn`. An issue labelled `withdrawn`, or whose cloud record's status is `withdrawn`, is never triaged: its sender withdrew the suggestion, and `/intake-suggestions` closes it. When Brahm names one, say so and stop. When Brahm names a suggestion whose issue still carries `needs-triage`, run `/triage-issue <n>` in this session first, then carry on. When it has no issue yet, say intake has not filed it, and stop. If none is waiting, say so and stop.
2. **Read.** Read the issue and its latest `## Agent Brief` comment (`gh issue view <n> -R Mharbulous/probanda-dev --json body,labels,comments`). The suggestions it covers are its `Suggestion <id>` line and each `Suggestion <id>` line of an `### Also covers` comment, each with its item mapping. For each, run `node cloud/suggestions/tools/triage.mjs show <suggestion_id>` and save its output to a file outside the checkout: this cloud record, not the issue, holds the submitted text. Any item already decided in the record is shown with its decision and is not asked again. A brief that says `Merged by fingerprint into #m`: say the suggestion is decided with `#m`, and pick `#m` instead.
3. **Decide, one item per message.** Each message is self-contained, because Brahm often answers from an iPhone, where a question card shows without the earlier context. In this order: the suggestion's pain point and this item's text from the record, verbatim, its `skill`, `plugin_version` and `source`; the brief's sections for this item (Item, Recommendation, Reason, Check and its result, Plan); for a merged issue, the matching item of each other suggestion. Send the mockup, when the record has one, to Brahm as a file card with the first item, never to an agent. Then ask one question with these choices, the brief's recommendation marked `(Recommended)`:
   1. Approve, with the brief's reason or Brahm's own.
   2. Decline, with the brief's category and reason or Brahm's own. The category is one of `not enough detail`, `already works as asked`, `already suggested`, `outside what Probanda does`, `cost outweighs benefit` or `conflicts with how Probanda must work`.
   3. Something else, or leave it undecided.

   A reason is one line of plain words, at most 200 characters, that any practitioner who sent this problem can read, quoting none of the submitted text. Run the guard over it before step 4.
4. **Record each decision** as Brahm gives it: `node cloud/suggestions/tools/triage.mjs set-item <suggestion_id> <item> approved --reason "<reason>"`, or `... set-item <suggestion_id> <item> declined --reason "<reason>" --category "<category>"`. For an issue that covers several suggestions merged by fingerprint, record the same decision and reason on the matching item of each. A refusal is a question: relay it, and record nothing else for that item until Brahm answers. An item left undecided keeps the issue at `ready-for-human`: finish the other items, then stop at step 5 without relabelling.
5. **The issue.** Once every item is decided:
   - **Every item declined:** comment with each item's number and reason (guarded), then `gh issue close <n> -R Mharbulous/probanda-dev --reason "not planned"`, and close each issue merged into it the same way.
   - **Any item approved:** post one comment, guarded, that opens with `> *Decisions recorded by /suggestion-triage.*` and holds a new `## Agent Brief`: the triage brief with only the approved items' Item, Plan, Check and Red test sections, its Verification, a Scope and Done when cut to those items, and a `### Decisions` list giving every item, one line each, as `- Item <n>: approved. <reason>`, `- Item <n>: declined (<category>). <reason>` or `- Item <n>: undecided.`, the form `scripts/select_approved_items.py` reads. The latest brief governs the build (`.claude/commands/implement-suggestions.md`), so declined items are not built. Then ask one question: relabel now, `gh issue edit <n> -R Mharbulous/probanda-dev --remove-label ready-for-human --add-label ready-for-agent` (Recommended: the label trigger starts the cloud build at once when the issue carries `cloud`), or leave it. Close each issue merged into it, with a comment `Decided with #<n>`.
6. **Implement now?** Only when step 5 relabelled the issue, ask in the same message as the triage summary one question with these choices:
   1. Implement it now (Recommended: it lands today instead of waiting for the cloud run, whose gate may also relabel it `local`).
   2. Do nothing. The cloud run (`.claude/commands/implement-suggestions.md`) takes it.

   On 1, you run the build in this session as below, and fix-maker builds each approved item (design decision 21). Subagents cannot dispatch subagents, so you dispatch each one yourself.

   1. **Claim** the issue by `docs/agents/issue-tracker.md` **Claim** steps 1 to 4 before any edit, and record the claim id. If it is claimed or blocked, say so and stop.
   2. **Select.** Save `gh issue view <n> -R Mharbulous/probanda-dev --json body,comments` to a file outside the checkout, and run `python scripts/select_approved_items.py --issue <that file> --record <each record file from step 2>` to a selection file outside the checkout. It builds an item only when the cloud record and the Decisions list just posted both approve it, and lists every other item under `not_built` with why. Exit 2, or an empty `build` list: show Brahm its output, release the claim by **Release**, and stop. Show Brahm each `not_built` line.
   3. **Build.** For each entry of `build` (a **unit**), in item order, dispatch Agent with `subagent_type: developer:fix-maker` (it carries its own model, effort and tools) in the background, with the issue number, the suggestion id, the unit as JSON, its `### Item <n>` section verbatim from the brief just posted, that brief's Scope and the Done-when lines for that item, the paths of the selection file and of each record, and the line: "Other sessions work in this checkout and leave uncommitted files. Commit on `main` by pathspec. Never push, and never run git checkout, reset, stash, clean or rebase, or edit, commit or revert a file outside the Scope." Wait for it before dispatching the next. Relay each return in full. A return of `already green` drops that unit: note `<id>:<n>` for the next step. A return of `stopped`: dispatch nothing more, release the claim by **Release** with its reason, and say which of fix-maker's commits are on `main` unpushed, for Brahm to keep or drop; stop.
   4. **Land.** Dispatch Agent with `subagent_type: general-purpose`, `model: opus` and `effort: medium`, in the background, with the brief below, filling in `<n>`, the claim id, the selection and record paths and each dropped unit. When it returns, relay its report in full, including any check it left for Brahm.

   ```text
   Land probanda-dev issue #<n> from this checkout onto main. fix-maker has already committed each approved item on main, one commit each, named `Suggestion <id> item <n>`; build nothing yourself. Your claim id is <claim id>. The selection file is <selection path>; the records are <record paths>; dropped units: <id>:<n> ..., or none. Run every gh call as `env -u GH_TOKEN gh`.

   Rules for the whole run:
   - Other sessions work in this checkout and leave uncommitted files. Never run git checkout, reset, stash, clean or rebase. Never edit, commit or revert a file outside the issue's Scope.
   - Commit by explicit pathspec (`git commit -F <msg file> -- <paths>`), never `git add -A`. The message says what changed and why, never quotes the suggestion, and never mentions Claude or Anthropic.
   - Push only to main. If `git pull --ff-only` is refused, merge origin/main by the git rules in Brahm's global CLAUDE.md, never by rebase.

   1. Run every Done-when check of the latest `## Agent Brief`, then `python scripts/check_layering.py`, `python scripts/check_file_ops.py` and `python scripts/check_publishable.py --new-since origin/main`.
   2. Classify the change by .claude/commands/release.md step 4. Minor or 1.0: take the stop route (step 5).
   3. Release by .claude/commands/release.md steps 2, 3, 5 and 6, patch only, then commit as its step 7 says, without pushing. Release's clean-tree check, its list of plugins and its commit cover only this issue's files, the plugins they feed, the bumped plugin.json files and the plugins/ files built from them, each named by path. `python scripts/build_plugin.py --check` and `python scripts/check_plugin.py` must pass.
   4. Before every push, read the issue afresh (`gh issue view <n> -R Mharbulous/probanda-dev --json labels,state`). When it carries `withdrawn` or is closed, its sender withdrew the suggestion: push nothing, take the stop route (step 5) with the reason `withdrawn`, and report the unpushed fix commits for Brahm to drop. Then run `python scripts/check_fix_commit.py --selection <selection path> --suggestion <each record path> --range origin/main..HEAD [--dropped <id>:<n> ...]`. It must pass; never amend or rewrite a commit to make it. Then `git pull --ff-only` and `env -u GH_TOKEN git push`; after a merge of origin/main, run it again before pushing.
   5. Stop route: a minor bump, a failed check you cannot fix inside the Scope, or a check that needs a person (a live service, a browser, public/ approval). Never fake or skip such a check. Restore your own uncommitted edits with `git restore -- <your paths>` and delete any new file you created. Release the claim by issue-tracker.md **Release**, whose comment says why. Report the reason, the unpushed fix commits, and any check Brahm must run, and stop.
   6. Land: after the push, comment on the issue (guarded with `python scripts/check_verbatim.py --suggestion <each record path> <comment file>`) with each fix commit's SHA and its `Suggestion <id> item <n>`, each check run and its result, each dropped unit and each not_built item of the selection with why. Close it with `gh issue close <n>`, then delete the claim comment (issue-tracker.md **Release**, delete only). Report the SHAs, the versions, the check results and anything left for Brahm.
   ```
