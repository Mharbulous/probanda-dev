# Workspace output rule

When a skill writes a file for a litigation matter, the file's kind picks the destination. Data goes to the matter's matter-data folder; documents go to the matter's draft folder. There is no third place, with three exceptions, below.

**1. Documents** — anything written for the practitioner or the forum to read: Word (`.docx`/`.doc`) and PDF deliverables, a Writing's mockups, and a Markdown draft or report meant for the practitioner to read (a client letter's draft, an overstatement review, a blackline):

```
{matter}\<draft folder>\<writing folder>\
{matter}\<draft folder>\   (an individual document's deliverables)
```

`<writing folder>` is the Writing's own folder, named after the document, the one its mockups are rendered into (spec 2026-10-22): its title, never a type's code, a stock type's name or an id. A package's Word and PDF deliverables go there beside the mockups. An individual document's go at the top of the draft folder under its `/file-naming` name: a general Writing (a letter, memo, release), a single BCSC form (a NOCC, petition, Response to Civil Claim, affidavit or amended pleading), a notice to admit, a bill of costs, an affidavit's bound PDFs and a BCCA factum. The packages are a Notice of Application or Application Response, a small claims reply, a BCCA book and a VanIAC package, and an affidavit sworn for a package goes in that package's folder. A submission package round uses the dated form `{date }{title}` (ADR 0008): dateless until a hearing or exchange date is confirmed, then the existing folder is renamed through `file-manager`, never duplicated. A document with no Writing gets a folder named `{CODE} {description}` by `/file-naming`'s grammar. The writing folder is created if absent. Nothing else is written by a skill at the top of the draft folder except the renderer-owned files `Litigation Strategy.html`, `workboard-status.js`, one `Job Board <id>.html` per open Job Board with no Writing and `Job Board - proceeding <id>.html` per pre-filing proceeding, and the `Drafting records` folder of render manifests (ADR 0017, ADR 0033's 2026-10-05 amendments, `shared/html-pages.md`). A Writing's Job Board page and view pages are in its own folder.

A mockup is a regenerable projection of the drafting database: overwritten in place on every re-render, its previous copy archived in the Writing's `archive` folder when the revision moved, never read back (sole exception: `/draft`'s revision-checked read of a mockup too large to return inline, ADR 0012). The matter's pages, the Litigation Strategy page and one Job Board page per board (ADR 0033, 2026-10-05 amendment; a merged board has one), are never read at all. A Markdown draft or report written for the practitioner to read is rewritten in place on each revision. **A Word or PDF deliverable is never overwritten**, because one the practitioner may already have reviewed, signed, or served must never be silently replaced. The default remedy is a new copy suffixed " v2", " v3", etc. A skill may instead refuse: write nothing, name the existing file, and ask the practitioner to move it aside by hand. Refusal is required when a later step takes the deliverable by one fixed file name and would not find a versioned copy, because that step would bind the stale copy and silently skip the new one (`assemble-vaniac-package` binds `Package\` that way, whereas `assemble-bcca-book` looks for the suffix). A skill may ask the practitioner before writing, but never overwrites, renames or deletes the old deliverable itself, except by the TRASH offer here. When a revision's Word or PDF copy is presented, the presenting skill names it as current, lists each copy of the same Writing presented earlier this session as superseded, and asks which to send to TRASH (`file_ops__trash`), acting only on the answer. If `file_ops__trash` is not available in this session, the `file-manager` plugin is not enabled: trash nothing, tell the practitioner that this step trashes a file and needs `file-manager`, and do nothing else for it. Never fall back to a shell `mv` or `rm` or the Write tool. A writing folder containing files the current skill did not write is never renamed or deleted — stop and ask. Exception: `/publish`'s `renumber-affidavit` writes each renumbered copy beside its source, named as the source with the number swapped and never over an existing file, and renames the affidavit's folder on the practitioner's yes.

- **Draft folder:** glob `0. DRAFT*` under the matter. Real matters spell it with and without a trailing "s" and in mixed case. Exactly one match → use it. Zero matches → fail loudly ("no draft folder in {matter}"). Two or more → fail loudly as ambiguous; never guess. Never create it — its absence means the matter path is wrong.

**2. Data** — agent working state: `.json`, `.jsonl`, indexes, previews, substance intermediates, session state, queues, scratch:

```
<matter-data folder>\<skill-or-workflow name>\
```

The matter-data folder is the folder `probanda.json`'s `case_data_dir` names — never a guessed literal. For a new or relocated matter it is the matter's own `0. CASE DATA\`; a matter not yet relocated keeps `..\0. CASE DATA\<matter name>\`. It must already exist: a writing skill never creates it, and its absence means the matter is not initialized (fail loudly, naming `/matter-data` initialize). `<skill-or-workflow name>` names the producer (e.g. `bcsc-form-substance`, `bill-of-costs`, `housekeeping`); a folder several skills hand files through keeps its one workflow name, and a workflow handling several instances nests one further level under a stable instance id. The subfolder is created on demand. Data files are rewritten in place — a workflow that re-reads its own data file must find one file, not a pile of versions.

- **Reaching it:** MCP tools resolve the matter-data folder host-side, through matter-data's own resolver. A Cowork project mounts only the matter folder. The matter's own `0. CASE DATA\` is inside it. For a matter not yet relocated, a session that writes data with its own file tools, or runs a script in the sandbox, first requests access to the matter-data folder itself (its path from `case_data_dir`), never to a parent or firm root. Either way it passes a script the path the session sees. A script handed a matter-data folder checks that it exists and that its name matches the last segment of `case_data_dir`, and fails loudly otherwise.

**The first exception:** research-agent answers are filed under `6. LAW\`, which `shared/legal-research.md` owns, because tier-3 audits read them there.

**The second exception:** the research agent's internal notes go to `<draft folder>\AI Scratchpad\research-agent\`, written only through `research_filing__write_scratch`, by the practitioner's decision of 2026-10-05, so the practitioner can open them beside the drafts. It is the one folder named for an agent that anything writes into.

**The third exception:** the matter's `ProceduralHistory.md` sits at the top of the matter folder, where `shared/procedural-history.md` puts it, so the practitioner finds it without opening a folder. It is rewritten in place.

No skill creates `4. LAWYER BRIEF` or any `CoWork` folder, and no skill writes matter files to `.claude`, `AI\`, or dated folders named for a specific agent such as `Claude` or `Codex`. Copying the firm's own matter template into a new matter (`/matter-data`'s matter skeleton) is not a skill output and is unaffected.

Outside this rule: matter-data's own files, which sit at the top of the matter-data folder; files that are not matter files at all (time-pipeline store data, skill eval reports); and /housekeeping's Move to `0. DRAFT` unchanged, which moves the practitioner's own existing file rather than writing one: a root-level file flagged as the firm's unfinished draft, or a root file of a kind ingest cannot read, goes to the top of the draft folder under its current name.
