# Deadline isolation

Shared doctrine for drafting work in this practice. It is not a skill: it has no `SKILL.md` and is never wrapped. It ships inside the `skills/shared/` tree of the installed litigation `.plugin`. Decision record: `docs/adr/0013-deadline-isolation-in-the-drafting-pipeline.md`.

- **Scope.** Binds drafting: eliciting, writing, researching, verifying and rendering a filing's substance, and outlining the work. A past event the draft needs is read from the matter's `ProceduralHistory.md` (`shared/procedural-history.md`) and is content; the practitioner is asked only that doctrine's one currency question.
- **Calling docket-clerk.** `lawyer:docket-clerk` is the only route for a date, from any session, a drafting session included: recording anchors, deriving, recalculating and listing deadlines, limitation dates, what-ifs, the court calendar and rule-overlay updates. Spawn it with the matter and the facts or document the practitioner gave. It never asks the practitioner anything: what it needs comes back as numbered open items. Relay each open item to the practitioner, collect the answer, and spawn it again with the answer, naming the open item it answers, until none remain. An item marked `kind: procedural-research` is not put to the practitioner: run `/legal-research` with its question, instrument and fetch target under the clerk's matter (with no matter, ask the live-issue question once), then spawn the clerk again with the cited answer, the item's `assumption` id and the original request, as its `re_spawn` line says. Without the researcher plugin, relay the item to the practitioner and say that closing it needs that plugin. For a date question (a what-if, an earliest hearing date, when something falls due), when the practitioner is present and has not given the application type or the time estimate, ask one question for it before spawning. Otherwise make the clerk's `Assumed` line the first line of your own reply, before any date it gives. A session never works a date out itself, from the court-calendar tools, the rule text or anything else.
- **Invariant standard.** Time remaining is not an input to drafting. There is no fast path, and none is invented.
- **No countdown.** Never fetch, compute, infer, or ask how long remains before a filing deadline. Whether a past event happened, and what a filing records about it (a hearing held, an order pronounced, an entry), is content. A deadline is not, past or future, even one an order sets: it stays a placeholder the practitioner fills. Content too: a letter's response date, computed from the period the practitioner states, and open days from `/practice-data` court-calendar-days offered as hearing dates, never reckoned from a rule period.
- **The other side's missed deadline is content** (ADR 0024 D7, which narrows the rule above and ADR 0013's #1028 amendment). A past deadline the other side missed, cited from the order that set it, is content in a drafting session: the draft may state the date the order set and that it passed unmet, as the order records it. The practitioner's own deadlines, past or future, stay isolated exactly as above. `/draft`'s date check keeps running for a cited missed deadline.
- **If the practitioner states a deadline anyway.** Acknowledge once, in one sentence: the plan and standard are unchanged, and timing belongs to the practitioner and `/executive-assistant`. Name the hatch in that same sentence. Never restate the deadline afterwards, since repetition amplifies it through the context.
- **A BF date is a start date, not time remaining** (`docs/adr/0021-the-matter-board-becomes-the-to-do-list.md` D2). A to-do's bring-forward date says when its work should start, so it may show anywhere, including on the Litigation Strategy page written at `/draft` session entry, as a plain date: no day count, no overdue marking, no reason for its position. A to-do's deadline is a deadline: it stays withheld from drafting sessions, and the Litigation Strategy page never shows it. A job's bring-forward date (`tickets.bf_on`, `/drafting-data` `references/jobs-closeout.md` §10b) is the same kind of date under the same rule: it shows as a plain date on the Milestone page and as `BF <date>` on `board_card`, it is set, changed or cleared only on the practitioner's word, and it is never proposed, computed, labelled as a deadline or sent to `lawyer:docket-clerk`.
- **A step's wait is a time to check a process, not a deadline.** A job step waiting on an external process, such as a Westlaw run, carries `ticket_steps.wait_until` (`/drafting-data` `references/jobs-run.md` §6b): the minute the session checks whether the process has finished. It shows as `⏳ until HH:MM`, a plain time, and never as time remaining or a countdown. It is never a deadline, and it never goes into a handover or a captured idea.
- **Hearing dates on the Milestone page** (ADR 0013, both 2026-10-04 amendments). The matter's anchors, the other side's deadlines, and deadlines whose anchor is linked to no filing with a completion-criteria card are plain dates in the page's Key dates card, with no day count. A deadline whose hearing anchor is linked to a filing is a criterion on that filing's completion-criteria card: its name, its state and its order within its anchor reach `board_summary` and `board_card`, and its date, rule text and review flag never do. That order follows the rule's offsets from one anchor, so it carries no matter timing, and no order across anchors is ever given. Every date is rendered for the human on the page and withheld from everything a session reads: `board_summary`, `board_card`, every other response field, and every persisted file. The page itself is never read by a session (`shared/html-pages.md`).
- **A Milestone is never a date.** The docket clerk never creates, closes or reads a Milestone. It only records dates; a Milestone's Key dates card shows the dates it has recorded.
- **Filing order.** Bootstrap lists filings in the order to present them. A session presents that order and never asks or infers what produced it.
- **Never persist it.** Not in a job's title, intent, plan or steps, an idea captured for later, or a handover written from a drafting session. All of these are read at the opening of later sessions. If the practitioner wants a deadline recorded, that is `lawyer:docket-clerk`, called as "Calling docket-clerk" above says.
- **The hatch.** A shorter filing is a different deliverable the practitioner chooses, never the same one done worse. It is the existing plan-change path: the practitioner says the plan should change, the revised plan records what was cut and never the date that prompted it. No new form, no new schema, no new work marker.

  *Why prose and not a decision form:* inside an approved plan the only permitted interruption is an obstacle the plan did not anticipate, and pausing for approval is itself an anti-pattern. A stated deadline is not an obstacle and a widget is a pause. The hatch stays named, and taking it enters the plan-change path, which has its own approval form.
- **Owners.** `lawyer:docket-clerk` holds anchors and does not rank or alert. `/executive-assistant` surfaces urgency, and ranking belongs to `task-prioritization`. Whether and when to start or file is decided there and by the practitioner, before a drafting session opens. Drafting owns quality and triage owns timing.
