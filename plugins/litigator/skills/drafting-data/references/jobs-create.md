Read when: an outlining session writes the jobs the practitioner selected at the closing read-back or picked from the Proposed lane (§3), the practitioner asks to rework a `queued`, unshelved job or adds a part to a queued form job (§3a), or the practitioner pulls Proposals from the `proposed` lane onto the board by a group, a filter, a submission or "take the next" (§3e), or a holding session spins off blocker jobs for the job it holds (§3f), or the practitioner says to work on the loose threads in a session holding no job (§3j), or a render's result carries `note_up_due` (§3k).
Any §N not in this file: find it in SKILL.md, "Job and scrutiny operations".

## 3. Create (outlining only)

**Who may create a job.** A job is created only on the practitioner's explicit request, or from a pattern they set up in advance: a document type's stock jobs, or a rule tied to a completion criterion. An idea that comes from the session or an agent, such as a research offer, a tangent, a suggestion or a finding outside these patterns, is captured as a loose thread (`jobs-run.md` §8, §8a) and never written as a job. A job's wording needs no practitioner approval: the practitioner-words gate does not read it. This table lists every path that creates a job.

| Path | Created when | Source | Wording |
|---|---|---|---|
| §3 outlining | The practitioner selects it at the closing read-back | Practitioner's request | The session's, from their answers, cleaned by the rules below |
| §3 fast path, §3e intake | The practitioner picks a Proposal, or pulls Proposals onto the board | Practitioner's request | A Proposal title a `drafting_forms__*` result printed, or §3e's fixed group title |
| §3f spin-off blockers | The practitioner says yes to the spin-off | Practitioner's request | Their words, or the session's proposal from the obstacle as recorded |
| §3j loose-threads job | The practitioner says to work on the loose threads | Practitioner's request | Their own words |
| §3h conversion job | The practitioner accepts the conversion offer | Practitioner's request | Its fixed title and intent, naming one Writing |
| §3i research offer job | The practitioner names a relayed offer to add | Practitioner's request | The offer's `job:` line from the subagent's return |
| §3l research plan issue jobs | The practitioner answers "No" to `/legal-research`'s closing plan question | Practitioner's request | Each approved issue's text as the list showed it |
| §3m research board premise job | The practitioner says yes to a premise or threshold question the research triage proposes | Practitioner's request | The proposed question as the triage return gives it |
| §3b stock jobs | `/prepare` offers them, or a letter, memo or Unstructured Writing is saved | Practitioner's pattern: the document type | Fixed text |
| §3c counsel's review pair | The completion criteria above counsel's review hold | Practitioner's pattern: the completion criteria | Fixed text and title prefix |
| §3d scrutiny review job | A scrutiny return is recorded `'failed'` | Practitioner's pattern: the scrutiny rule | Fixed text and title prefix |
| §3g pass finding job | A pre-review pass leaves a finding undecided | Practitioner's pattern: the pre-review passes | Fixed text |
| §3k note-up job | A render's result carries `note_up_due` | Practitioner's pattern: noting up is mandatory before a Writing is sent or filed | Fixed text |
| §14 gate job | The Writing's last open job completes | Practitioner's pattern: the completion criteria | Fixed text |
| §14a pre-send gate job | `drafting_data__record_sent` finds a held criterion unmet | Practitioner's pattern: the pre-send hold | Written by that tool, not through `execute` |

Only in an outlining session (Branch B's outlining interview, or a `kind = 'charting'` job's own work), and only for jobs the practitioner outlined and selected at the closing read-back, and in the fixed-text creates with sections of their own: §3b to §3e, §3f, §3g, §3i, §3j, §3k, §3l, §3m and §14. **Two calls, not one** — the job's `id` is autogenerated, and nothing after the first `INSERT` in the same `execute` script can safely name it: `last_insert_rowid()` only ever holds the *most recent* insert's own rowid, so a second child `INSERT` in the same script (e.g. the second `ticket_steps` row) would see the first child's rowid, not the job's — silently attaching a step to the wrong job, or failing the `ticket_steps.ticket_id` foreign key if no job happens to share that id.

**Read first — the priorities already queued on this Writing.** `priority` is set relative to the jobs already queued there, never guessed: the Ready queue is `priority` descending then `id`, which no session reorders. No session asks the practitioner for an order.

```sql
SELECT id, priority, title FROM tickets
  WHERE proceeding_id = 1 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL AND (filing_id = 1 OR filing_id IS NULL)
  ORDER BY priority DESC, id;
```

Every job of the batch takes one below the lowest `priority` returned, or the schema default, `0`, when no row returns, so the new jobs queue behind every job already queued, in the order written by `id`. Order between jobs that depend on each other comes from their dependency edges, never from `priority`: the board holds a blocked job out of Ready until its blocker is done. Only where the practitioner stated an order unasked is a job placed otherwise: one they want worked before everything queued takes one above the highest returned; one that belongs between two takes a value between theirs, which needs the rows beneath it renumbered in the same script when those two are adjacent. Proceeding-scoped jobs (`filing_id IS NULL`) are included because they queue on this Writing's board too (§11). `rejected_at IS NULL` excludes a shelved queued job because it sits in Shelved, not the Ready queue (design §10's Job list precedence), so its priority anchors nothing. On a Job Board with no Writing, the job's `filing_id` is the board's id, never NULL, and this read drops `OR filing_id IS NULL`, because a proceeding-scoped job never queues on that board (§11).

**Call 1 — create the job:**

```sql
INSERT INTO tickets (proceeding_id, filing_id, title, intent, kind, priority, billing_anchor, created, created_by)
  VALUES (1, 1, 'reply to their attornment argument', 'I want to reply to their attornment argument once the memos are audited.', 'work', 4, 'L8212|attornment defeats the stay', strftime('%Y-%m-%dT%H:%M', 'now', 'localtime'), 'sess-a1');
```

`created_by` is this session's own `session_token` (§1; `'sess-a1'` stands in for it), written by this section's two creates, the plain one above and the guarded one below, and by no other create. It is what lets this session later be assigned one of the jobs it created, and only those (§4).

Outside nine fixed-text exceptions — §14's gate job, the fast-path job, §3b's stock bundle jobs, §3c's counsel's review jobs, §3d's scrutiny review jobs, §3i's research offer jobs, §3j's loose-threads job's step, §3k's note-up job and §3l's research plan issue jobs — `title`, `intent` and every `ticket_steps.text` written here are worded by the session from what the practitioner selected at the closing read-back, with no adoption ceremony and no pasting (`shared/paralegal-posture.md` section 3) — `intent` one sentence stating what they asked, in their own words where their answer states it, `title` a short label for it, cleaned as below; the `title` literal is the selected card's value. Neither states a position, figure, statement of law or research question the practitioner or the record did not. How the work divides into jobs and steps is the session's call, and so is their wording, except that filling one form is one job with a step per part: a further part extends a live job on that form (§3a, "Adding a step") rather than creating another (`/work`'s `job-session.md`, "A form is one job"). The steps are the job's plan, so the intent is never written as a step, not even a one-step job's only one, and no `ticket_steps.text` written here equals or contains the job's title or intent (`/work`'s `job-session.md`, "A step that only restates the request"): where the answers hold no step that names the work, `/draft` writes one that does before the read-back. A fast-path job's title and intent are the Proposal's title as the card printed it, `<work name>: <item label>`, and its steps are §6a's step derivation (`filing-checklists.md`) on the Proposal's item, so that each step names the work rather than restating the title. All of them are fixed text from the record and not the session's words, written with no closing read-back because the pick is the practitioner's: a Proposal picked and left unedited is its approval. A stock bundle job's strings are §3b's, a counsel's review job's are §3c's, a scrutiny review job's are §3d's, and a research offer job's are §3i's, on the same terms.

**A new job's title is a cleaned label; its intent is the record.** The title is how the Job Board names the job, and the intent carries what was asked, so the intent keeps every word the practitioner used, typos and all, and the title is cut from them and cleaned. Cleanup corrects spelling, typos, grammar and capitalisation only, and may close the title with a full stop. It never adds, drops, swaps or moves a word's meaning, never narrows or broadens what they asked, and states no law, figure, position or research question they did not. A title the practitioner gives as a title is written exactly as typed. Cleanup is not a proposal, so it needs no approval. Fixed text, Proposal titles and the prefix-matched titles above are never cleaned.

| Typed | `title` | `intent` |
|---|---|---|
| `research whether there is such a think as criminal nuisance in BC` | `Research whether there is such a thing as criminal nuisance in BC` | `Research whether there is such a think as criminal nuisance in BC.` |

**A new job's intent and steps take a capital and a full stop.** The intent and each step a new job takes from the practitioner's words start with a capital letter and end with a full stop, which is added only where their words have no closing mark: a question keeps its question mark. That is presentation only, and needs no approval. Fixed text, Proposal titles and items, a step built from a printed item, and §3j's intent are never touched.

**A job outlined from Proposals takes the guarded create instead of the plain `INSERT` above** — the fast-path job always, and a hand-worded job outlined from Proposals too. The job row survives only when no `queued` or `wip` job with `rejected_at IS NULL` already holds any of its keys. Call 1 is the plain `INSERT ... VALUES`, followed in the same script by a `DELETE` of that row whenever a live job holds any of its keys, every key named in the `IN` list:

```sql
INSERT INTO tickets (proceeding_id, filing_id, title, intent, kind, priority, billing_anchor, created, created_by)
  VALUES (1, NULL, 'Note up: Smith v. Jones, 2023 BCCA 182', 'Note up: Smith v. Jones, 2023 BCCA 182', 'work', 4, 'L8212|attornment defeats the stay', strftime('%Y-%m-%dT%H:%M', 'now', 'localtime'), 'sess-a1');
DELETE FROM tickets WHERE id = last_insert_rowid()
  AND EXISTS (
    SELECT 1 FROM ticket_proposals p JOIN tickets t ON t.id = p.ticket_id
      WHERE p.proposal_key IN ('note-up:authorities:5') AND t.status IN ('queued', 'wip') AND t.rejected_at IS NULL AND t.deleted_at IS NULL);
```

Keep the `INSERT` then `DELETE` shape: `last_insert_rowid()` is safe here only because the `DELETE` directly follows the job's own `INSERT`. The new row has no `ticket_proposals` rows yet, so it can never match its own guard.

A 📇 Proposal becomes a job of its own, `Note up: <item>`, only here, when the practitioner picks that one Proposal. Every other note-up is the Writing's one `Note up all cited authorities` job (§3k).

**Call 2 returning no row is the signal** that the key is already held: nothing was written, and the rest of that job's calls are skipped. Take the holder's number from `drafting_forms__board_card` with `key`, after a re-render (the live job it prints, or the Proposed line's `held by #N`), say "already a job: Job #N" in one line, and go on with the rest of the batch. There is deliberately no unique index: a `completed` job keeps its rows, and a second job on the same key after completion is legitimate, so the guard looks only at `queued` and `wip` holders. Without the guard, a fast-path duplicate would be silent, because its Proposal is hidden behind the first holder and nothing on the board shows the second.

**Call 2 — recover its id**, the same single-practitioner trust model as the confirm-read after assigning (§4): the just-written `title` and `created` stamp together are specific enough in practice; if more than one row matches, stop and ask rather than guessing which is the new one.

```sql
SELECT id FROM tickets WHERE proceeding_id = 1 AND title = 'reply to their attornment argument' ORDER BY id DESC LIMIT 1;
```

After a guarded create the recovery takes a different shape, because a fast-path title recurs: an older job on the same key, now completed, carries the same `<work name>: <item label>` title, and the plain shape above would return it when the guard wrote nothing. The just-created job is the one queued job with that title that holds no `ticket_proposals` rows yet, since those rows are written after this call and an older job on the same key keeps its rows. No `LIMIT`, so that a second match shows and stops the session:

```sql
SELECT id FROM tickets t WHERE proceeding_id = 1 AND title = 'Note up: Smith v. Jones, 2023 BCCA 182' AND status = 'queued' AND deleted_at IS NULL
  AND NOT EXISTS (SELECT 1 FROM ticket_proposals p WHERE p.ticket_id = t.id);
```

No row is the signal above. One row is the new job. More than one: stop and ask.

**Call 3 — the job's children**, every one of them using that recovered id as a literal (here, `2`) — steps and scope reference the job row just written; blocks/conflicts reference other jobs that must already exist:

```sql
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 1, 'Audit the exhibit list');
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 2, 'Reconcile against the disclosure log');
-- one INSERT per step, always at least one, ordinal 1, 2, 3... -- every one uses the SAME literal
-- job id recovered in call 2, never last_insert_rowid() (see above).

INSERT INTO ticket_scope (ticket_id, entity, entity_id) VALUES (2, 'facts', NULL);
-- entity is any table name as spelled in schema.sql, substance or join.
-- entity_id NULL means the whole table within this job's filing/
-- proceeding -- what a job that CREATES rows needs, not one that only
-- edits existing rows.

INSERT INTO ticket_blocks (blocker_id, blocked_id) VALUES (1, 2);
-- blocker_id must already exist and complete first.

INSERT INTO ticket_conflicts (a_id, b_id) VALUES (1, 2);
-- canonical order required by the CHECK -- always the smaller id first.
```

**The plan marker.** A job written here with no steps the practitioner supplied or approved, and none derived from a Proposal card, takes exactly one step, ordinal 1, this fixed text character for character: `Create a plan for how to complete this job.` The session never words a plan in its place. The marker says the job still needs a plan, so a planning pass finds it by its text. It is never reworded, never stamped done and never approved as a plan: `/job-planning` replaces it with the planned steps (`shared/job-planning.md` section 3), and `/draft` assigns no job whose only step it is (`work/references/job-session.md`, "A job that needs a plan"). A job outlined from a Proposal keeps its card-derived steps, and each fixed-text create keeps the steps its own section gives, taking the marker only where that section says so (§3f, §3i, §3l).

```sql
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 1, 'Create a plan for how to complete this job.');
```

`billing_anchor` (`kind = 'work'` only — the CHECK rejects a work job with none): derive per `shared/live-issue-test.md`, written `<matter>|<live issue or deliverable>`, asked only when it cannot be inferred from the Writing/proceeding already in hand. A job outlined from a Proposal is never asked: it copies the anchor every work job on the open Writing carries, else takes `<matter>|<that Writing's title>`. A `kind = 'charting'` job carries no `billing_anchor` — outlining itself decides what gets billed once it produces `work` jobs.

`filing_id` **on a job outlined from a Proposal** follows the row the Proposal is keyed on, not the Writing being worked. Nearly every keyed row is proceeding-scoped substance shared across that proceeding's Writings, so the job defaults to proceeding scope — `filing_id` NULL, a General Job — and shows on every Writing's board in the proceeding, tagged General. Two keyed rows are the Writing's own and default to its id: the venue form's pointer rows (`filing_facts` / `filing_submissions` / `filing_orders`) and the `filings` row itself. The practitioner may say otherwise in the interview, and their answer wins over either default. Its scope rows are the key's own `(<table>, <id>)` and `(<table>, NULL)` for each other table, created or edited, that the work's clearing action writes, read off its key type's row in `filing-checklists.md` §6a ("Clearing action also writes"), never inferred. This rule governs only a job outlined from a Proposal; one the practitioner outlined from their own words takes the scope their answers give it.

**Consuming a loose thread not yet outlined** (the practitioner chose to outline it now):

```sql
UPDATE seeds SET charted_into = 2 WHERE id = 1;
```

Run this once the job it became now exists (its recovered literal id — call 2 above); it removes the loose thread from the Job Board's "Loose Threads" section (the query there filters on the board's open-thread condition: not outlined, not discarded, not suggested). §3i's add path runs this same write outside an outlining session, on a thread its sort captured.

**Consuming a loose thread the held job worked** (`/work`'s `work/references/loose-thread-triage.md`, "Working the threads without a pick"): the job whose intent is working the loose threads marks the thread it worked as consumed by itself, once that work is done. No job is created. The write carries §5's lock guard, then its confirm-read, expected the one row with `charted_into` the held job's id:

```sql
UPDATE seeds SET charted_into = 42 WHERE id = 7 AND charted_into IS NULL
  AND EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND locked_by = 'sess-a1');
SELECT id, charted_into FROM seeds WHERE id = 7;
```

`42` is the held job, `7` the thread and `'sess-a1'` this session's token. The thread and the job are in the same proceeding (`jobs-integrity.md` §11). `charted_into` still NULL on the confirm-read means the lock is no longer this session's: stop, and run §2's scope read, whose row says why. No other assigned job runs this write.

**Recording the Proposals a job was outlined from** — the same shape as the loose-thread consumption above: its own statement, after call 2, on the recovered literal id, never `last_insert_rowid()`. One row per key the job was outlined from; one job may hold several keys, and a merged job does:

```sql
INSERT INTO ticket_proposals (ticket_id, proposal_key, item)
  VALUES (2, 'note-up:authorities:5', 'Smith v. Jones, 2023 BCCA 182');
INSERT INTO ticket_proposals (ticket_id, proposal_key, item)
  VALUES (2, 'authority-excerpt:statements_of_law:12', 'Smith v. Jones, 2023 BCCA 182 — the implied-term test');
```

`proposal_key` is the key the render put on that Proposal, copied character for character out of `drafting_forms__board_card`'s Proposed lane (its detail line's `key:`) — never recomposed from a slug and a row id. `item` is NOT NULL and takes **that key's own item text as that card printed it at the write (its detail line's `item:`), without any count** — the keyed row's identity, never the job's title. So a job the practitioner merged from two Proposals and titled in their own words carries a different `item` on each row and a title matching neither. There is no `marker` column: a glyph shift on the keyed row is not something this record can notice, and deliberately so.

These rows are what hide their Proposals from `drafting_forms__board_card`'s Proposed lane while the job is `queued` or `wip` and unshelved, so a key copied wrongly hides nothing and its Proposal shows again beside the job. They are written only for a job outlined from Proposals — a job the practitioner outlined for the same work in their own words carries no conversion record and leaves its Proposal showing, which is a visible duplicate rather than a silent one.

## 3a. Outline afresh (outlining only)

Reworking an existing job in place, at the practitioner's request, where `status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL`. It is outlining, so the session that does it is never assigned a job (§4) and never does it inside an assigned job's own session — §5's Change path is the assigned job's route and is untouched by this.

**The guard rides every statement in the script, not only the `tickets` update.** `drafting_data__execute` runs the script in one transaction and rolls back on an exception; a guarded `UPDATE` or `DELETE` that matches zero rows is not an exception, so an unguarded `INSERT` beside it would commit alone and leave the job half-rewritten. Each statement therefore carries the job's still-queued, unshelved state itself — as its own `WHERE` clause on the job row, as an `EXISTS` subquery on a child delete, and as `INSERT ... SELECT` on a child insert:

```sql
UPDATE tickets SET title = 'audit the exhibit list against the disclosure log', intent = 'I want the exhibit list audited before the reply goes out.', priority = 6
  WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;

DELETE FROM ticket_scope WHERE ticket_id = 42
  AND EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);

INSERT INTO ticket_scope (ticket_id, entity, entity_id)
  SELECT 42, 'statements_of_law', 12 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
```

`title` and `intent` are worded from this interview, on §3's terms.

**A `priority` set between two adjacent jobs renumbers the rows beneath it** (§3), and here those rows are *other* jobs, so their `UPDATE` cannot lean on job 42's own `WHERE` clause. It carries job 42's still-queued, unshelved state as an `EXISTS` of its own, the same shape a child delete uses — otherwise the renumbering commits alone when the outline itself matched nothing, and the Writing's queue is left reordered around a job that was never rewritten:

```sql
UPDATE tickets SET priority = 5 WHERE id = 11
  AND EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);
```

**Scope rows may be replaced, not only appended.** The job has no holder, so no write is in flight against a row this deletes — the opposite of §7, which appends for a job already assigned and never deletes.

**The steps and their approval travel together or not at all.** If the practitioner confirms the read-back step list unaltered — nothing reworded, reordered, added or removed — `ticket_steps` and `plan_approved_at` are left alone and every `done_at` on those steps survives. Any alteration at all deletes and recreates the steps and clears `plan_approved_at`, in the same script:

```sql
DELETE FROM ticket_steps WHERE ticket_id = 42
  AND EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);
INSERT INTO ticket_steps (ticket_id, ordinal, text)
  SELECT 42, 1, 'Audit the exhibit list' FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
INSERT INTO ticket_steps (ticket_id, ordinal, text)
  SELECT 42, 2, 'Reconcile against the disclosure log' FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
UPDATE tickets SET plan_approved_at = NULL
  WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
```

**Adding a step.** A part added to a queued form job (`/work`'s `job-session.md`, "A form is one job") is an addition, so it clears `plan_approved_at` too, but it appends rather than replaces, so every existing step keeps its row, its ordinal and its `done_at`. One `INSERT` per added step, in order, each after the highest ordinal, and the clear in the same script:

```sql
INSERT INTO ticket_steps (ticket_id, ordinal, text)
  SELECT 42, (SELECT COALESCE(MAX(ordinal), 0) + 1 FROM ticket_steps WHERE ticket_id = 42), 'Fill in Part 3 (Legal Basis).'
  FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
UPDATE tickets SET plan_approved_at = NULL
  WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
```

A completed, superseded, shelved or in-progress job matches no row, so nothing lands and the job stays as it was. A completed job is never extended: the part goes into one new job (§3).

**Edges may be added or deleted, on either side** — unlike §3, which only ever creates them:

```sql
DELETE FROM ticket_blocks WHERE blocker_id = 7 AND blocked_id = 42
  AND EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);

INSERT INTO ticket_blocks (blocker_id, blocked_id)
  SELECT 9, 42 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL
    AND EXISTS (SELECT 1 FROM tickets WHERE id = 9 AND status <> 'superseded' AND rejected_at IS NULL AND deleted_at IS NULL);

INSERT INTO ticket_conflicts (a_id, b_id)
  SELECT 11, 42 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
```

**A newly named blocker must be one the job can actually wait on** (design §11): a fresh outline that names a superseded or shelved blocker drops the job straight back into Blocked behind a dead blocker, the very state the outline was run to leave. So the blocker-side insert proves job 9 too — that it exists, and that it is not superseded, shelved or deleted. A `queued`, `wip` or `completed` blocker all pass: completion is what the blocked job is waiting for, and a blocker still in progress will reach it.

`ticket_conflicts` still takes the canonical order the CHECK demands (§3), smaller id first, whichever job is being outlined. An edge whose **blocked** side is another job is different: it changes what that job waits on, so that job must be queued and unshelved too, and the script proves it rather than assuming it from the board:

```sql
INSERT INTO ticket_blocks (blocker_id, blocked_id)
  SELECT 42, 11 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL
    AND EXISTS (SELECT 1 FROM tickets WHERE id = 11 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);
```

**What never changes, whatever the practitioner says:** `proceeding_id`, `kind`, `created` and `billing_anchor`. `filing_id` changes only by `jobs-closeout.md` §10c's move, never in an outline afresh. Accepted cost: a job outlined afresh away from the work its Proposal named still hides that Proposal while it is queued. The marker itself still shows on the mockup, so the work is not lost.

**The job's `ticket_proposals` rows change in two ways only** (the 2026-09-21 design §4.6 and §4.8). **Refresh `item`** on each key the job keeps whose item now reads differently, so a reworded item is not reported each time the job is assigned. It runs only after the practitioner has been shown the old and new text and has confirmed; without that confirmation the old `item` is the evidence the column exists to keep, and it is left alone. The new text is the key's current item as the job's card (`drafting_forms__board_card` with `jobs`) prints it now, the quoted text in that key's `(now: <glyph> "<current item>")` on the job's `keys:` line, unquoted and without any count, on §3's terms:

```sql
UPDATE ticket_proposals SET item = 'Brown v. Green, 2024 BCSC 77'
  WHERE ticket_id = 42 AND proposal_key = 'note-up:authorities:5'
    AND EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);
```

**Drop the dead keys** where the outline afresh was entered as "keep it" from a pre-claim check (the 2026-09-21 design §4.8), by §5's `DELETE` shape with this section's guard in place of §5's. Never otherwise.

Then run the confirm-read (§2) — the one read that distinguishes a script that landed from a guard that matched nothing.

## 3e. Intake

`/draft`'s intake writes Proposals in the `proposed` lane, read off `drafting_forms__board_card` with `lanes: ["proposed"]`, as fast-path jobs, on the practitioner's word and with no further act. It never runs at an Opening of its own accord, so a bare Opening writes nothing, and it never runs in an unattended run. It takes only `- <glyph> <title>` lines whose detail line reads `lane: proposed`, never a `lane: held by #N …` line nor anything under `## Shelved`, and it runs on one of three triggers, each of which chooses the batch:

- **A group or filter the practitioner names** ("all the exhibit pinpoints", "every note-up", "everything for Submission 3"): the lines their words pick out, by key type (§6a's work, as they name it) or by a submission's rows (below). Where the words fit more than one reading, ask which, and write nothing until they answer.
- **"Take the next", with Ready empty:** one job's worth. The first line in the lane's printed order whose key is never-held (below) and whose key type `filing-checklists.md` §6a does not mark as the practitioner's own, together with every line that would join it in one job (Grouped Proposals and One title, one job, below).
- **A task typed with the invocation that names a submission:** the lines keyed on that submission's rows (below). A typed task that names no submission converts nothing.

A single Proposal named is not intake: it is the fast path (§3), picked by the practitioner. A batch's `note-up` lines are never written by the calls below: intake runs §3k on them, however many there are, which writes the Writing's note-up job or adds them to it. Proposals of another type in the group table (Grouped Proposals, below) are written together as one job, and so are lines that print one title (One title, one job, below); every other line is its own job. Intake, like §3c's pair and §14's gate job, is a fixed-text create and not outlining: it writes no `created_by`, so §4's rule for a session that created jobs does not bind the intaking session when it then assigns a job. Each job's three calls run before the next job's Call 1, so that Call 2 sees only the job just written.
