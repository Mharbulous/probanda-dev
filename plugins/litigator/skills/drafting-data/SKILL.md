# drafting-data — router and schema owner

Helper skill — not user-invocable. The single gatekeeper for the drafting database: **one SQLite database per matter**, reached only through the `drafting_data__*` / `drafting_forms__*` MCP tools. No other skill may embed SQL, resolve the database path, or assume schema shape — all of that stays here.

Design source of truth: `docs/Research/2026-08-18 legal-submissions plugin domain model and schema (issue 291).md` (sections referenced below), ADR 0004 "The submission database is one file per matter; privilege is a property of the row's kind, not of which database it sits in" (unlike matter-data's main/law/privileged split, the whole drafting database is work product — temporarily privileged until delivered; a `disposition` column (`included | reserved`) carries reserved submissions/relief/authorities, which render only in a mockup's trailing *Held in reserve* section and never on the filed face — court-form exception (the BCSC Notice of Application, [#367](https://github.com/Mharbulous/CoClerk/issues/367)): this form has no trailing section at all, so a reserved order renders inline in Part 1, crossed out (struck through, unnumbered), and a reserved submission/statement simply does not render on it; both still never reach the filed face — see `.claude/skills/draft/User_Journeys/hold-it-in-reserve.md` for the design gap this leaves open; true solicitor-client material has no column anywhere in this schema and stays in matter-data's privileged store), ADR 0005 "Every submission session starts from a freshly rendered mockup, not from database queries" (amended by ADR 0017: `drafting_forms__bootstrap` renders nothing — a mockup is proven fresh by its render stamp, and whatever is stale renders in the background, off the critical path; a session orients from the mockup via its work markers — reached through `drafting_forms__render`'s returned `markdown`, since a session never reads the mockup files itself ([#337](https://github.com/Mharbulous/CoClerk/issues/337)) — going to the database only to look up detail, refresh, or verify, never opening a session with a battery of queries), and the root `GLOSSARY.md`. This skill is the schema's home, not a restatement of the design doc — read it there for rationale; read `references/schema.sql` here for the current DDL.

## Operation Routing

Determine the operation and call the corresponding tool. Tool names below are the roster fixed by the design doc's section 6, and every row is built and callable ([#294](https://github.com/Mharbulous/CoClerk/issues/294) shipped `query`/`execute`/`migrate`; [#297](https://github.com/Mharbulous/CoClerk/issues/297) shipped the `drafting_forms__*` pair). `write_slice` and the per-slice worker model it served were closed as superseded ([#302](https://github.com/Mharbulous/CoClerk/issues/302) decision 6, closing [#296](https://github.com/Mharbulous/CoClerk/issues/296)) — v1 has no parallel-worker concurrency to guard against.

Every tool below except `drafting_forms__open_session` takes an already-resolved absolute `db_path`, never a `matter_root` it resolves itself; `open_session` is the Configuration section's path rule as one call, and returns the `db_path` every other tool takes. The backend is deliberately generic about matter-workspace layout (see Configuration). Compute `db_path` once, per the Configuration section, before calling any of them.

| Create a Writing (a `filings` row with its stored layout) | `drafting_data__create_writing` | `{db_path, proceeding_id, tree: {country, jurisdiction, venue}, kind, recipient?, title, subkind?, round?, signer_key?, signer_party_id?}` — `venue` is a venue folder of `/draft`'s knowledge tree or `_NoVenue`, and `kind` a row's file stem or alias in that folder's kinds index, matched exactly (no case folding or fuzzy match), that names exactly one row by itself: a re-snapshot resolves the stored kind with no recipient, so a shared alias refuses `kind_unresolved` naming the candidate rows, and the composing skill resolves the user's phrase to one row's identifier first. Refusals write nothing: `invalid_title` (a blank title), `no_writing` (the proceeding has no Writing, so its own board already holds jobs with no Writing). `drafting_data__create_writing` refuses the kind (`reserved_kind`), and `execute` never inserts the row. States, closing and the writes that refuse it: `references/filing-checklists.md` §11 |
| Record a Job Board's statement of goals (the card labelled Goal) | `drafting_data__set_board_goal` | `{db_path, filing_id or proceeding_id, status, statement?, description?, session_token}` — one write, on any kind of board: `filing_id` for a Writing's board or a Job Board with no Writing, `proceeding_id` for a pre-filing proceeding's board (one with a Writing refuses `proceeding_has_writing`). `status` is `confirmed` (the practitioner approved the statement), `inferred` (the session's own wording after the practitioner declined: shown in italics as "Inferred, not confirmed", never relied on as confirmed) or `declined` (the practitioner declined and nothing is inferred yet: no `statement`). `statement` is the whole text, stored verbatim with its line breaks and indentation, required for `confirmed` and `inferred`. `description` is the line the closed card shows; omitted, the stored one stays, else the board's default (`<Writing title> Drafting`, a Job Board with no Writing's own title, or `Proceeding <id>`). | Assign a job to this session (the assigning write and its confirm-read) | `drafting_data__assign_job` | `{db_path, ticket_id, session_token, takeover?, expected_holder?}` — one guarded `UPDATE` then the confirm-read, in one call. By default it matches only a job that is queued, unlocked and not shelved; `takeover: true` admits a `wip` job, only after the practitioner's explicit yes to the take-over prompt, and needs `expected_holder`, the `holder:` tag off the job's card: the write lands only while that holder is still on the row. Outcomes, read off the confirm-read: `completed` (`changes` 1 when this call completed it, 0 when another session did), `not_held` (another session's token: taken over), `shelved` (no lock, `rejected_at` set), `no_match` (the guards matched nothing), `steps_open` (a step is ☐, ↻ or ⏳, so nothing was written; `open_steps` names each). Never retry to win. It moves no revision. Refusals write nothing: `invalid_ticket_id`, `invalid_session_token`, `invalid_expected_holder`, `not_found`. Semantics: `references/jobs-run.md` §10 |

| All other writes: create a proceeding, ingest parties/documents, and every subsequent write | `drafting_data__execute` | `{db_path, sql_script}` — one transaction, no compare-and-swap. | Render one Writing's mockup(s) | `drafting_forms__render` | Writing → mockup + conditional archive copy, stamped with `db_meta.revision` (§5); memoised by render stamp (ADR 0017): when the Writing's stamp matches its `render-manifest.json`, nothing is re-rendered and no canonical mockup is rewritten, and a named document's markdown still returns. A successful mockup render carries `background_job` (see bootstrap). Returns each document's `markdown` inline as well as its path ([#337](https://github.com/Mharbulous/CoClerk/issues/337)) — read that text to interpret work markers, and present the practitioner the file (`shared/present-files.md`), never its contents. With `presentation_dir` ([#466](https://github.com/Mharbulous/CoClerk/issues/466), ADR 0012) or `draft_dir` it also writes each presentation copy into that confined `0. DRAFT` subfolder and returns `markdown` only for documents named in `documents`; every other document carries `markdown_chars`, its length, in place of its text. To read a document's work markers, name its `document_type` in `documents`. Optional `draft_dir` ([#689](https://github.com/Mharbulous/CoClerk/issues/689), never with `presentation_dir`) has the server find that subfolder itself, `<CODE> <filing folder>` with or without a leading `YYYY-MM-DD `: none creates the undated one, one undated is used, and one dated (`presentation_dir_dated`) or two or more (`presentation_dir_ambiguous`) refuse before any write, naming each candidate and whether a dated one is renameable. ## Schema reference

`references/schema.sql` is the canonical current schema — generated by dumping `sqlite_master.sql` from a database freshly migrated via `references/scripts/migrate_engine.py`, with `references/scripts/regen_schema.py`, never hand-edited. It must match a live migrated database byte-for-byte; if it doesn't, `migrations.sql` changed without regenerating it, and it must be regenerated before this skill is trusted.

**Shape** (design doc §1–§2): `Matter → Proceeding → Filing → sections/join rows`, with substance (parties, facts, documents, witnesses, authorities, relief, submissions, opposing points) **proceeding-scoped and shared** — stored once per proceeding, selected and ordered into a Writing through a join row (`filing_relief`, `filing_facts`, `filing_submissions`, `filing_documents`). All ordering is by explicit `ordinal` columns, never rowid or timestamp.

**Not stored, deliberately**: deadlines (`lawyer:docket-clerk`), matter/client identity beyond `matter_reference` (`practice_data__matter_lookup`), review state other than job process state (below), solicitor-client communications and legal advice (§3 / ADR 0004). The Writing lifecycle (schema v19) does not breach the deadline clause: the four lifecycle dates it stores (`filings.filed_on`/`decided_on`/`entered_on`/`retired_on`) record acts that have happened, not dates by which something must, and so does `facts.procedural_on` (schema v77), the date a procedural step happened, from which nothing is computed, and `ticket_steps.wait_until` (schema v78) is the minute to check an external process, never a deadline or time remaining; the one genuine deadline the derivation consults — the appeal deadline — is supplied per render call as `drafting_forms__render`'s `appeal_deadline` parameter and is **never written to this database**.

**Job process state** (schema v15, ADR 0009 — the exception to "review state of any kind" above, superseding that clause for the nine `tickets`/`ticket_steps`/`ticket_scope`/`ticket_blocks`/`ticket_conflicts`/`seeds`/`ticket_proposals`/`proposal_rejections`/`ticket_answers` tables only): a `/draft` session either executes one assigned job or outlines jobs, new or outlined afresh, per `Engineering/1. Design/2026-09-02_draft-submission-ticket-sessions-design.md`. ## CRUD guidance

- **Reserve is derived, never stored** (ADR 0004, design doc §3, schema v10 [#380](https://github.com/Mharbulous/CoClerk/issues/380)): there is no `disposition` column — an item (`submissions`, `order_sought`, `authorities`, `statements_of_fact`, `rhetorical_paragraphs`) is *held in reserve* purely because no Writing's advocacy document currently points at ("deploys") it, computed at render time from the join tables. A renderer must filter a deployed face to deployed rows only — a reserved row reaching the filed face is a renderer defect, not something this skill scans for.
- **Killed is a stored, retained rejection, distinct from reserve** (schema v16, practitioner + Fable review 2026-09-06): `submissions.killed_on` and `authorities.killed_on` are nullable dates — set = the practitioner reviewed and rejected this item, kept intact (wording, excerpts, statements of law) so a later drafting or research pass never regenerates or re-proposes it; NULL = not killed; clearing the date restores it. This never means row deletion — the content is the point, so a second session can recognize "already considered." Killing a submission also removes its `filing_submissions` rows from every drafting Writing in the same write, so a killed item is reserved by construction there; a sent or retired Writing keeps its row, because it was sent with the submission and v58 freezes its pointer lists; a killed authority's `statements_of_law` ride the same brief-only cap as `verification = 'lead'`. Neither state carries a work-marker emoji (`references/work-markers.md` rule 5 — a decision already made names no work); neither prints on any mockup or filed face; the dates stay in the database. Since v64 the practitioner can also omit a proposition (`law_assertions.killed_on`), by the same idiom: kept, never re-proposed, restored by clearing the date. Omitting unlinks nothing, and so far only the Raw Research page reads it.
- **Statute currency is a stored, relayed result** (schema v34, #1181): `authorities.currency_status` and `authorities.currency_checked_on` are written by `/draft` after `/legal-research` relays the statute-currency check's `currency` value for an authority of kind `statute`, `regulation` or `rule`: `currency_status` is that value verbatim, `currency_checked_on` the date it was relayed. NULL in both = never checked. Never write `'validation_unavailable'` for a check that never ran — that value is the check's own report of a lookup it attempted and could not verify. An edit to the authority's `citation` or `style_of_cause_or_title` clears both columns, since the result was for the enactment as then named; since v35 the trigger `clear_authorities_currency_on_rename` does this, so a statement that renames and sets a new result in one write still ends cleared, and the writer records the fresh result in a later statement. The general renderer's `terms` projection reads it: an implied clause naming that enactment while `currency_status` is anything but `'current'` is tagged on the mockup and refuses the filed render.
- **Statute currency is also recorded per cited provision** (schema v53): the instrument's `'current'` never clears a clause on its own, because one instrument-level value cannot say "Rule 8-1 amended; Rules 9-6, 3-4 and 14-1 untouched". Each provision a statement of law pinpoints on a `statute`/`regulation`/`rule` authority takes its own `provision_currency` row, keyed by `authority_id` and `provision`, which is the statement's `pinpoint` verbatim (a statement with no pinpoint has no provision row, so a clause citing it stays withheld). `/draft` writes it after `/legal-research` relays that provision's result, never from the session's own knowledge: `currency_status` the relayed value, `checked_on` the date it was relayed, `current_to` the consolidation's "current to" date (`shared/statute-currency.md` leg 3), `amended_on` the effective date of the newest amendment to the provision that took effect after `current_to` (NULL only when the relayed result shows none), and `amendment_checked_on` the date that amendment was checked against the provision. While such an amendment is not yet checked the value is `'amendment-unchecked'` (in force, an unconsolidated amendment not yet checked); a CHECK refuses `'current'` without `current_to`, and while `amended_on` is set and `amendment_checked_on` is not. Write it as an upsert, `INSERT INTO provision_currency (...) VALUES (...) ON CONFLICT (authority_id, provision) DO UPDATE SET ...`. A rename of the authority deletes its rows (`clear_provision_currency_on_rename`), so each provision is checked again for the enactment as now named. The `terms` projection withholds an implied clause naming an enactment whose own result is `'current'` while its statement's provision has no `'current'` row, and the tag names the provision: `[currency: Rule 8-1 amendment-unchecked]`, `[currency: s 6 unchecked]`.
- `verification='verified'` needs a research-agent return; `/verify-law` alone never licenses it, and the verified write snapshots the pair (`scrutinized_authority_id`, `scrutinized_pinpoint`, `scrutinized_excerpt`). `'failed'` is that return's negative half, its finding in `doubt` (CHECK-required), never reset by an edit. `'settled'` (v47) is the practitioner's confirmed close over a finding (`settled_on`, `settled_note` and the `scrutinized_*` snapshot, CHECK-required), counting as support and printing on the filed face by counsel's call; it never reads as verified by the research lawyer. A verified or settled row whose `authority_id`, `pinpoint` or `excerpt` moves off its snapshot returns to `'lead'` by trigger; the proposition's wording never resets anything. Since v61 a move into `'verified'` with no pinpoint is refused by trigger. The writes, and the provenance line a reused statement shows, are `references/scrutiny.md`.
- **`paragraph_statements_of_fact` is a pure link table** — composite primary key (`statement_paragraph_id`, `statement_of_fact_id`), no `id` column of its own, unlike every other table's integer primary key.
- **CHECK-constrained enum columns are closed sets** — see `references/schema.sql` for the exact values (`interviewed`, `kind`/`tier`/`treatment`/`disposition` on `authorities`, etc.). `proceedings.forum` and `filings.kind` are open text since v28 and v29, validated against `/draft`'s knowledge tree rather than by the schema. `parties.role` is deliberately **not** constrained — it is the forum's own vocabulary (Plaintiff/Defendant/Petitioner/Respondent/Applicant/Claimant/Respondent), not a neutral enum (design doc §2.1).
- **Migrations are additive and self-contained.** A future hop in `references/migrations.sql` must end by stamping `db_meta.schema_version` to its own target version — the runner applies the hop's SQL verbatim and does no stamping of its own (see the header comment in that file). The 27 → 28, 28 → 29 and 29 → 30 hops are engine-assisted: 27 → 28 reads `temp.forum_tree_keys`, which the engine builds from `/draft`'s venues index, 28 → 29 is preceded by an engine refusal check, and 29 → 30 reads `temp.filing_layouts`, which the engine builds from `/draft`'s type files and `venue.md` files (see the module docstring of `references/scripts/migrate_engine.py`).
- **Populating a Writing**: `references/filing-checklists.md` is the per-Writing-kind write checklist consumed by `/draft` — which fields each renderer reads, the closed value sets it enforces (e.g. Form 8's `template_key`), and which field values drive the work markers. Keep it in sync with the renderers and `references/schema.sql` it cites.
- **Job writes** (schema v15, ADR 0009): `references/jobs-common.md` and the files "Job and scrutiny operations" names are the write checklist for `tickets`/`ticket_steps`/`ticket_scope`/`ticket_blocks`/`ticket_conflicts`/`seeds`/`ticket_proposals`/`proposal_rejections` — assigning, plan approval, step progress, scope expansion, loose-thread capture, completion, supersession, outlining afresh, release, and shelving and restore. `ticket_answers` has no checklist write: `research_filing__save_answer` writes it, given the job's id, under the same lock guard. Every write there is exempt from the `filing-checklists.md` §8 revision bump — those nine tables carry no revision triggers.
- **Counsel's review records** (schema v27): `references/review.md` holds the `review_approvals` snapshot field list and serialization (the one definition the renderer's 🧐 predicate and the approval writer share), the latest-approval read, and, from Phase 7 of the practitioner-review plan, the write idioms. Both tables are revision-exempt and `review_approvals` is append-only.
- **On-the-fly paragraph revision** (schema v57): `references/paragraph-revision.md` holds the revisable text columns (the six reviewed types, a rhetorical paragraph, and a per-Writing order override), how a mockup paragraph is found, the foreign-scope read, the one-script write (the guarded substance `UPDATE` and the `paragraph_revisions` audit `INSERT` together) and its confirm-read, and (§6) the fact move: swapping two Part 2 facts on a Writing's form, recorded with `entity` `'filing_facts'`, `field` `'ordinal'`, `choice` `'move'` and the ordinals as text. `paragraph_revisions` is revision-exempt and append-only.
- **Locating an authority's own text** on disk, read-only: `references/locate-authority.md`.
- **`documents.file_path`** is written in the stored form, relative to the matter root with backslash separators. Re-pointing it after a file moves: `references/document-paths.md`.
- **The rules position and serve log** (schema v73, rules-DAG spec §4.5–§4.8): four process-state tables with no revision triggers, written only by `rules__move`, `rules__branch` and `rules__provisional` and read by them and `rules__lifecycle`; never write them with `drafting_data__execute`. Paths are node ids, root first, joined by spaces, and every timestamp is local `YYYY-MM-DDTHH:MM:SS`.
  - `session_position` (`session_token`, `branch`, `path`, `session_facts`, `in_force`, `updated_at`), keyed (`session_token`, `branch`): `branch` is `'main'` or the label of the one open side branch, `session_facts` the kept `unattended` and `host` as JSON, and `in_force` the rules the branch's last block left in force, as JSON `[[rule_id, [conditional facts]], ...]`. No row exists before a session's first move.
  - `job_position` (`job_id` → `tickets.id`, cascading on delete, `last_in_bounds_path`, `went_out_of_bounds_to` → `out_of_bounds_visit.id`, `updated_at`): the held job's latest in-bounds path, served to a session that takes the job over, and the visit that took its holder out of bounds since, if any.
  - `rule_served` (`id`, `rule_id`, `node`, `path`, `session_token`, `served_at`, indexed on `rule_id`): one row per rule whose text a move or branch sent. A rule is verified once two distinct session tokens were served it from its current node.
  - `out_of_bounds_visit` (`id`, `session_token`, `from_path`, `turn_summary`, `provisional_rules`, `visited_at`): one row per move onto the map's out-of-bounds node, with the path left. `turn_summary` and `provisional_rules` stay NULL until `rules__provisional` writes them, once per visit: the summary as given, and the rules-improviser's rules as JSON `[{id, door, act, text}, ...]`.
- **Board attachments** (schema v67, ADR 0042): a client letter's folder and a reply's file, which are not Writings, each attach to one Job Board by a `board_attachments` row holding only the board and the path. Attach when the draft is first saved, on the board the practitioner names, the default being the board of the Writing the session holds (a matter with no proceeding gets a forum-less one first); move to another board of the matter, or detach, only when the practitioner asks; all three are `drafting_data__execute` writes. A Writing with a draft attached is not retired until each attachment is moved or detached, as the practitioner says. Idioms, the board read and the guards: `references/filing-checklists.md` §14 and §11.
- **Statement of goals** (no schema change, 2026-10-14): one `db_meta` row per Job Board, never a table. Key `board_goal:filing:<id>` for a Writing's board or a Job Board with no Writing, `board_goal:proceeding:<id>` for a pre-filing proceeding's board. Value: JSON `{description, statement, status, approved_at, session_token, updated_at}`: `status` one of `confirmed`, `inferred`, `declined`; `approved_at` set only for `confirmed`; `statement` null only, and always, when `declined`; `description` null means the board's default. Timestamps are local `YYYY-MM-DDTHH:MM`. Job process state: `db_meta` has no revision trigger, so it moves no revision and archives no mockup. Written only by `drafting_data__set_board_goal`, never by `drafting_data__execute`. A row whose board no longer exists (its `filings` row gone, or its proceeding now has a Writing) is never read, since no section is built for it, and the next write removes it. Every Job Board page draws it as the card labelled Goal, above the Completion Criteria card, which keeps its own name.
- **Viewed thumbnails** (no schema change, 2026-10-22): one `db_meta` row per Job Board, never a table. Key `board_viewed:filing:<id>` or `board_viewed:proceeding:<id>`, by the board's survivor (docs/ADRs/0010). Value: a JSON array of item keys, most recently viewed first: `view:<page name>` for a view page, `doc:<filing id>:<file name>` for a Writing's document by its render manifest's file name. It holds an order and no time. Written only by `drafting_data__record_viewed`, never by `drafting_data__execute`, and it moves no revision. Every Job Board page draws its viewed thumbnails first, in this order, then the never-viewed ones, and dashes a view page's tile only while it has never been viewed. A retitle that renames a document's file drops its key, so its tile reads never viewed again. A merge does not carry the absorbed board's row over.
- **Procedural and material facts** (schema v77, docs/ADRs/0011): a fact that speaks to the litigation process itself (a filing, a service and its method, an order made, correspondence about a procedural matter) is procedural, and every other fact, the ones that speak to the merits of a claim or defence, is material. Whenever a session records a fact, it decides which by reading the fact and its source, and for a procedural fact sets `facts.procedural_on` to the date the step happened, taken from the source: `UPDATE facts SET procedural_on = '2026-03-04' WHERE id = ?`. A material fact keeps it NULL. A procedural fact whose date the source does not give stays material and the session asks the practitioner for the date. The practitioner's correction moves a fact: set the date to put it on Procedural History, clear it (`SET procedural_on = NULL`) to put it on Material Facts. When the practitioner asks to sort a board's facts, the session reads every fact its Writings use (`filing_facts`, `submission_facts`) and sets the date on each procedural one in one `drafting_data__execute` script, then reports which facts it moved. All are `drafting_data__execute` writes, and each moves the revision, so both pages are rewritten. The date records a step that happened: never compute, store or show a deadline or a time remaining from it, and never pass it to a deadline tool (`shared/deadline-isolation.md`). How each fact is proven is unchanged: its court record, admissions and statements of fact.

## Configuration

Unlike `practice_data__*` (one fixed `practice.db`) or `matter_data__*` (a `probanda.json` pointer that exists to survive a matter-folder rename and heal a legacy layout), the `drafting_data__*` backend takes no path convention of its own by design — it is a generic connection-discipline primitive over whatever absolute `db_path` it is handed (`source/lawyer/mcp/src/submission/backend.ts`). **Computing that path is this skill's job, once per call, with no persisted pointer of its own** — there is no legacy state to heal for a brand-new schema.

This skill's choice: the drafting database lives **in the matter's per-matter matter-data folder** — the same location `/matter-data` already uses for `main.sqlite` / `law.sqlite` / `privileged.sqlite` (the matter's own `0. CASE DATA\`, or `0. CASE DATA\<matter_id> <short_name>\` under the firm root for a matter not yet relocated, resolved via `probanda.json`'s `case_data_dir`) — as a fourth file, `submission.sqlite` (the file name predates the skill's rename and stays). This reuses the established per-matter resolution rather than inventing a second one; the design doc leaves this open, specifying only "in the matter workspace" (design doc §1).

If no matter folder is connected, ask its exact path, request only it, not a parent or firm root. To compute `db_path`: prove the current matter folder live through a host-namespace surface (list it, require a known child such as `4. LAWYER BRIEF`) — never trust a stored breadcrumb — resolve `case_data_dir` the same way `/matter-data` does, and append `submission.sqlite`. `drafting_forms__open_session` is this rule's executable form ([#591](https://github.com/Mharbulous/CoClerk/issues/591)): it performs exactly these steps host-side from the matter folder's absolute path, and this section stays the rule's owner. Only its pointer read is read-only: the call also migrates a database behind the bundle's schema on its own initiative (with a copy-aside backup), writes the matter's Litigation Strategy page and Job Board pages, and can return counsel and parties refusals. So it is a session-entry call, never a way to look up a path for a tool that does not open the database ([#1427](https://github.com/Mharbulous/CoClerk/issues/1427)). A `C:\…` string is not a path inside the Cowork sandbox's Linux guest — treat any listing of it there as unproven, never as evidence of absence.

**Render output** ([#297](https://github.com/Mharbulous/CoClerk/issues/297), location decided in [#324](https://github.com/Mharbulous/CoClerk/issues/324), presentation-copy location updated by `docs/adr/0008-mockup-presentation-copy-relocated-to-draft-folder.md`): `drafting_forms__render` and the background render job write mockups under `<dirname(db_path)>/mockups/Filing <id>/` (keyed by Writing id since [#1317](https://github.com/Mharbulous/CoClerk/issues/1317), so a retitle never moves it; ADR 0017's 2026-10-01 amendment), with revision-triggered archive copies in an `archive/` folder beside them — beside `submission.sqlite` in the matter-data folder, so for a new or relocated matter under the matter's own `0. CASE DATA\mockups\` (`docs/ADRs/0013-per-matter-case-data-inside-the-matter-folder.md`), not in the draft folders (`4. LAWYER BRIEF\…` or `0. DRAFT\…`). They are written and reached host-side through the `drafting_data__*`/`drafting_forms__*` tools. The location is deterministic from `db_path`, so it takes no output-root parameter; the practitioner opens the returned paths directly. A *session* never reads these files itself, so `drafting_forms__render` returns each document's `markdown` in its response ([#337](https://github.com/Mharbulous/CoClerk/issues/337)) — the tool response is host-side, so no session file read is needed. `bootstrap` returns no markdown: it renders nothing. `/draft` step 6 has `render` write a presentation copy into the mounted matter workspace's draft folder (`0. DRAFT\<CODE> <filing folder>\…`, no date prefix, ADR 0013) by passing `presentation_dir` (ADR 0012), to present a file card. That copy is a disposable projection — written host-side by the server, overwritten on every re-render, and read back only when a document is too large to return inline; the mockup beside the database remains canonical. Both tools also take optional `client_name`/`client_no`/`matter_no` frontmatter values — no schema column backs client identity, so when omitted `proceedings.matter_reference` stands in for all three.

**The board-first bootstrap's files** (ADR 0017), each named once here:

- **`render-manifest.json`**, one beside each Writing's mockups: the render stamp and each mockup's hash. `render` and bootstrap's `render_state` compare against it. The `filing-checklists.md` §8 revision bump is what moves the stamp.
- **`Litigation Strategy.html` and the Job Board pages**, at the top of the matter's `0. DRAFT*` folder: one self-contained `Litigation Strategy.html` per matter (ADR 0021), and one `Job Board <id>.html` per live Writing, one under the same name per open Job Board with no Writing, and one `Job Board - proceeding <id>.html` per pre-filing proceeding, named by id so a retitle never moves a page (ADR 0033 and its 2026-10-05 amendments). The Litigation Strategy page: the matter's open to-dos lead it, read server-side through `/practice-data`'s `open-tasks` by `matter_no`, each with its BF date as a plain date and never its deadline, and with its Writing's line beneath it when its Writing reference resolves. Below them, one line per Writing and pre-filing proceeding: name, lifecycle state, mockup status, jobs in progress. A Job Board page holds one board's section, its Writing's or its proceeding's, and a merged board's page every board merged into it, drawn as one board, named by the survivor's id even when the survivor is retired, while any of its sections is live (`docs/ADRs/0010-job-boards-organized-by-goals.md`); each page is named by its id, so a retitle never moves it; a retired Writing has none; a General Job (a job with no Writing) is on every Writing's page in its proceeding, its card tagged General, and never on the page of a Job Board with no Writing, which holds only the jobs and loose threads that name it and has no view page. Its Attached lane lists the drafts attached to the board (schema v67), each by name and stored path in plain text, never a link, with a client letter's review status read from its review draft's first line at the write, a path with nothing at it shown as missing, and one that cannot be read shown as unreadable with its error code. Beside them, each view page per board holding a live Writing, `<page name> - Job Board <id>.html`, reading every Writing on the board (`shared/html-pages.md`; ADR 0033, 2026-10-07 amendment), under its own marker. All are written by `bootstrap` given `draft_dir`, by `open_session` (through its opening render, or its own page write when nothing opens), by every `render` given `draft_dir` or `presentation_dir`, a Writing's or a proceeding's, and by the background render job after each Writing. Each write is atomic (a temp file, then a rename over the page). A page is overwritten only when it carries that page's marker; a file at any page's path without it fails the render, naming it, before any page is written. Never archived and never copied beside the database. A write moves every old page file the generator wrote in the `0. DRAFT*` folder and its immediate subfolders (a retired Writing's page, a proceeding's once it has a Writing, a page under an older name, the old single `Job Board.html`, a numbered copy, a per-Writing or `Pre-filing proceeding <id>` board copy, a `Matter Board.html` or `Work Board.html`) into the matter's `TRASH`, reported as `moved_to_trash`, any it could not move as `trash_skipped`.
- **`matter-pages-state.json`**, in the `mockups` folder beside the database: what `board_changed` and `board_moves` compare against (the last section a foreground render reported for each Writing or proceeding), and the last to-dos read, which the background job reuses for the Litigation Strategy page.
- **`workboard-status.js`**, beside the Litigation Strategy page: the background render job's progress, which only that page reads. Written temp-then-rename.
- **The job's lock and status mirror**, host-local under `%LOCALAPPDATA%\Coclerk\submission-locks` beside the data lock (`render-job.lock`, `render-job.status.json`), outside the synced matter tree. The mirror is what `background_job` reports.

A session never reads any of these files itself (#324): job status arrives as `background_job` on the tool responses. The pages are human interfaces generated from the databases, never read, staged or screenshotted by a session: `shared/html-pages.md`.

**The Job Board** is one page per board: a live Writing's, an open Job Board with no Writing's or a pre-filing proceeding's, and a merged board's page draws every board merged into it as one board, each job naming its Writing (ADR 0033, 2026-10-05 amendment; `docs/ADRs/0010-job-boards-organized-by-goals.md`), and no board is written beside the database or in a presentation folder. A session reads a section only as `board_summary` and `drafting_forms__board_card`, never the page (`shared/html-pages.md`).

**The bundle states what schema it can read** ([#812](https://github.com/Mharbulous/CoClerk/issues/812)). `source/lawyer/mcp/scripts/bundle.mjs` reads `TARGET_SCHEMA_VERSION` out of `references/scripts/migrate_engine.py` at build time and bakes it into the bundle, the same way it bakes the build stamp. A migration is applied only when its target is at or below that baked number, so a hop that has landed in this tree but has not been packaged cannot reach a client matter database. Before this, every ahead-of-bundle guard compared the database against `TARGET_SCHEMA_VERSION` read live from this tree — the same file a pending migration comes from — so the ceiling rose with every hop and the guard could never fire. Matter L8145 was migrated to v26 by a read-only baseline call and then rendered `no such column: s.dropped_on`.

Two environment variables sit behind it, both read from the server's environment and therefore settable only by restarting the server — never by a tool argument, which the very session being guarded could set:

- `COCLERK_SUBMISSION_ALLOW_UNBUILT_SCHEMA=1` — the deliberate escape hatch for in-progress schema work. Migrations past the bundle's ceiling are applied anyway, and every response says so. **Every database migrated this way stays unrenderable until a matching bundle is built and installed.**
- `COCLERK_SUBMISSION_BUNDLE_SCHEMA_VERSION` — a test seam that states the ceiling when there is no baked one. It loses to the baked value, so on a real bundled server it does nothing.

Every `bootstrap` and `open_session` response carries `schema_target_version`, `bundle_schema_version` and `schema_source_ahead`, with a `schema_note` when they diverge, whether or not a migration was attempted. When a migration is due but would exceed the ceiling, `migration_withheld` is true, `migration_required` is false, and nothing is migrated.

When the bundle cannot serve the database (`migration_withheld` or `bundle_outdated`), the note names the server's build and plugin version and gives one next step, by case. If the plugin installed on disk is a newer build than the one running, the app was not restarted after an update: fully restart it. If the migration source or the database is ahead of the bundle: run `/lawyer:suggestion` naming the note, then fully restart the app once a plugin update arrives. Relay that step as given; never call `drafting_data__migrate` for it. `scripts/check_plugin.py` (bundle-schema-ceiling) fails while the migration source's target differs from the bundle's baked version, so a split cannot ship unnoticed.

## Anti-Patterns

- **Any other skill embedding SQL, resolving the drafting DB path, or opening a connection directly.** All access goes through the `drafting_data__*` / `drafting_forms__*` tools via this skill.
- **Rendering a `reserved` row, or a `killed` row, on any filed face.** Held-in-reserve/undisclosed material by design (ADR 0004); a killed submission or authority (schema v16) is reserved by construction and additionally must never resurface as a "new" candidate in a later drafting or research pass. Both are renderer defects, not business decisions to make per-call.
- **Treating the design doc's table list as informal.** `references/schema.sql` is the literal contract; if a change is needed, change `references/migrations.sql` (a new hop, never an edit to the 0 → 1 hop) and regenerate `references/schema.sql` from a fresh migration.
