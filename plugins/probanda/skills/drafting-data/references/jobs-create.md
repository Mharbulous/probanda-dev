Read when: an outlining session writes the jobs the practitioner selected at the closing read-back or picked from the Proposed lane (§3), the practitioner asks to rework a `queued`, unshelved job (§3a), or the practitioner pulls Proposals from the `proposed` lane onto the board by a group, a filter, a submission or "take the next" (§3e), or a holding session spins off blocker jobs for the job it holds (§3f).
Any §N not in this file: find it in SKILL.md, "Job and scrutiny operations".

## 3. Create (outlining only)

Only in an outlining session (Branch B's outlining interview, or a `kind = 'charting'` job's own work), and only for jobs the practitioner outlined and selected at the closing read-back, and in the fixed-text creates with sections of their own: §3b to §3e, §3f, §3g and §14. **Two calls, not one** — the job's `id` is autogenerated, and nothing after the first `INSERT` in the same `execute` script can safely name it: `last_insert_rowid()` only ever holds the *most recent* insert's own rowid, so a second child `INSERT` in the same script (e.g. the second `ticket_steps` row) would see the first child's rowid, not the job's — silently attaching a step to the wrong job, or failing the `ticket_steps.ticket_id` foreign key if no job happens to share that id.

**Read first — the priorities already queued on this Writing.** `priority` is set relative to the jobs already queued there, never guessed: the Ready queue is `priority` descending then `id`, which no session reorders. No session asks the practitioner for an order.

```sql
SELECT id, priority, title FROM tickets
  WHERE proceeding_id = 1 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL AND (filing_id = 1 OR filing_id IS NULL)
  ORDER BY priority DESC, id;
```

Every job of the batch takes one below the lowest `priority` returned, or the schema default, `0`, when no row returns, so the new jobs queue behind every job already queued, in the order written by `id`. Order between jobs that depend on each other comes from their dependency edges, never from `priority`: the board holds a blocked job out of Ready until its blocker is done. Only where the practitioner stated an order unasked is a job placed otherwise: one they want worked before everything queued takes one above the highest returned; one that belongs between two takes a value between theirs, which needs the rows beneath it renumbered in the same script when those two are adjacent. Proceeding-scoped jobs (`filing_id IS NULL`) are included because they queue on this Writing's board too (§11). `rejected_at IS NULL` excludes a shelved queued job because it sits in Shelved, not the Ready queue (design §10's Job list precedence), so its priority anchors nothing.

**Call 1 — create the job:**

```sql
INSERT INTO tickets (proceeding_id, filing_id, title, intent, kind, priority, billing_anchor, created, session_proposed, created_by)
  VALUES (1, 1, 'reply to their attornment argument', 'I want to reply to their attornment argument once the memos are audited.', 'work', 4, 'L8212|attornment defeats the stay', strftime('%Y-%m-%dT%H:%M', 'now', 'localtime'), 0, 'sess-a1');
```

`session_proposed` is `1` only when the `title` and `intent` are a session proposal the practitioner approved word for word, and `0` otherwise.

`created_by` is this session's own `session_token` (§1; `'sess-a1'` stands in for it), written by this section's two creates, the plain one above and the guarded one below, and by no other create. It is what lets this session later be assigned one of the jobs it created, and only those (§4).

Outside five fixed-text exceptions — §14's gate job, the fast-path job, §3b's stock bundle jobs, §3c's counsel's review jobs and §3d's scrutiny review jobs — `title`, `intent` and every `ticket_steps.text` written here are the practitioner's own words as selected at the closing read-back, or a proposal the session showed in its visible reply that they approved word for word with a bare yes, written with `session_proposed = 1`, and never the session's words unapproved — `intent` one sentence of theirs or of the approved proposal, verbatim (for a one-step job it is its only step, quoted at dispatch, so nothing the session composed may stand in it unapproved), `title` an unbroken run of their own words from one answer (the text typed after a slash command is one) or of the approved proposal, no word swapped or moved; the `title` literal is the selected card's value. How the work divides into jobs and steps is the session's call; the words in them are the practitioner's or a proposal they approved word for word. A fast-path job's title and intent are the Proposal's title, `<work name>: <item>`, and its single step is its key type's step frame (`filing-checklists.md` §6a) on the Proposal's item, so that the step names the work rather than restating the title. All three are fixed text from the record and not the session's words, written with no closing read-back because the pick is the practitioner's: a Proposal picked and left unedited is its approval. A stock bundle job's strings are §3b's, a counsel's review job's are §3c's, and a scrutiny review job's are §3d's, on the same terms.

**A job outlined from Proposals takes the guarded create instead of the plain `INSERT` above** — the fast-path job always, and a hand-worded job outlined from Proposals too. The job row survives only when no `queued` or `wip` job with `rejected_at IS NULL` already holds any of its keys. Call 1 is the plain `INSERT ... VALUES`, followed in the same script by a `DELETE` of that row whenever a live job holds any of its keys, every key named in the `IN` list:

```sql
INSERT INTO tickets (proceeding_id, filing_id, title, intent, kind, priority, billing_anchor, created, created_by)
  VALUES (1, NULL, 'Note up: Smith v. Jones, 2023 BCCA 182', 'Note up: Smith v. Jones, 2023 BCCA 182', 'work', 4, 'L8212|attornment defeats the stay', strftime('%Y-%m-%dT%H:%M', 'now', 'localtime'), 'sess-a1');
DELETE FROM tickets WHERE id = last_insert_rowid()
  AND EXISTS (
    SELECT 1 FROM ticket_proposals p JOIN tickets t ON t.id = p.ticket_id
      WHERE p.proposal_key IN ('note-up:authorities:5') AND t.status IN ('queued', 'wip') AND t.rejected_at IS NULL AND t.deleted_at IS NULL);
```

Keep the `INSERT` then `DELETE` shape: `last_insert_rowid()` is safe here only because the `DELETE` directly follows the job's own `INSERT`. The new row has no `ticket_proposals` rows yet, so it can never match its own guard.

**Call 2 returning no row is the signal** that the key is already held: nothing was written, and the rest of that job's calls are skipped. Take the holder's number from `drafting_forms__board_card` with `key`, after a re-render (the live job it prints, or the Proposed line's `held by #N`), say "already a job: Job #N" in one line, and go on with the rest of the batch. There is deliberately no unique index: a `completed` job keeps its rows, and a second job on the same key after completion is legitimate, so the guard looks only at `queued` and `wip` holders. Without the guard, a fast-path duplicate would be silent, because its Proposal is hidden behind the first holder and nothing on the board shows the second.

**Call 2 — recover its id**, the same single-practitioner trust model as the confirm-read after assigning (§4): the just-written `title` and `created` stamp together are specific enough in practice; if more than one row matches, stop and ask rather than guessing which is the new one.

```sql
SELECT id FROM tickets WHERE proceeding_id = 1 AND title = 'reply to their attornment argument' ORDER BY id DESC LIMIT 1;
```

After a guarded create the recovery takes a different shape, because a fast-path title recurs: an older job on the same key, now completed, carries the same `<work name>: <item>` title, and the plain shape above would return it when the guard wrote nothing. The just-created job is the one queued job with that title that holds no `ticket_proposals` rows yet, since those rows are written after this call and an older job on the same key keeps its rows. No `LIMIT`, so that a second match shows and stops the session:

```sql
SELECT id FROM tickets t WHERE proceeding_id = 1 AND title = 'Note up: Smith v. Jones, 2023 BCCA 182' AND status = 'queued' AND deleted_at IS NULL
  AND NOT EXISTS (SELECT 1 FROM ticket_proposals p WHERE p.ticket_id = t.id);
```

No row is the signal above. One row is the new job. More than one: stop and ask.

**Call 3 — the job's children**, every one of them using that recovered id as a literal (here, `2`) — steps and scope reference the job row just written; blocks/conflicts reference other jobs that must already exist:

```sql
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 1, 'Audit the exhibit list');
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 2, 'Reconcile against the disclosure log');
-- one INSERT per step, always at least one, ordinal 1, 2, 3... -- every one uses the SAME literal
-- job id recovered in call 2, never last_insert_rowid() (see above).

INSERT INTO ticket_scope (ticket_id, entity, entity_id) VALUES (2, 'facts', NULL);
-- entity is any table name as spelled in schema.sql, substance or join.
-- entity_id NULL means the whole table within this job's filing/
-- proceeding -- what a job that CREATES rows needs, not one that only
-- edits existing rows.

INSERT INTO ticket_blocks (blocker_id, blocked_id) VALUES (1, 2);
-- blocker_id must already exist and complete first.

INSERT INTO ticket_conflicts (a_id, b_id) VALUES (1, 2);
-- canonical order required by the CHECK -- always the smaller id first.
```

`billing_anchor` (`kind = 'work'` only — the CHECK rejects a work job with none): derive per `shared/live-issue-test.md`, written `<matter>|<live issue or deliverable>`, asked only when it cannot be inferred from the Writing/proceeding already in hand. A job outlined from a Proposal is never asked: it copies the anchor every work job on the open Writing carries, else takes `<matter>|<that Writing's title>`. A `kind = 'charting'` job carries no `billing_anchor` — outlining itself decides what gets billed once it produces `work` jobs.

`filing_id` **on a job outlined from a Proposal** follows the row the Proposal is keyed on, not the Writing being worked. Nearly every keyed row is proceeding-scoped substance shared across that proceeding's Writings, so the job defaults to proceeding scope — `filing_id` NULL — and shows on every Writing's board in the proceeding. Two keyed rows are the Writing's own and default to its id: the venue form's pointer rows (`filing_facts` / `filing_submissions` / `filing_orders`) and the `filings` row itself. The practitioner may say otherwise in the interview, and their answer wins over either default. Its scope rows are the key's own `(<table>, <id>)` and `(<table>, NULL)` for each other table, created or edited, that the work's clearing action writes, read off its key type's row in `filing-checklists.md` §6a ("Clearing action also writes"), never inferred. This rule governs only a job outlined from a Proposal; one the practitioner outlined from their own words takes the scope their answers give it.

**Consuming a loose thread not yet outlined** (the practitioner chose to outline it now):

```sql
UPDATE seeds SET charted_into = 2 WHERE id = 1;
```

Run this once the job it became now exists (its recovered literal id — call 2 above); it removes the loose thread from the Job Board's "Loose Threads" section (the query there filters `charted_into IS NULL`).

**Recording the Proposals a job was outlined from** — the same shape as the loose-thread consumption above: its own statement, after call 2, on the recovered literal id, never `last_insert_rowid()`. One row per key the job was outlined from; one job may hold several keys, and a merged job does:

```sql
INSERT INTO ticket_proposals (ticket_id, proposal_key, item)
  VALUES (2, 'note-up:authorities:5', 'Smith v. Jones, 2023 BCCA 182');
INSERT INTO ticket_proposals (ticket_id, proposal_key, item)
  VALUES (2, 'authority-excerpt:statements_of_law:12', 'Smith v. Jones, 2023 BCCA 182 — the implied-term test');
```

`proposal_key` is the key the render put on that Proposal, copied character for character out of `drafting_forms__board_card`'s Proposed lane (its detail line's `key:`) — never recomposed from a slug and a row id. `item` is NOT NULL and takes **that key's own item text as that card printed it at the write (its detail line's `item:`), without any count** — the keyed row's identity, never the job's title. So a job the practitioner merged from two Proposals and titled in their own words carries a different `item` on each row and a title matching neither. There is no `marker` column: a glyph shift on the keyed row is not something this record can notice, and deliberately so.

These rows are what hide their Proposals from `drafting_forms__board_card`'s Proposed lane while the job is `queued` or `wip` and unshelved, so a key copied wrongly hides nothing and its Proposal shows again beside the job. They are written only for a job outlined from Proposals — a job the practitioner outlined for the same work in their own words carries no conversion record and leaves its Proposal showing, which is a visible duplicate rather than a silent one.

## 3a. Outline afresh (outlining only)

Reworking an existing job in place, at the practitioner's request, where `status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL`. It is outlining, so the session that does it is never assigned a job (§4) and never does it inside an assigned job's own session — §5's Change path is the assigned job's route and is untouched by this.

**The guard rides every statement in the script, not only the `tickets` update.** `drafting_data__execute` runs the script in one transaction and rolls back on an exception; a guarded `UPDATE` or `DELETE` that matches zero rows is not an exception, so an unguarded `INSERT` beside it would commit alone and leave the job half-rewritten. Each statement therefore carries the job's still-queued, unshelved state itself — as its own `WHERE` clause on the job row, as an `EXISTS` subquery on a child delete, and as `INSERT ... SELECT` on a child insert:

```sql
UPDATE tickets SET title = 'audit the exhibit list against the disclosure log', intent = 'I want the exhibit list audited before the reply goes out.', priority = 6
  WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;

DELETE FROM ticket_scope WHERE ticket_id = 42
  AND EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);

INSERT INTO ticket_scope (ticket_id, entity, entity_id)
  SELECT 42, 'statements_of_law', 12 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
```

`title` and `intent` are the practitioner's own words from this interview, on §3's terms — the session decides nothing about the wording here either.

**A `priority` set between two adjacent jobs renumbers the rows beneath it** (§3), and here those rows are *other* jobs, so their `UPDATE` cannot lean on job 42's own `WHERE` clause. It carries job 42's still-queued, unshelved state as an `EXISTS` of its own, the same shape a child delete uses — otherwise the renumbering commits alone when the outline itself matched nothing, and the Writing's queue is left reordered around a job that was never rewritten:

```sql
UPDATE tickets SET priority = 5 WHERE id = 11
  AND EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);
```

**Scope rows may be replaced, not only appended.** The job has no holder, so no write is in flight against a row this deletes — the opposite of §7, which appends for a job already assigned and never deletes.

**The steps and their approval travel together or not at all.** If the practitioner confirms the read-back step list unaltered — nothing reworded, reordered, added or removed — `ticket_steps` and `plan_approved_at` are left alone and every `done_at` on those steps survives. Any alteration at all deletes and recreates the steps and clears `plan_approved_at`, in the same script:

```sql
DELETE FROM ticket_steps WHERE ticket_id = 42
  AND EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);
INSERT INTO ticket_steps (ticket_id, ordinal, text)
  SELECT 42, 1, 'Audit the exhibit list' FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
INSERT INTO ticket_steps (ticket_id, ordinal, text)
  SELECT 42, 2, 'Reconcile against the disclosure log' FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
UPDATE tickets SET plan_approved_at = NULL
  WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
```

A step list or title the session proposes, rather than one the practitioner words, is presented and adopted by the ceremony in `shared/paralegal-posture.md` section 3.

**Edges may be added or deleted, on either side** — unlike §3, which only ever creates them:

```sql
DELETE FROM ticket_blocks WHERE blocker_id = 7 AND blocked_id = 42
  AND EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);

INSERT INTO ticket_blocks (blocker_id, blocked_id)
  SELECT 9, 42 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL
    AND EXISTS (SELECT 1 FROM tickets WHERE id = 9 AND status <> 'superseded' AND rejected_at IS NULL AND deleted_at IS NULL);

INSERT INTO ticket_conflicts (a_id, b_id)
  SELECT 11, 42 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL;
```

**A newly named blocker must be one the job can actually wait on** (design §11): a fresh outline that names a superseded or shelved blocker drops the job straight back into Blocked behind a dead blocker, the very state the outline was run to leave. So the blocker-side insert proves job 9 too — that it exists, and that it is not superseded, shelved or deleted. A `queued`, `wip` or `completed` blocker all pass: completion is what the blocked job is waiting for, and a blocker still in progress will reach it.

`ticket_conflicts` still takes the canonical order the CHECK demands (§3), smaller id first, whichever job is being outlined. An edge whose **blocked** side is another job is different: it changes what that job waits on, so that job must be queued and unshelved too, and the script proves it rather than assuming it from the board:

```sql
INSERT INTO ticket_blocks (blocker_id, blocked_id)
  SELECT 42, 11 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL
    AND EXISTS (SELECT 1 FROM tickets WHERE id = 11 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);
```

**What never changes, whatever the practitioner says:** `proceeding_id`, `filing_id`, `kind`, `created` and `billing_anchor`. Accepted cost: a job outlined afresh away from the work its Proposal named still hides that Proposal while it is queued. The marker itself still shows on the mockup, so the work is not lost.

**The job's `ticket_proposals` rows change in two ways only** (the 2026-09-21 design §4.6 and §4.8). **Refresh `item`** on each key the job keeps whose item now reads differently, so a reworded item is not reported each time the job is assigned. It runs only after the practitioner has been shown the old and new text and has confirmed; without that confirmation the old `item` is the evidence the column exists to keep, and it is left alone. The new text is the key's current item as the job's card (`drafting_forms__board_card` with `jobs`) prints it now, the quoted text in that key's `(now: <glyph> "<current item>")` on the job's `keys:` line, unquoted and without any count, on §3's terms:

```sql
UPDATE ticket_proposals SET item = 'Brown v. Green, 2024 BCSC 77'
  WHERE ticket_id = 42 AND proposal_key = 'note-up:authorities:5'
    AND EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND status = 'queued' AND rejected_at IS NULL AND deleted_at IS NULL);
```

**Drop the dead keys** where the outline afresh was entered as "keep it" from a pre-claim check (the 2026-09-21 design §4.8), by §5's `DELETE` shape with this section's guard in place of §5's. Never otherwise.

Then run the confirm-read (§2) — the one read that distinguishes a script that landed from a guard that matched nothing.

## 3e. Intake

`/draft`'s intake writes Proposals in the `proposed` lane, read off `drafting_forms__board_card` with `lanes: ["proposed"]`, as fast-path jobs, on the practitioner's word and with no further act. It never runs at an Opening of its own accord, so a bare Opening writes nothing, and it never runs in an unattended run. It takes only `- <glyph> <title>` lines whose detail line reads `lane: proposed`, never a `lane: held by #N …` line nor anything under `## Shelved`, and it runs on one of three triggers, each of which chooses the batch:

- **A group or filter the practitioner names** ("all the exhibit pinpoints", "every note-up", "everything for Submission 3"): the lines their words pick out, by key type (§6a's work, as they name it) or by a submission's rows (below). Where the words fit more than one reading, ask which, and write nothing until they answer.
- **"Take the next", with Ready empty:** one job's worth. The first line in the lane's printed order whose key is never-held (below) and whose key type `filing-checklists.md` §6a does not mark as the practitioner's own, together with every line that would join it in one job (Grouped Proposals and One title, one job, below).
- **A task typed with the invocation that names a submission:** the lines keyed on that submission's rows (below). A typed task that names no submission converts nothing.

A single Proposal named is not intake: it is the fast path (§3), picked by the practitioner. Proposals of a type in the group table (Grouped Proposals, below) are written together as one job, and so are lines that print one title (One title, one job, below); every other line is its own job. Intake, like §3c's pair and §14's gate job, is a fixed-text create and not outlining: it writes no `created_by`, so §4's rule for a session that created jobs does not bind the intaking session when it then assigns a job. Each job's three calls run before the next job's Call 1, so that Call 2 sees only the job just written.

**The priority read** is §3's read, run once for the batch. Every intake job takes one below the lowest `priority` returned, or `0` when no row returns. The batch is written in the Proposed lane's printed order, so at equal priority it keeps that order by `id`, behind every job already queued.

**Call 1, per Proposal**, is the fast path's shape with a stricter guard:

```sql
INSERT INTO tickets (proceeding_id, filing_id, title, intent, kind, priority, billing_anchor, created)
  VALUES (1, NULL, 'Note up: Smith v. Jones, 2023 BCCA 182', 'Note up: Smith v. Jones, 2023 BCCA 182', 'work', -1, '<matter>|attornment defeats the stay', strftime('%Y-%m-%dT%H:%M', 'now', 'localtime'));
DELETE FROM tickets WHERE id = last_insert_rowid()
  AND EXISTS (SELECT 1 FROM ticket_proposals p JOIN tickets t ON t.id = p.ticket_id
    WHERE p.proposal_key = 'note-up:authorities:5' AND t.deleted_at IS NULL);
```

No status filter, on purpose: intake writes a key only while no job of any status that is not deleted has ever held it. The join to `tickets` leaves out only a deleted job (§10a), whose Proposals return to Proposed and are written afresh, as they were after the delete removed its rows. A key once held stays in Proposed for the practitioner to name through §3's fast path, whose guard looks only at live holders. Without this, a job completed over a marker that still fires would be re-created by every intake.

**Call 2** is §3's guarded-create recovery, with no `LIMIT`:

```sql
SELECT id FROM tickets t WHERE proceeding_id = 1 AND title = 'Note up: Smith v. Jones, 2023 BCCA 182' AND status = 'queued' AND deleted_at IS NULL
  AND NOT EXISTS (SELECT 1 FROM ticket_proposals p WHERE p.ticket_id = t.id);
```

No row: the key was once held, so skip it and carry on. One row: the new job. More than one: two sessions' intakes wrote the same job at the same moment, since an earlier job of this intake already holds its keys by the time the next job's Call 2 runs, and so never matches. Delete them all in one statement and carry on, saying so in one line. The next intake writes the job cleanly, because the key is still never-held. The rows carry no steps, scope or conversion record yet, so no foreign key refuses:

```sql
DELETE FROM tickets WHERE proceeding_id = 1 AND title = 'Note up: Smith v. Jones, 2023 BCCA 182' AND status = 'queued' AND deleted_at IS NULL
  AND NOT EXISTS (SELECT 1 FROM ticket_proposals p WHERE p.ticket_id = tickets.id)
  AND NOT EXISTS (SELECT 1 FROM ticket_steps s WHERE s.ticket_id = tickets.id);
```

The subqueries name `tickets.id` because SQLite refuses a bare alias on the `DELETE` target (`DELETE FROM tickets t`).

**Call 3** is §3's, on the recovered literal id: the job's steps, the scope rows by §3's rule for a job outlined from a Proposal, and the `ticket_proposals` row with the key and item copied from the card. `billing_anchor` and `filing_id` follow §3's rules for a job outlined from a Proposal.

The steps come off the card. A note-up of a statute, regulation or rule is done provision by provision, so its card prints a `  step <n>: <text>` line under its detail line for each provision the Writing cites: each pinpoint its statements of law print 📇 on, then each provision cited only in a contention's text. Write one `ticket_steps` row per line, ordinal `<n>`, text the line's `<text>` character for character:

```sql
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 1, 'Note up: Supreme Court Civil Rules, B.C. Reg. 168/2009, r. 9-6(3)');
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 2, 'Note up: Supreme Court Civil Rules, B.C. Reg. 168/2009, Rule 14-1(12)');
```

A card printing `  steps: none` (the Writing cites no provision) gets no step row, the one exception to §3's "always at least one", so that no step restates the title. Every other Proposal not in a group (below) gets one row, ordinal 1, text its key type's step frame (`filing-checklists.md` §6a) with `<item>` replaced by its detail line's `item:` character for character, never its title: a step equal to the title fails `/draft`'s pre-claim check, so the job could never be assigned.

```sql
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 1, 'Find and record the pinpoint in the document: M. Reyes: Overtime for the final week was recorded in the Site Diary.');
```

**The submission's rows.** A task typed with the invocation, or a filter the practitioner names, that names a submission picks the `lane: proposed` lines whose key's table and id, the text between the key's first and second `:` and the id after the second, is a row this read returns. A submission named by its number is the `filing_submissions` row with that `ordinal` on the open Writing; one named by its words is the submission whose `contention` the practitioner quotes; ask when neither picks out one. Here the submission is `3`:

```sql
SELECT 'submissions' AS tbl, id FROM submissions WHERE id = 3
UNION SELECT 'filing_submissions', id FROM filing_submissions WHERE submission_id = 3
UNION SELECT 'facts', fact_id FROM submission_facts WHERE submission_id = 3
UNION SELECT 'statements_of_fact', s.id FROM statements_of_fact s JOIN submission_facts sf ON sf.fact_id = s.fact_id WHERE sf.submission_id = 3
UNION SELECT 'witnesses', s.witness_id FROM statements_of_fact s JOIN submission_facts sf ON sf.fact_id = s.fact_id WHERE sf.submission_id = 3
UNION SELECT 'documents', s.instrument FROM statements_of_fact s JOIN submission_facts sf ON sf.fact_id = s.fact_id WHERE sf.submission_id = 3 AND s.instrument IS NOT NULL
UNION SELECT 'documents', s.exhibit_id FROM statements_of_fact s JOIN submission_facts sf ON sf.fact_id = s.fact_id WHERE sf.submission_id = 3 AND s.exhibit_id IS NOT NULL
UNION SELECT 'admissions', a.id FROM admissions a JOIN submission_facts sf ON sf.fact_id = a.fact_id WHERE sf.submission_id = 3
UNION SELECT 'law_assertions', law_assertion_id FROM submission_law WHERE submission_id = 3
UNION SELECT 'statements_of_law', l.id FROM statements_of_law l JOIN submission_law sl ON sl.law_assertion_id = l.law_assertion_id WHERE sl.submission_id = 3
UNION SELECT 'authorities', l.authority_id FROM statements_of_law l JOIN submission_law sl ON sl.law_assertion_id = l.law_assertion_id WHERE sl.submission_id = 3;
```

A line keyed on a row this read does not return stays in Proposed, however near the submission's work it looks. No row at all means the submission has none of its own work in Proposed: say so in one line and write nothing.

**One title, one job.** Lines in one batch that print the same title, other than lines already in a group (below), are written as one job: its title and intent are that title, and it holds every one of their keys, with a `ticket_proposals` row each. Their keys are written in one Call 1 `IN` list, as a group's are, and its scope rows are each key's rows, each written once. Its steps:

- **A note-up of a statute, regulation or rule:** every member's `step <n>:` lines, members in printed order and each member's lines in its own order, each distinct text written once, numbered 1, 2, 3…; no step row when every member prints `steps: none`. So the note-ups of one Act, however many `authorities` rows name it, are one job titled `Note up: <Act>`, with one step per provision, which runs on one currency check (`/draft`'s job-session).
- **Any other line:** one step, the shared item's step frame.

So no two jobs one intake writes share a title, and Call 2 never mistakes a sibling for a race.

```sql
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 1, 'Note up: Supreme Court Civil Rules, B.C. Reg. 168/2009, r. 9-6(3)');
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 2, 'Note up: Supreme Court Civil Rules, B.C. Reg. 168/2009, Rule 14-1(12)');
INSERT INTO ticket_proposals (ticket_id, proposal_key, item)
  VALUES (2, 'note-up:authorities:5', 'Supreme Court Civil Rules, B.C. Reg. 168/2009');
INSERT INTO ticket_proposals (ticket_id, proposal_key, item)
  VALUES (2, 'note-up:authorities:6', 'Supreme Court Civil Rules, B.C. Reg. 168/2009');
INSERT INTO ticket_scope (ticket_id, entity, entity_id) VALUES (2, 'authorities', 5);
INSERT INTO ticket_scope (ticket_id, entity, entity_id) VALUES (2, 'authorities', 6);
INSERT INTO ticket_scope (ticket_id, entity, entity_id) VALUES (2, 'provision_currency', NULL);
```

**Grouped Proposals.** Proposals of a type in this table, on one of the tables it names, are written as one job for the type, not one job each. A key's type is its text before the first `:`, and its table is the text between the first and second `:`. Every other key keeps the one-job shape above, including an `exhibit-pinpoint` key on `clauses`, whose item is a clause's wording and not a fact.

| Type | Tables | Title and intent |
|---|---|---|
| `exhibit-pinpoint` | `statements_of_fact`, `admissions`, `facts` | `Locate pinpoint references for the following facts` |

**The never-held read** runs once for the batch, before grouping, over every key the batch's lines carry:

```sql
SELECT DISTINCT p.proposal_key FROM ticket_proposals p JOIN tickets t ON t.id = p.ticket_id
  WHERE p.proposal_key IN ('exhibit-pinpoint:statements_of_fact:7', 'exhibit-pinpoint:statements_of_fact:8', 'note-up:authorities:5') AND t.deleted_at IS NULL;
```

Drop every key it returns from the batch. It is Call 1's guard, read ahead. A key a completed job once held still prints in Proposed, and one such key in a group would otherwise make the guard drop the whole group at every intake. "Take the next" runs this read before it chooses, so that it chooses a line that will be written.

**Grouping.** The keys left of one type in the table, on its tables, form one job when they number 2 or more. The job is written at its first member's place in the Proposed lane's printed order. A lone key of that type is written as above, as its own job titled with its Proposal's title (`Locate the exhibit pinpoint: <item>`), with one step.

**Call 1, group**, is Call 1 above with the table's text as title and intent and every member key in the `IN` list:

```sql
INSERT INTO tickets (proceeding_id, filing_id, title, intent, kind, priority, billing_anchor, created)
  VALUES (1, NULL, 'Locate pinpoint references for the following facts', 'Locate pinpoint references for the following facts', 'work', -1, '<matter>|attornment defeats the stay', strftime('%Y-%m-%dT%H:%M', 'now', 'localtime'));
DELETE FROM tickets WHERE id = last_insert_rowid()
  AND EXISTS (SELECT 1 FROM ticket_proposals p JOIN tickets t ON t.id = p.ticket_id
    WHERE p.proposal_key IN ('exhibit-pinpoint:statements_of_fact:7', 'exhibit-pinpoint:statements_of_fact:8') AND t.deleted_at IS NULL);
```

`filing_id` is NULL, because every table the group takes is proceeding-scoped substance.

**Call 2, group**, is Call 2 above with one more clause, that the job has no steps:

```sql
SELECT id FROM tickets t WHERE proceeding_id = 1 AND title = 'Locate pinpoint references for the following facts' AND status = 'queued' AND deleted_at IS NULL
  AND NOT EXISTS (SELECT 1 FROM ticket_proposals p WHERE p.ticket_id = t.id)
  AND NOT EXISTS (SELECT 1 FROM ticket_steps s WHERE s.ticket_id = t.id);
```

The table's title recurs on every batch. A group job whose keys were all dropped as dead ends holding no conversion record, and once released or reworked it sits `queued` with that title and no keys. Without the clause it would match beside the new row, the delete for more than one row would remove only the new row, which has no steps, and the group would never be written. With it, more than one row again means only two sessions' intakes writing at the same moment, and the delete above, with the table's title, removes them.

No row: a member became held between the never-held read and Call 1. Skip the group, say so in one line, and carry on. The next intake regroups.

**Call 3, group**, on the recovered literal id: one `ticket_steps` row per member, ordinal in the printed order, text the member's detail-line `item:` character for character, with no prefix. One `ticket_proposals` row per member, key and item copied from that line. The scope rows are each member's rows under §3's rule for a job outlined from a Proposal, each written once. `billing_anchor` follows §3's rule.

```sql
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 1, 'M. Reyes: Overtime for the final week was recorded in the Site Diary.');
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (2, 2, 'M. Reyes: The foreman signed each daily timesheet.');
INSERT INTO ticket_proposals (ticket_id, proposal_key, item)
  VALUES (2, 'exhibit-pinpoint:statements_of_fact:7', 'M. Reyes: Overtime for the final week was recorded in the Site Diary.');
INSERT INTO ticket_proposals (ticket_id, proposal_key, item)
  VALUES (2, 'exhibit-pinpoint:statements_of_fact:8', 'M. Reyes: The foreman signed each daily timesheet.');
```

After the batch the session re-renders. The practitioner-words gate reads no `INSERT INTO tickets` and no step written without a delete, so nothing intake writes reaches it. A job of its own, or of one title, takes the Proposal's fixed text as title and intent, and its step is §6a's fixed frame on the card's item, or the card's own `step <n>:` text. A group job's title and intent are the table's fixed text and its steps are items from the record. A later rewrite of a group job's steps passes the gate when each step is an item a `drafting_forms__*` result printed in that session.

## 3f. Spin off blockers (the holding session)

The practitioner has said yes to the spin-off offered on an obstacle in the job this session holds (`/draft`'s `draft/references/job-session.md`, "An obstacle on any assigned job"). The session holds job 42 under its own token `'sess-a1'` (§1). Like §3e, this is a fixed-section create and not outlining, so it runs in the holding session on the job it holds. Each blocker's `title` and `intent` are the practitioner's own words on §3's terms, written with their explicit yes, or a proposal the session showed in its visible reply that they approved word for word with a bare yes, written with `session_proposed = 1`, except a question's `intent` is all its sentences, consecutive in one turn.

**What each blocker copies from the held job**, read off the held job's card or §2's scope read: `proceeding_id`, `filing_id`, `billing_anchor` and `priority`. Copying `priority` places each blocker beside the work it unblocks, so the session asserts no order of its own. `kind` is `'work'`. Blockers are written in the order the practitioner named them, so at equal priority they queue in that order by `id`. §3's priority read is not run.

**Per blocker, three calls, all three before the next blocker's**, so that a lost lock leaves whole jobs behind, never a job without a step.

**Call 1, the guarded create.** §3's `INSERT ... VALUES` then `DELETE`, the guard being the holder's lock instead of a key:

```sql
INSERT INTO tickets (proceeding_id, filing_id, title, intent, kind, priority, billing_anchor, created, session_proposed)
  VALUES (1, 1, 'does attornment defeat the stay', 'Does attornment defeat the stay?', 'work', 4, '<matter>|attornment defeats the stay', strftime('%Y-%m-%dT%H:%M', 'now', 'localtime'), 0);
DELETE FROM tickets WHERE id = last_insert_rowid()
  AND NOT EXISTS (SELECT 1 FROM tickets WHERE id = 42 AND locked_by = 'sess-a1');
```

`session_proposed` is `1` only when the blocker's `title` and `intent` are the session's proposal, approved word for word with a bare yes, and `0` when they are the practitioner's own words.

The `DELETE` directly follows the job's own `INSERT`, the only place `last_insert_rowid()` is safe (§3). The practitioner-words gate reads no `INSERT INTO tickets`, so nothing in this script reaches it. The `INSERT ... VALUES` is §3's own shape.

**Call 2, id recovery.** Not §3's plain shape: its `LIMIT 1` would return an older job carrying the same title when the guard deleted the new row. §3e's shape, with no steps yet in place of no keys yet, and no `LIMIT`:

```sql
SELECT id FROM tickets t WHERE proceeding_id = 1 AND title = 'does attornment defeat the stay' AND status = 'queued' AND deleted_at IS NULL
  AND NOT EXISTS (SELECT 1 FROM ticket_steps s WHERE s.ticket_id = t.id);
```

No row: the lock was lost before this blocker was written. Stop, run §2's confirm-read after a release on job 42 so the readings below have a row to read, name any blocker already written, and report. One row: the new job. More than one: stop and ask.

**Call 3, the children**, on the recovered literal id (here `51`), unguarded on purpose: this job is the session's own creation and must not be left without a step. One `ticket_steps` row, ordinal 1, its text the intent verbatim. The scope rows are the held job's own, copied, since the blocker's work serves the held job's step:

```sql
INSERT INTO ticket_steps (ticket_id, ordinal, text) VALUES (51, 1, 'Does attornment defeat the stay?');
INSERT INTO ticket_scope (ticket_id, entity, entity_id) SELECT 51, entity, entity_id FROM ticket_scope WHERE ticket_id = 42;
```

No `ticket_proposals` rows: a blocker job is outlined from the practitioner's words, not from a Proposal.

**The final script, one `execute` call, after every blocker is written.** Edges first, then the release, because the release clears the token the edge guard checks, and statements in one script see each other's writes:

```sql
INSERT INTO ticket_blocks (blocker_id, blocked_id)
  SELECT 51, 42 FROM tickets WHERE id = 42 AND status = 'wip' AND locked_by = 'sess-a1';
INSERT INTO ticket_blocks (blocker_id, blocked_id)
  SELECT 52, 42 FROM tickets WHERE id = 42 AND status = 'wip' AND locked_by = 'sess-a1';
UPDATE tickets SET status = 'queued', locked_by = NULL, locked_at = NULL
  WHERE id = 42 AND status = 'wip' AND locked_by = 'sess-a1';
```

One edge insert per blocker. The release is §10's own statement, unchanged. Every statement carries the same guard, so either all land or none do: `changes` is the number of blockers plus 1 when the script landed, and 0 when it did not. Any other value is a composition bug: stop and report it. This is the one `ticket_blocks` edge written onto a `wip` blocked job (§11's one exception): the blocked job is the holder's own, and the same script releases it.

**Confirm-read**, run whatever `changes` says: §2's confirm-read after a release on job 42, plus

```sql
SELECT blocker_id FROM ticket_blocks WHERE blocked_id = 42;
```

Landed: `status = 'queued'`, `locked_by`, `locked_at` and `rejected_at` NULL, `plan_approved_at` as before, and one edge per blocker. Then re-render: the held job shows as Blocked, the blockers in Ready.

**Readings when the lock was lost.** The causes are §10's: another session's token means it was taken over, NULL with `rejected_at` stamped means it was shelved elsewhere, `completed` means a successor finished it, and `locked_by` NULL with `status = 'queued'` and `rejected_at` NULL means it was taken over and released, or shelved and restored, in another session. In every case this session's job work is over: report which it was and stop. If the loss came after one or more blockers were written, those stand as ordinary queued jobs with no waits-on edge, so name them by id and title. Never re-run any part of the script against a guess.
