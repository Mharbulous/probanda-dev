# HTML pages

Shared doctrine for every litigation skill. It is not a skill: it has no `SKILL.md` and is never wrapped. It ships inside the `skills/shared/` tree of the installed litigation `.plugin`. Decision record: `docs/adr/0033-plugin-html-pages-are-human-interfaces-never-read-by-agents.md`.

> Every HTML file the Probanda plugin produces is a human interface for viewing data held in the plugin's databases, generated deterministically from that data. An agent never views, reads, greps, parses, scripts over, stages, authors or requests a screenshot; however, an agent may present the html to a human user for them to view, and an agent may view screenshots provided by a human user on the user's own initiative. The only exception is developing/debugging the generator, in Claude Code. Agents review via markdown mockups and database data. One Litigation Strategy page per matter, and one Job Board page per live filing and per pre-filing proceeding, never more than one filing on a page, each at a path fixed by the filing's or the proceeding's id, so the user always sees the latest version.

- **The pages.** `<matter>\<DRAFT>\Litigation Strategy.html`, and one Job Board page per section (ADR 0033, 2026-10-05 amendments): `<matter>\<DRAFT>\Job Board <id>.html` per live Writing and `<matter>\<DRAFT>\Job Board - proceeding <id>.html` per pre-filing proceeding, where `<DRAFT>` is the matter's one `0. DRAFT*` folder. Each is named by its database id, so a retitle never moves a page. A retired filing has none, and the next write moves its old page to `TRASH`. A job with no filing is on every filing's page in its proceeding. A Job Board page's header carries the matter's dates as a second row of plain text, and a filing's completion-criteria card carries the dates of the deadlines linked to it, all read from the practice database at each write (ADR 0013, 2026-10-04 amendments). The server writes every page, each as a whole new file swapped in at once, at session entry when the matter has a draft folder, on every render given `draft_dir` or `presentation_dir`, and after each filing the background render finishes. No other copy of a page exists: none beside the database, none in a presentation folder, no numbered copy. A write moves older page files the server wrote into the matter's `TRASH`.
- **View pages** (ADR 0033, 2026-10-07 amendment). Beside them, each view page below, one per live Writing at `<matter>\<DRAFT>\<page name> - Job Board <id>.html`: a read-only view of that one filing's data, written with the other pages by the same writes, in the same way, under its own marker. Named by the filing's id, so a retitle never moves it; a retired filing has none, and the next write moves its old one to `TRASH`. Session entry and every render that writes the pages return every view page as `view_page_paths` (`[{name, filing_id, path}]`). A filing's Job Board page draws a tile for each of that filing's view pages after its Writings' tiles, naming the view page, with no link. One line per view page:
  - **Provable Facts**: the facts the filing uses, in the order the filing states them, each in ordinary text when provable (on the court record, admitted, or proved by evidence in hand that the practitioner has not recorded as inadmissible), faded when not yet in evidence, and struck through with the recorded decision shown when every piece of its evidence is recorded inadmissible. An admissibility concern alone shows as a flag. Two checkboxes show the faded and struck facts.
  - **Raw Research**: every proposition of law the drafting database records for the filing's proceeding, each statement with its citation, pinpoint, excerpt, verification and note-up status, and the submissions it is linked to. In use on this filing in ordinary text, undecided (recorded but not used on this filing, held in reserve included) faded, and not relevant (the proposition omitted by the practitioner, or its authority killed) struck through. Two checkboxes show the faded and struck propositions.
  - **Arguments**: the submissions and counter-arguments the drafting database records for the filing's proceeding, in three kinds. Submissions are the live submissions some filing of the proceeding deploys, this filing's first. Counter-arguments are the opposing points raised and the points the practitioner anticipates. Rebuttals are the live submissions held in reserve; this is not ↩️'s "rebuttal needed". Each submission and rebuttal shows the law and then the facts linked to it. A counter-argument lists the submissions and rebuttals the practitioner has linked to it (schema v65, many-to-many), so a rebuttal linked to two counter-arguments shows under both. The links are advisory, neither complete nor exhaustive, so a counter-argument with no link is never called unanswered. Folder tabs sit on one panel: All shows the three sections stacked, and Submissions, Counter-arguments or Rebuttals shows that section alone. Each section numbers its cards 1..N in page order, and each card's statement ends in a tag with its number ("Submission #N", "Rebuttal #N", "Raised #N" or "Anticipated #N"). The number buttons in a section's heading pick its one open card. Clicking a statement opens or closes its card, and closing it clears the number.
  - **Loose Threads**: every open loose thread of the filing's proceeding, the same set `board_card`'s loose_threads lane prints, in the same order. The ranked come first by rank (schema v66), ties by id, and the unranked follow by id, under an Unsorted heading that reads them as captured since the last ranking. Ranking never drops a loose thread. Each thread is a collapsible card. A ranked card's visible text is the job description the ranking restated it as (schema v70), ending in its rank tag and a tag with its group's short name in the group's colour (Practitioner decisions, Tooling, Housekeeping, Research, Authority mismatch, Evidence mismatch, Miscellaneous). Opened, it shows the original loose thought verbatim, then the one-line reason the ranking gave it, then its id, who surfaced it and where it came from. An unranked card, and one ranked before v70 with no job description, shows the loose thought verbatim, collapsed or opened, ending in its rank tag (a "?" while unranked). The controls are folder tabs (All, Ranked, Unsorted), an All groups switch on the Ranked heading that, turned off, shows one toggle chip per group present with its count of ranked threads, and a Defer button at the top right of each thread not yet deferred (schema v68). Defer sets the thread aside indefinitely: the page posts it to the data server's localhost listener, which writes the deferral to the drafting database, and on success the card collapses to its first line and fades, as every deferred thread shows. On load the page checks the listener; when it does not answer, the buttons stay disabled and one line reads "Buttons need the Claude desktop app running." A failed click shows its error on the card. A session reads the ranks, the job descriptions and the deferrals only through `board_card`'s loose_threads lane. A filing's Job Board page no longer lists the loose threads: its Loose Threads section shows their count and a plain-text cue to ask a session for this page. A pre-filing proceeding's Job Board page has no view page, so it still lists them.
- **Rendered for the human, generated from the databases.** A page holds nothing the databases do not. A session that read one would spend its tokens twice on data it already reaches directly.
- **A page can write, a session still never reads it.** A page button that changes data (today only the Loose Threads page's Defer) writes through the data server's localhost listener on 127.0.0.1, port 47615 unless `page_api_port` in coclerk.json names another, and only with the token the render embedded for that database and proceeding. The listener runs inside each session's data server, so the buttons work while a Claude session is open. A session learns what a button wrote from the database, through `board_card` and `/drafting-data`, never from the page.
- **What a session uses instead.** The board: session entry's `opened.board_summary` (the filing or proceeding `drafting_forms__open_session` opened), or `drafting_forms__render` naming `Work_board`, or rendering a pre-filing proceeding by its id, returns `board_summary`, fixed-grammar text for that one filing or proceeding, with `board_changed` and `board_moves`. The summary is short: the matter, the client, the revision, the linked to-do, and the unmet and met completion criteria. The lanes (each job as the page's collapsed card text with its dispatch, eligible and idle tags), the completion criteria in board order with their counts, a job's keys, plan, scope and steps, the members of Completed, Shelved, Proposed and Loose Threads, the drafts in Attached (ADR 0042), and the criterion items come from `drafting_forms__board_card`, which is read-only and reads the same inventory as the latest render. Those two are the only board content a session reads. The page paths and the filing list: session entry (`drafting_forms__open_session`) returns `job_board_path` (the opened filing's or proceeding's page), `job_board_paths` (every Job Board page), `view_page_paths` (every view page), `matter_board_path` and the filings in order. Everything else, a view page's data included: `/drafting-data`'s read tools, and the markdown mockups through the render response.
- **No screenshot requests.** An agent never requests a screenshot of a page. A screenshot the practitioner sends on their own initiative may be viewed. A session never reads page content any other way.
- **Cards only, no link.** The pages reach the practitioner only as file cards. A session gives no link to any page and relays none. No page links to another page either: a page that names another page says, in plain text, to ask a session for it, because a link on a previewed card resolves against the preview's web origin and opens an external browser.
- **Present each page by its path.** The session presents two pages as file cards at the fast open, the Litigation Strategy page first, then the opened filing's or proceeding's Job Board page, each by the path session entry returned (`matter_board_path`, `job_board_path`). When a render or completion reports the board changed, it presents the page at that result's `job_board_path` again. Another Job Board page is presented only when a different filing is opened. The card tool is `mcp__cowork__present_files` in Cowork and `SendUserFile` in the Code tab (ToolSearch if either is deferred). It is given the PC path and nothing else, so the card opens the file itself, not a copy, and the call returns no page content. No tool refreshes a card already open: presenting it again is the refresh. On a remote-device-only host, where `SendUserFile` takes staged paths only, stage those two pages in one `device_stage_files` call in the round trip right after session entry returns, which may share that round trip with the lapse-cleanup and intake writes, and call `SendUserFile` on the returned paths, the Litigation Strategy page first. Staging this early puts the cards up two round trips sooner when the intake writes jobs. When the intake's re-render, or any later render or `drafting_data__complete_job` result, reports `pages_written` true and `board_changed` true, stage and present the page at that result's `job_board_path` again, alone. The card is a copy frozen at staging, so restaging is the only refresh. The staged copy is a page: never read, grep, parse or script over it, and never reach it through a wildcard or a folder-wide search. Staging a page solely so its card can be presented is presenting, not reading. On every other host staging stays forbidden. On every host the Litigation Strategy page is presented again only when the practitioner asks. A view page is never presented at the fast open: it is presented only when the practitioner asks for it by name, as a card by its path in the latest `view_page_paths`, staged alone first on a remote-device-only host (`/draft` section 11, View pages). The one exception: after the loose-thread ranking the practitioner asked for, the session presents the Loose Threads page as a file card by its path in that render's `view_page_paths`, staged alone first on a remote-device-only host, since the request to rank is the request for the page. If presenting fails, say so in one line. A session never opens a page in a browser tool.
- **A file the server did not write.** A render refuses to overwrite a file at any page's path that does not carry that page's marker, and names it. Say so and stop. Never open, move or rename that file: what happens to it is the practitioner's call.
- **The one exception.** Developing or debugging the generator, in Claude Code, in the plugin's source repository, whose `.claude/settings.json` sets `COCLERK_HTML_DEV=1`. No Cowork task and no regular skill run is ever the exception.
- **The hook is the backstop.** `drafting-data/hooks/html-pages-gate.py` refuses a tool call that names a page: a file read or write, a grep aimed at one, a shell command naming one, or a device tool given one, except `device_stage_files` given exactly `Litigation Strategy.html` (or the legacy `To Do List.html`), `Job Board <id>.html`, `Job Board - proceeding <id>.html` or a view page's `<page name> - Job Board <id>.html`, case aside, or a page under its name before 2026-10-09 (`Job Board - filing <id>.html`, `<page name> - filing <id>.html`). It knows each view page by the name listed in its `VIEW_NAMES`, so a new view page adds its name there. It matches names only, so a page reached through a variable or a wildcard passes it. This doctrine is the rule.
