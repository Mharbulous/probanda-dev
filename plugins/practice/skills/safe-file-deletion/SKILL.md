# Safe file deletion

> **Enforcement ships in three layers, quietest first.**
>
> 1. **The tool.** `file_ops__trash`, on the `file-admin` plugin's `files` server, moves one file or folder to `<root>/TRASH/<same relative path>` in a single call. It runs on the host, outside the Cowork sandbox, so it needs no shell, raises no delete-permission prompt, and still works while the device mount is down. This is the primary path.
> 2. **The rewriting hook.** `hooks/redirect-delete-to-trash.py`, alongside this file, is a `PreToolUse` hook with matcher `Bash|PowerShell|mcp__(.+__)?device_bash`. It is declared in the `practice` plugin's `plugin.json`, so it runs whether or not `file-admin` is enabled, and in this repo's `.claude/settings.json`. A single `rm` or `unlink` outside a Git worktree and the OS temp directory, whose every target parses with confidence, is silently rewritten into `mkdir -p` + `mv --backup=numbered` into TRASH.
> 3. **The block.** Whatever the hook cannot rewrite is denied, with a message naming `file_ops__trash` and saying that without the `file-admin` plugin the deletion is refused. That covers globs, chained commands, `find -delete`, Python or .NET deletes, PowerShell, and a target that is a workspace root or already in TRASH.
>
> A plugin-shipped hook is confirmed to fire in Cowork. In session https://claude.ai/code/session_01FDrn3GekPVFrnV5X3hVUQW (2026-09-14), a probe `rm` from the cloud Bash tool was blocked with the TRASH redirect.
>
> **Known gap:** the hook only sees shell tool calls. Cowork's `device_request_delete_permission` (formerly `mcp__cowork__allow_cowork_file_delete`) path, or any other non-shell delete, bypasses it. Any future non-shell delete path must route to `file_ops__trash`, and on such paths the policy below still applies by hand. Extending the hook's pattern list is a one-line change to the list inside `_destructive_patterns()` at the top of the script. Extending it to a new shell tool means adding that tool to the plugin matcher and to `TOOL_RE`.
>
> **Known gap: deletes hidden from a text matcher (#632, #645).** The hook reads one level past the command text. A shell script the command runs is opened and scanned: a `.ps1`, `.sh`, `.bat` or `.cmd` path in command position (`./x.sh`, `& x.ps1`), after `bash`/`sh`/`zsh`/`source`/`.`, after `cmd /c`, or anywhere in a `pwsh`/`powershell` invocation (`-File`, `-f`). A relative path resolves against the session cwd. A missing script is allowed (nothing runs), an odd encoding is read leniently, and an unreadable script counts as a delete. An encoded command (`-EncodedCommand`, `-ec`, or any prefix such as `-e` or `-enc`, after `-` or `/`) is decoded as base64 UTF-16LE and scanned, and a payload that will not decode counts as a delete. Paths named inside that text count as locations. A `.bat` or `.cmd` script is read with the PowerShell pattern set, so a plain `rd` in one counts as a delete. On `device_bash` the script is on another machine, so every script run there is denied. Still uncovered: a script run through any other interpreter (`python x.py`, `node x.js`), a script with no such extension (`bash cleanup`), a script another script calls or dot-sources, an encoded command inside a script, a script written and run in the same call (it does not exist yet when the hook reads it), a relative path meant to resolve after a `cd` in the same command, a script run inside a quoted command string (`bash -c 'source ./x.sh'`), a script fed on stdin (`bash < x.sh`, `cat x.sh | bash`), the colon spelling `-EncodedCommand:<base64>`, and a script or encoded command passed as an argument to another program (`Start-Process pwsh -ArgumentList ...`). A shell word only counts in command position, so a script or switch named in prose is not read. A bare `x.sh` is read from the cwd even where the shell would find it on PATH. On these paths the policy below applies by hand: route the deletion through `file_ops__trash`.
>
> **Known gap: text that is only stored, and text that only looks run (#643).** A heredoc whose body is stored and never run is not scanned: `cat` or `tee` not piped anywhere, `git commit -F -`, `gh ... --body-file -`, or `$(cat <<...)` as the argument of such a git/gh command, each with a quoted delimiter (`<<'EOF'` or `<<"EOF"`) and its terminator line present. So a delete written into a script this way and run later is unseen, even in the same call (`cat > x.sh <<'EOF' ... EOF` then `bash x.sh`), which is the script-file gap above. Only the home forms `$HOME`, `$USERPROFILE` (either with braces), `%HOME%`, `%USERPROFILE%` and `~` are expanded before a location is sought, so a delete whose target is reachable only through another variable is not located. A path that ends at the shell binary itself (`cmd.exe`, `pwsh.exe`, `powershell.exe`) never counts as a location, so a delete of that binary is not guarded. An unquoted full path to the shell still reads as one path running on into its arguments and still denies from a worktree; quote it. False denies remain for every other heredoc: an interpreter's heredoc (`bash`, `pwsh -Command -`, `python -`) is script text that runs and is scanned in full, `rimraf` included. The same applies to an unquoted or `<<-` delimiter, two heredocs on one line, or a missing terminator. For those, write the text with the Write tool and reference the file.

**Scope gate -- check this before anything else, including when this skill was invoked explicitly.** Resolve the deletion target's absolute path (and its nearest existing parent, if the target itself doesn't exist yet -- e.g. a stale lock file).

1. **If the resolved path is inside a Git worktree** (anywhere under a directory containing a `.git` folder or file, including the `.git` directory itself, and regardless of whether the target is tracked, untracked, ignored, or generated) -- this skill is **out of scope**. Do not apply it. Follow the repository's normal deletion rules instead (e.g. `git clean`, a plain `rm` on a build artifact, or removing a stale `.git/index.lock`).
2. **Otherwise, if the resolved path is inside a Coclerk client-matter project** (identified by a `coclerk.json` marker at or above the target) -- this skill applies. Continue below.
3. **Otherwise** (outside both a client-matter project and a Git worktree) -- still never delete permanently. `file_ops__trash` refuses a path with no `coclerk.json` marker, so do not delete: tell the user no recoverable delete mechanism is available and ask them to delete it themselves (e.g. File Explorer, where the Recycle Bin applies). Never delete permanently without their explicit confirmation.

This gate applies even if a client-matter folder happens to live inside a Git worktree: the Git exclusion always wins.

**Never use `rm` (or any other permanent/hard-delete command: `os.remove`, `unlink`, `shutil.rmtree`, etc.) on a client-matter file that falls within this skill's scope.** `rm` unlinks a file immediately and permanently -- there is no undo, and this has caused real, unrecoverable data loss in past sessions on client/business files.

## What to do instead

**Move the item into a `TRASH` folder at the root of the project workspace, preserving its relative path under that root.** Not an OS recycle bin, not `gio trash`, not a freedesktop trash directory -- a plain `TRASH` folder inside the workspace itself, so the item stays with the matter it belongs to and stays visible to the practitioner.

1. **Call `file_ops__trash` with the item's absolute path.** One call, no shell. It finds the workspace root, refuses anything out of scope or protected, moves the item, and logs the move in TRASH so it can be reversed. A taken destination gets a ` (trashed YYYY-MM-DD HHMMSS)` suffix instead of an overwrite. Then continue the original task using the new location if anything still needs the file.
2. **If `file_ops__trash` is not available in this session**, the `file-admin` plugin is not enabled (or its server is down): stop, tell the practitioner that this step trashes a file and needs `file-admin`, and do nothing else. Never fall back to a shell `mv` or `rm` or the Write tool.
3. **A stray `rm` is caught.** The hook rewrites a parseable one into a move into `TRASH` automatically, and blocks what it cannot rewrite.
4. **The OS temp directory is exempt.** Throwaway files under the system temp folder (the session scratchpad) may be deleted normally -- they are not client data, and the hook lets them through. No temp cwd is needed for a lone `rm` naming absolute temp paths, or one after `cd <absolute temp dir> &&`. A `;` chain, or a `~`-led, `$`, `{` or dot-led path, still needs one. The hook judges this exemption, and the Git worktree one, by where a path really lands: a link under temp or a worktree that points elsewhere is not exempt once the delete follows it (a trailing `/` or `/.`). That holds for a relative target in a chained command too, joined to the directory it runs in after any `cd`, and for a glob in a component the delete follows (`<dir>/*/`, `<dir>/*/x`): every match must land in temp or a worktree. A glob in the last component with no trailing slash (`<dir>/*`) removes each link, not its target, and stays exempt. With no match, the shell passes the pattern on as written, so that literal path is judged. Where the hook cannot tell an `rm`'s targets or the directory it runs in, no exemption applies and the delete is denied. That covers a wrapper such as `sudo`, `xargs` or `find -exec`, a loop body, a subshell, and a substitution. It also covers a target holding a variable other than the home forms, or a brace or backtick, and any `cd` other than a plain `cd <dir>` (`pushd`, `builtin cd`, or a `cd` to `~`, `-` or a variable).
5. **Removing an empty directory is not a deletion of anything.** `rmdir` in Bash and `rd`/`rmdir` in cmd refuse to touch a non-empty directory, so they cannot lose data and are allowed. This is what lets a `TRASH` folder be removed once its contents have been dealt with: run `rmdir` from the Bash tool, since `file_ops__trash` refuses the `TRASH` folder itself. In PowerShell, `rd` and `rmdir` are aliases of `Remove-Item` and count as a delete whatever their flags. That holds on the PowerShell tool, and on Bash when the command invokes a Windows shell and names `powershell` or `pwsh`. On the PowerShell tool even a quoted `rd`, such as the `(st|nd|rd)` of a text search, reads as a delete, so run such a search from the Bash tool. `rm -r`, `rd /s` and `Remove-Item -Recurse` are tree deletes and stay blocked.
6. **Cowork's own delete-permission tool (`device_request_delete_permission`, formerly `mcp__cowork__allow_cowork_file_delete`)** governs whether delete operations are allowed at all in a connected folder -- it does not by itself make a deletion recoverable. Treat it as a permission gate, not a safety net. Even after it grants permission, still move the item into `TRASH` rather than deleting it.
7. **Never retry a failed delete blindly.** If a delete attempt fails (permission denied, operation not permitted, etc.), stop and check current state (`ls`/`stat`) before trying again. Do not loop `rm` attempts hoping one eventually succeeds -- a "failed" attempt may actually succeed on a delayed retry without it being obvious from the output, which risks a real, unrecoverable delete slipping through unnoticed.
8. **When replacing a file with a renamed/corrected version** (e.g., fixing a filename), prefer copy-then-verify-then-move over an in-place rename when there's any doubt: copy the original to the new name, hash-verify the copy is byte-identical, and only then move the original into `TRASH`. This way the content is never at risk even if the move step fails or is delayed.

## Summary

`rm` = forbidden. Moving the item to `<workspace root>/TRASH/<same relative path>` = required, through `file_ops__trash`. Without it (the `file-admin` plugin is not enabled), stop and tell the practitioner. Inside a Git worktree, or under the OS temp directory, none of this applies and ordinary deletion rules govern.
