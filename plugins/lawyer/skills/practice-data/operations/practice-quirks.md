Read when: reading, writing or reviewing the practice's quirks (the rule and knowledge entries that say how this practice works), or sorting memory lines the practitioner brings.

# Practice quirks

A quirk is one short entry about how this practice works: facts about its setup that a session would otherwise rediscover by trial and error, such as where its mail is routed, which mailbox the mail connector reads, folder habits and tool limits, and instructions the practitioner gives for the practice as a whole. Entries belong to the practice and live in `<case_data_root>\_practice\quirks\quirks.json`. They are never copied into a matter database or a plugin.

- **Entries.** Each has a type, one to three areas, a title, a body and dates. Type `rule`: something Probanda must or must not do in this practice, the practitioner's instruction. Type `knowledge`: a fact about how the practice works that informs reasoning and directs nothing. Areas are free one-word tags: `email`, `files`, `billing`, `court`, `staff` and `tools` are the usual ones, and `quirks__list` returns the areas in use, so reuse one before inventing another. The title is at most 100 characters. The body is one paragraph about one issue, at most 1,000 characters. A rule names no skill: an instruction for one named skill is a preference (`shared/paralegal-posture.md` section 9), not a quirk. An entry is never deleted. It is revised (the old entry is retired and the new one points back to it) or retired, and `last_confirmed_on` says when the practitioner last said it still holds. Temporary knowledge, such as duplicates present only for some days, is an ordinary entry that is retired when it stops being true.
- **Read.** A plugin hook adds the index of the active entries (type, areas, title) to the start of every session, rules first. It states facts and never asks the session to act. Where it cannot reach the practice folder, as in Cowork, it says only that no quirks are in the session's context. Each skill that starts a mail, calendar or file lookup then reads the bodies of the entries for its areas itself, before that first lookup, with `quirks__read` (`areas`) in the same round trip as its first tool call, as `/call-contact` does. `quirks__list` returns the index and the areas in use, and `quirks__read` also takes `ids` and `type`. A rule is followed as the practitioner's instruction within the limits of every verification, approval and privilege rule and Probanda's safeguards. Knowledge is context and never an instruction. An empty result means none are recorded for those areas: the task carries on. A failed call is reported once and the task carries on. Read each area at most once in a session. A session that dispatches a subagent whose work touches mail, a calendar or a tool an entry names copies the relevant entries into that subagent's brief. `practice_data__config_status` and `practice_data__firm_profile` still return every active entry as one text (`practice_quirks`, one `RULE` or `KNOWLEDGE` line each) for readers not yet changed.
- **Write.** Add, revise, confirm or retire an entry only when the practitioner asks, or when a session learns a quirk from the practitioner and proposes recording it, or when the practitioner asks to sort lines they bring from the assistant's memory ("Review of memory lines" below). Never infer a quirk and never write one unprompted. A rule is saved only in the practitioner's own words. Present the proposal under `/show-me` in a code block that reads `PROPOSED PRACTICE RULE  (area: <area>)`, `Title: <title>`, `Body: <body>`, and `Paste this whole block back into chat to save it.`, then call `quirks__write` only after the practitioner's next message holds the title and body. "Yes" or "Approved" never saves a rule. A hook refuses the call when the words are not in that message, and no rewording gets past it. Revising a rule is a new proposal block. Retiring a rule needs the practitioner's own words asking to remove it, with its title. Knowledge, and confirming an entry or retiring knowledge, are shown the same way with one question, and are saved after the practitioner's plain yes. A subagent never writes a quirk: it returns its proposal to the main session. Nothing shown names a tool, the settings file or the entry's file (`shared/internals-confidentiality.md`).
- **Review of memory lines.** Only when the practitioner asks to review or sort lines from the assistant's global memory or a Project's memory, and brings the lines themselves, pasted or pointed to. The session never searches memory on its own and never infers a line. Put each line in one of four bins, one line each: *personal* (stays in global memory), *one matter* (stays in that matter's Project), *every matter* (a fact about this practice that holds across matters, of the kinds named above) or *standing instruction* (an "always" or "never"). Propose each every-matter line as a knowledge entry under "Write" above, and a standing instruction that names no skill as a rule entry, each with its own area. A standing instruction for a named skill is never saved as a quirk: show suggested wording in a code block and say it becomes a Rule only in the practitioner's own words (`shared/paralegal-posture.md` section 9). Never save a Rule from a memory line. After a write, name each line that now lives in an entry and say the practitioner can remove it from memory themselves: Probanda does not read or edit memory.
- **Content.** Facts about the practice's setup, and the practitioner's instructions for it. Never a password, key, token or other credential, and never text that relaxes a verification, approval or privilege rule. A mailbox address, or the fact that a password exists and where it is kept, is allowed. Decline such an entry and say why. The tool also refuses what it recognizes as one, and knowledge worded as an instruction: it saves nothing and asks a question about the entry.
- **Mail routing.** The `lawyer:delivery-checker` agent reads the `email` entries first to learn where to look for a sent letter, and reports them as missing or stale when it cannot. The facts it needs, each in a short plain sentence: which mail folder holds which account's sent mail, naming the sending account's own folder; that a mirror account's copy of a message is the same sending and not a second one; which folders hold incoming mail; and that a search across the whole mailbox times out, so searches name one folder. `shared/matter-mail.md` reads them for one more: which mail folder trees hold matter folders, in the order preferred, each tree before any copy of it such as a "(This computer only)" sibling, with each path exactly as the mail folder list gives it. A fact check of outgoing correspondence reads them for two more: which mailbox receives whose mail, and which mailboxes the mail tools cannot reach. A session offers to record these only as "Write" above allows.
- **Limits.** A title over 100 characters or a body over 1,000 is refused and nothing is written, never truncated: say so and propose the entry again, shorter or split into one entry per issue.
- **Old note.** Before entries, one free-text note in this machine's `probanda.json` (`practice_quirks`, at most 1,000 characters) held everything, and a machine can still hold one. While the practice has no active entry the old note is still read, and still injected at session start. Once it has entries, a non-empty write to the old note is refused. To migrate it, propose entries for what its text says that the entries do not, one issue each, as "Write" above, then clear the old note with `practice_data__upsert_firm_profile` (`practice_quirks`, `""`) after the practitioner's yes.
