# timecamping-data — router and schema owner

Helper skill — not user-invocable. The single gatekeeper for the timecamping database: **one SQLite file, per practitioner** (not per matter, unlike `/matter-data`), reached only through the `timecamping_data__*` MCP tools. No other skill may embed SQL, resolve the database path, or assume schema shape — all of that stays here.

Design source of truth: `Engineering/1. Design/2026-08-28_timecamping-evidence-first-design.md` (the seven-point evidence-first pipeline, the evidence doctrine, the 9-row ceremony grid, the presumption lifecycle) and `.claude/skills/timecamping/VISION.md` (the core principle: inference forbidden until evidence assembly is complete, enforced by pipeline structure). This skill is the schema's home, not a restatement of the design doc — read it there for rationale; read `references/schema.sql` here for the current DDL.

## Operation Routing

| Operation | Tool | Notes |
|---|---|---|
| Read-only SQL against the schema, or the canonical consolidated-day read | `timecamping_data__query` | `{sql, params?}` — a single `SELECT`/`WITH`/`PRAGMA`; no `db_path` parameter (server-resolved, single fixed file); fails clearly if the database doesn't exist yet — run `migrate` first |
| Loading a day's source rows and fetch statuses | `timecamping_data__bulk_upsert` | `{path}` — an absolute path to a JSONL file in the shape under Bulk ingest file, below; one transaction that upserts each line on its `key`, no `db_path` parameter. **A non-success result does not prove the file did not commit — verify before you retry**, for the same reasons as `execute`: re-read the day's `source_fetch_log` rows and the per-table counts with `timecamping_data__query`. Re-running the same file is safe, because it upserts in place and ids do not change |
| Every other write: recording proposals/determinations/presumptions | `timecamping_data__execute` | `{sql_script}` — one transaction, no `db_path` parameter. **A non-success result does not prove the script did not commit — verify before you retry.** An error, a rejection, a timeout, or no response at all can each arrive on a write that already landed; the backend itself has no step after the copy-back that can fail, but a harness rejection or a bridge give-up after the call was dispatched reports non-success without the backend having failed at all. Before any further write or retry, re-read the rows the script targeted with `timecamping_data__query` and re-run only if they show the write did not land — what a blind re-run costs is per-table, see CRUD guidance |
| Schema migration | `timecamping_data__migrate` | `{}` — no parameters at all; separate spawn, sole schema-guard bypass, same containment discipline as this codebase's other generic-connection-primitive gatekeepers; run before the first `query`/`execute` against a fresh database |

**Reading a day's consolidated evidence — the hard gate lives here, not in the caller.** Never hand-roll the per-source `UNION ALL` yourself. Read `references/splice.sql` verbatim and pass it as `sql` to `timecamping_data__query` with `params: ["<YYYY-MM-DD>"]` (one param, the target local date — referenced multiple times inside the query via its own `target` CTE, so it is supplied exactly once). The result has one column, `line`: one row per line of text, in reading order. Fields within a line are tab-separated, and a tab shows as `\t` in the served JSON, as in the examples below.

- **Gate violation**: exactly one line and nothing else, naming each source still missing a terminal fetch status for the date — `GATE VIOLATION: missing syncopaid_captures, gcal_events`.
- **Otherwise**, in this order:
  1. The header — `DAY 2026-09-01 | lines 2493 | chars 243330`. `lines` counts every line after the header and `chars` is the sum of their lengths in characters, so a caller paging a spilled result can prove it reached the end. The query enforces no size budget and never splits a day.
  2. The legend of the source aliases the lines use — `SOURCES gc=gcal_events ic=icloud_events sc=syncopaid_captures sm=sent_mail tc=telus_calls tca=timecamp_computer_activities tte=timecamp_time_entries`.
  3. A `FORMAT` line restating the field order of the two line kinds below, so the output describes itself.
  4. Every standing-fact line: `FACT`, source alias, `detail`, `summary` — `FACT\ttc\tseen 2026-08-26 to 2026-08-28 (3 calls)\t+16045550172 = Jesse Marlowe`.
  5. Every evidence line for the day, in time order: source alias, member ids in brackets, member count, start, end, abuts, summary — `sc\t[593,594,595]\t3\t2026-09-01T17:16:09Z\t17:19:31\t<>\tclaude: Claude`. `start` is the stored UTC timestamp. `end` is `HH:MM:SS` when it falls on start's UTC date, else the full UTC timestamp. `abuts` is two characters: `<` when the line's first member begins exactly when another row (any source) ends, else `-`, then `>` when its last member ends exactly when another row begins, else `-` — boundary-continuity hints computed in SQL, per source row, before merging. `summary` is verbatim and always last, flags included (`[OCR available]`, `[amber/work-queue]`, `[switching-file/work-queue]`, `[all-day]`, `[free]`, `[guests listed]`, `[never edited since created …]`, and on an `ic` line `[calendar: <name>]`, the iCloud calendar the event was read from). An `sm` line is one sent email, an instant, so its start and end are the same: its summary is the subject, `->`, the To list, and `[cc <list>]` when there is a Cc, never a body. TimeCamp lines also carry tracked time (#1102). A `tte` line's `[tracked Ns]` is the entry's `duration_seconds`, the seconds TimeCamp counts for it, which is not its clock span. A `tca` line names the entry the row counts toward, read from its payload's `entry_id`. `[tte <id>]` is that entry's id, which may belong to an entry dated another day and so have no line in this read. `[tte ?<native id>]` is an entry absent from the table, and `[untracked]` a row attributed to no entry.

**An evidence line with a count above 1 is a merged run.** In the day's order (start, then summary, source and row id), a row joins the line before it only when it comes from the same source, has a byte-identical summary (a flag appearing or disappearing breaks the run), and starts no later than the previous row ends (any gap, even one second, breaks it). A row from any other source sitting between two such rows breaks the run too, so overlaps are preserved, never resolved: two sources covering the same stretch stay separate lines. The bracketed ids are the member rows' own ids in that source table, in member order, and the span runs from the first member's start to the latest end among the members. Every row of the day appears on exactly one line.

**A standing fact is not an event.** A `FACT` line carries a fact one of the sources establishes that belongs to no particular day — today, the Telus contact directory: which person owns a phone number, over the whole call history rather than the target date (issue #844; the combined-history cross-day-identity fixture is the worked case). These lines carry no timestamps, member ids or abuts marker, sort ahead of the time-ordered evidence lines, and must never be read as something that happened on the target date. `summary` carries the fact; `detail` carries its own observation span (`seen 2026-08-26 to 2026-08-28 (3 calls)`), which a caller repeats verbatim whenever a conclusion rests on it. Standing facts are gated exactly like evidence — a violation returns the violation line alone. **A caller that gets a `GATE VIOLATION` line halts and reports it — it never falls back to reading a per-source table directly to "just see what's there."** That fallback is exactly the partial view the whole design exists to prevent.

**After the gate has released, a single-row detail read of one source table is permitted** — fetching the one row a ceremony must render (a capture's `ocr_text`, a calendar event's `attendees`/`created`/`updated`, an iCloud event's `notes`/`location`), which is what the consolidated read's `[OCR available]`-style flags are pointing at. It is never a substitute for the consolidated read, never a way to survey a source, and never done before the gate passes: the rule is about what the model sees *before* assembly completes, not about detail it needs to show a human afterwards.

**The backfill overlay is the second sanctioned read, with one use** (#1270): after a backfill has ingested a closed day's newly registered `sent_mail` and `icloud_events` rows, it lays those rows over the day's existing proposals. Read `references/backfill.sql` verbatim and pass it to `timecamping_data__query` with `params: ["<YYYY-MM-DD>"]`, exactly as for `splice.sql`. It embeds the same seven-source gate. Its columns are `source` (`sm` or `ic`), `source_row_id`, `start_ts`, `end_ts`, `summary` (the same text the consolidated read prints for that row), then the overlapping proposal's `proposal_id`, `proposal_status`, `proposed_matter_ref`, `proposal_start_ts`, `proposal_end_ts`, `written_back` and `entered_by_hand_at`, and last `timecamp_entries`: the target date's `timecamp_time_entries` rows covering the source row, as a JSON array of `{id, timecamp_task_id, task_display}` objects (`id` is the entry's id in the consolidated read's `tte` lines), or NULL when no entry covers it. Coverage uses the same overlap rule as proposals and depends only on the source row, so a row overlapping two proposals carries the same value on both its result rows. A NULL `timecamp_entries` is the overlay's test for possible unrecorded work: most of a day's entries never became proposals, so a NULL proposal column alone means only that no proposal covers the row. Such a row with a non-NULL `timecamp_entries` is tested against its covering entry's task instead, and a contradiction there is also possible unrecorded work. There is one row per source row and overlapping non-superseded proposal: a sent email overlaps a proposal when `start_ts <= sent_ts < end_ts`, and an iCloud event when the spans intersect. A row overlapping two proposals appears twice, and a row overlapping none appears once with every proposal column NULL. A `GATE` row (`source = 'GATE'`, `summary` the violation text, every other column NULL) comes alone and halts the caller exactly as a violation line does. The overlay is never an inference-pass input.

## Bulk ingest file

A day's source rows reach the database as one file, never as SQL and never through tool arguments. `timecamping_data__bulk_upsert` reads the file itself, one JSON object per line:

```
{"table":"telus_calls","key":["native_id"],"row":{"native_id":"c2026-09-01T09:20+16045551234","start_ts":"2026-09-01T16:20:00Z",...}}
{"table":"source_fetch_log","key":["source_name","local_date"],"row":{"source_name":"telus_calls","local_date":"2026-09-01","status":"fetched","row_count":1,"error_detail":null,"fetched_at":"..."}}
```

- `key` names the table's unique key: `["native_id"]` for a source table, `["source_name","local_date"]` for `source_fetch_log`. Every key column must appear in `row`.
- Row values are JSON scalars. A structured column (`raw_payload`, `attendees`) is a JSON-encoded string.
- **Never put `id` in a row.** The line would overwrite the rowid that `proposals.evidence_chain` points at.
- The whole file is one transaction. A bad line aborts it, naming the line number, and nothing is written.

`scripts/build_ingest.py` writes these files. It uses the standard library only and never opens a database. Each subcommand appends one source's lines to `--out` and prints a one-line JSON summary. Run every subcommand for the day against one file, then make one `bulk_upsert` call:

| Subcommand | Input file | Writes |
|---|---|---|
| `timeline --source timecamp\|telus\|gcal\|icloud\|sent_mail --export F --date D --out O` | a `/time-pipeline-data` export of prefix `activity:{source}:`, or `event:sent_mail:` for sent mail | `timecamp_computer_activities`, `telus_calls`, `gcal_events`, `icloud_events` or `sent_mail`: the rows whose `start_ts` (a sent email's `ts`) falls on local date D. An `icloud` row with no calendar, or from a calendar other than `Work` or `Home`, fails the run. A `sent_mail` row from a folder other than `Sent Items`, `Sent Messages` or their `Outbound LEAP Matter Based Emails` subfolders fails the run, and a Message-ID found in several folders is one row, the copy in the earliest folder in that order |
| `timecamp-entries --json F --date D --user-id U --out O` | the TimeCamp entries response | `timecamp_time_entries`: user U's rows for D |
| `syncopaid-captures --json F --date D --out O` | the `evidence query --include-ocr-text` response | `syncopaid_captures`. Fails on a window that is not local day D, a truncated response, or two captures in the same second |
| `fetch-log --source T --date D --status skipped\|failed\|empty [--error-detail X] --out O` | none | `source_fetch_log` only, for an exit that produced no rows. T is the source's table name |

Each of the first three also writes the source's status line: `fetched` with the row count, or `empty`. `--timezone` defaults to `America/Vancouver`. A required field missing from an input row fails the run and names the field, and a failed run appends nothing. Run the script with the host Python (`python`; if that is the WindowsApps stub, the interpreter `COCLERK_PYTHON` names).

## Schema reference

`references/schema.sql` is the canonical current schema — generated by dumping `sqlite_master.sql` from a database freshly migrated via `references/scripts/migrate_engine.py`, never hand-edited. It must match a live migrated database byte-for-byte; if it doesn't, `migrations.sql` changed without regenerating it, and it must be regenerated before this skill is trusted.

**Shape**: seven source tables (`timecamp_time_entries`, `timecamp_computer_activities`, `syncopaid_captures`, `telus_calls`, `gcal_events`, `icloud_events`, `sent_mail`), one per evidence source (design doc step 2); `source_fetch_log`, the durable record the assembly gate reads (design doc step 3); `presumptions` and `proposals` (design doc step 5, the inference pass's output — one proposal *is* one time block, so there is no separate block table: a proposal's `evidence_chain` JSON column names every source row that fed it); `determinations` (design doc step 7, ceremony answers recorded as evidence for future corroboration); `db_meta` (schema version).

**Not stored, deliberately**: what a proposal's matter reference *means* (`practice_data__matter_lookup` is the authority on matters); raw screenshot bytes (only a `screenshot_ref` handle — the SyncoPaid tool's own image store is the authority); anything about a matter's parties, proceedings, or filings (that lives in `/matter-data`, and in other per-matter data stores outside this plugin).

**Current version**: `db_meta.schema_version = 6` (v1 migration, issue #430 — the initial build; the additive 1 → 2 hop, issue #454 — registering Google Calendar as the fifth evidence source; the 2 → 3 hop, issue #938 — rewriting every `proposals.evidence_chain` entry's scalar `source_row_id` into a `source_row_ids` list, with no DDL change; the additive 3 → 4 hop, issue #997 — `proposals.entered_by_hand_at`; the additive 4 → 5 hop, issue #1199 — registering the iCloud calendar as the sixth evidence source; the additive 5 → 6 hop, issue #1261 — registering sent mail as the seventh evidence source), 12 tables. A database at an older version fails any statement naming a newer column: run `timecamping_data__migrate` first.

## CRUD guidance

- **What a re-run costs is per-table.** Source-row ingests are self-protecting (`native_id` upserts), and so is `source_fetch_log` (`UNIQUE (source_name, local_date)`) — a re-run overwrites rather than duplicates. `determinations.proposal_id` and `presumptions.identifier` are `UNIQUE`, so a re-run errors loudly instead of duplicating. **`proposals` has no unique key**: re-running a supersede-then-insert script supersedes the rows the first run inserted and inserts a second copy under new ids, silently. Verify with a read before re-running any `proposals` write.
- **A day's source rows arrive through `bulk_upsert`, never through an `execute` script.** Its `ON CONFLICT ... DO UPDATE` keeps each row's `id`, so `proposals.evidence_chain` stays valid across re-fetches. A bulk re-ingest is additive: it updates and inserts but never deletes, so a row that a later re-fetch no longer returns stays in the table with its older `fetched_at`.
- **A source row's `native_id` is the idempotent re-fetch key** (`UNIQUE` on every source table) — re-fetching a day upserts by `native_id`, it never blindly re-inserts and duplicates.
- **`source_fetch_log` upserts on `(source_name, local_date)`.** Re-running a day's fetch overwrites that day's row per source rather than accumulating history — the gate only ever needs to know the *current* terminal status, not a log of attempts. **`source_name` is the source's table name** — the gate joins on it, so a status filed under a source's informal name (`gcal` rather than `gcal_events`) leaves the real source looking never-fetched and blocks the day.
- **Re-running a day's inference pass supersedes, never accumulates.** Before inserting new `proposals` rows for a `local_date` already populated, set the prior rows' `status = 'superseded'` first. A **terminal** proposal (`written_back = 1`, or `entered_by_hand_at` set) is exempt: leave it as it is, since superseding it would re-categorize something already in TimeCamp. Before a re-run's inference pass, hand the caller the day's terminal spans: `SELECT id, start_ts, end_ts, proposed_matter_ref FROM proposals WHERE local_date = ? AND status <> 'superseded' AND (written_back = 1 OR entered_by_hand_at IS NOT NULL)`. Time those spans cover is covered for the uncovered-time rule. A reopened proposal (below) keeps `written_back = 1` as history but is `superseded`, so its span is covered by its successor, not by it.
- **Manual-completion record: an uncovered proposal entered by hand is `entered_by_hand_at`, never `written_back`.** An uncovered proposal has no entry to write to, so the practitioner creates the entry by hand. Only on the practitioner's explicit confirmation for that one proposal, stamp it with a guarded update: `UPDATE proposals SET entered_by_hand_at = <UTC now> WHERE id = <id> AND entered_by_hand_at IS NULL AND written_back = 0 AND status IN ('committed_silent','committed_after_ceremony')`, then re-read the row. `status` keeps its Step 6 outcome and `written_back` stays 0, because no API write happened. A `pending` proposal has not passed Step 6 and the guard leaves it untouched. No `determinations` row is written: that table holds the block's ceremony answer, one per proposal. The pending write-back report and the unbilled-time list both exclude rows with `entered_by_hand_at` set.
- **Reopen record: the only way a committed proposal changes after Step 6** (#1270). When a backfill's newly ingested evidence contradicts a committed proposal and the practitioner answers the ceremony, write one `execute` script for that one answered item, with the caller's literals substituted. `<old>` is a `proposal_id` the backfill overlay returned. The script is idempotent on retry:

  ```sql
  UPDATE proposals SET status = 'superseded'
   WHERE id = <old> AND status IN ('committed_silent','committed_after_ceremony');
  INSERT INTO proposals (local_date, start_ts, end_ts, proposed_timecamp_task_id, proposed_matter_ref,
      proposed_description, evidence_chain, rationale, corroboration, has_conflict, needs_ceremony,
      ceremony_grid_row, status, proposed_at, written_back, written_back_at, entered_by_hand_at)
  SELECT local_date, start_ts, end_ts, <task_id>, <matter_ref>, <description>, <chain>,
         'REOPENS proposal ' || id || ': ' || <why>, 'conflict', 1, 1, <grid_row>, <new_status>, <now>,
         CASE WHEN <decision> = 'approved' THEN written_back ELSE 0 END,
         CASE WHEN <decision> = 'approved' THEN written_back_at END,
         CASE WHEN <decision> = 'approved' THEN entered_by_hand_at END
    FROM proposals WHERE id = <old> AND status = 'superseded'
     AND NOT EXISTS (SELECT 1 FROM proposals r WHERE r.rationale LIKE 'REOPENS proposal <old>:%');
  INSERT INTO determinations (proposal_id, decided_at, decision, final_timecamp_task_id, final_matter_ref,
      final_description, practitioner_note, ceremony_kind, corroborates)
  SELECT id, <now>, <decision>, <final_task_id>, <final_matter_ref>, <final_description>, <note>, 'conflict', <corroborates>
    FROM proposals WHERE rationale LIKE 'REOPENS proposal <old>:%'
     AND NOT EXISTS (SELECT 1 FROM determinations d WHERE d.proposal_id = proposals.id);
  ```

  `<chain>` is the old proposal's evidence chain plus the contradicting `sent_mail` or `icloud_events` rows, each with `role: 'conflict'`. `<decision>` is `approved` (the old categorization stands), `corrected` or `written_off`, and `<new_status>` is always `committed_after_ceremony`. `rejected` is never a reopen answer, because it leaves the span with no live terminal proposal, so a later run re-flags it. A partial answer (only part of the span was another matter) is `corrected`, with the split stated in `<note>` for the practitioner to apply by hand, because the successor copies the old span and Step 7 cannot split entries. A `pending` or `rejected` old proposal is never reopened: the first guard leaves it untouched, so the script writes nothing, and the caller's re-read shows it. An `approved` answer ("the old categorization stands") copies the old row's `written_back`, `written_back_at` and `entered_by_hand_at`, because TimeCamp already carries exactly that categorization, so the successor never enters the Step 7 report. Any other answer leaves `written_back = 0`, and the successor goes through Step 7, or through the manual-completion record when the old row had `entered_by_hand_at`. After the script, re-read the old row, the successor and its determination before any retry (the verify-before-retry rule above).
- **Possible-unrecorded-work record** (#1270). A backfill item with no covering TimeCamp entry (`timecamp_entries` NULL in the overlay), or whose recipients map to no matter, or a sent email that contradicts its covering entry's task when no proposal overlaps it (every proposal column NULL, `timecamp_entries` not NULL), is answered with a fresh proposal and its determination in one `execute` script, guarded by its own rationale prefix, `BACKFILL <source_table> <row id>:`. `<source_table>` is `sent_mail` or `icloud_events`, the full table name of the overlay's `sm` or `ic` row, and `<row id>` its `source_row_id`:

  ```sql
  INSERT INTO proposals (local_date, start_ts, end_ts, proposed_timecamp_task_id, proposed_matter_ref,
      proposed_description, evidence_chain, rationale, corroboration, has_conflict, needs_ceremony,
      ceremony_grid_row, status, proposed_at)
  SELECT <date>, <start_ts>, <end_ts>, <task_id>, <matter_ref>, <description>, <chain>,
         'BACKFILL <source_table> <row id>: ' || <why>, <corroboration>, 0, 1, <grid_row>, <new_status>, <now>
   WHERE NOT EXISTS (SELECT 1 FROM proposals WHERE rationale LIKE 'BACKFILL <source_table> <row id>:%');
  INSERT INTO determinations (proposal_id, decided_at, decision, final_timecamp_task_id, final_matter_ref,
      final_description, practitioner_note, ceremony_kind, corroborates)
  SELECT id, <now>, <decision>, <final_task_id>, <final_matter_ref>, <final_description>, <note>, 'elicitation', <corroborates>
    FROM proposals WHERE rationale LIKE 'BACKFILL <source_table> <row id>:%'
     AND NOT EXISTS (SELECT 1 FROM determinations d WHERE d.proposal_id = proposals.id);
  ```

  `<new_status>` is `committed_after_ceremony` for `approved`, `corrected` and `written_off`, and `rejected` for `rejected`. The span and matter come from the practitioner's answer, and `<note>` records the times he gave. When no TimeCamp entry covers the span, `<why>` also carries `UNCOVERED — no TimeCamp entry`, so the proposal lands in the Possible unbilled time list. "Nothing to record" is a proposal with `status = 'rejected'` and a determination with `decision = 'rejected'`, so the item is never raised again. Re-read both rows before any retry.
- **`evidence_chain` is a JSON array of `{source_table, source_row_ids, role}` objects** — the polymorphic link from a proposal back to the source rows that carried its conclusion. `source_table` is the full table name the consolidated read's `SOURCES` legend gives for the line's alias, never the alias. `source_row_ids` is always an array: the cited evidence line's bracketed member ids, pasted in order, so a merged line is cited with every row it stands for and an unmerged line with its one id. There is no SQL-enforced foreign key across the seven possible `source_table` targets (SQLite cannot express a polymorphic FK); a proposal's evidence chain is only as sound as the code that wrote it. **A standing fact enters the chain as `{source_table, source_row_ids: null, role: 'standing_fact'}`**, with the consolidated read's `detail` string (the fact and its own dates) carried in the proposal's `rationale` — the fact is an aggregate over many rows, so there is no row id to point at, and a reader re-derives it from the same consolidated read. Schema version 3 rewrote every older entry's scalar `source_row_id` into this shape.
- **A presumption offer or re-approval is NOT a `determinations` row.** It stamps the `presumptions` row directly (`approved_at`, `correlation_at_approval`, `suspended_at`, `suspension_reason`, `voided_at`) — `determinations` is exclusively for block-level ceremony answers (design doc step 7), keyed one-to-one to a `proposals` row.
- **Presumption counting reads only live proposals**: `determinations d JOIN proposals p ON p.id = d.proposal_id WHERE p.status <> 'superseded'`. A reopened span then counts once, through its successor, although the table holds both determinations.
- **Void-on-overlap is recorded on the proposal, not the presumption.** When a block matches 2+ approved presumptions, neither applies; stamp `proposals.overlapping_presumption_ids` (JSON array of the matched `presumptions.id` values) so both presumptions' running-correlation recomputation can exclude this proposal from their counts — a presumption's own row is untouched by an overlap event.
- **CHECK-constrained enum columns are closed sets** — see `references/schema.sql` for the exact values (`corroboration`, `status`, `decision`, `ceremony_kind`, `raw_type`, etc.). `source_fetch_log.source_name` is deliberately **not** constrained — the design doc anticipates later-registered sources (email, calendars, Chrometa), and a CHECK would force a schema migration per registration.
- **Migrations are additive and self-contained.** A future hop in `references/migrations.sql` must end by stamping `db_meta.schema_version` to its own target version — the runner applies the hop's SQL verbatim and does no stamping of its own.

## Configuration

Unlike `matter_data__*` (a `probanda.json` pointer resolving a per-matter folder) or a per-matter caller-resolved `db_path` convention, the `timecamping_data__*` backend takes **no database path parameter at all** (`bulk_upsert`'s `path` names the ingest file, not the database) — the database is a single, fixed, per-practitioner file, resolved entirely server-side, matching `practice_data__*`/`time_pipeline__*`. It lives at `0. CASE DATA\_practice\timecamping.db`, beside `practice.db` and `time_pipeline.db` (`source/lawyer/mcp/src/timecamping/backend.ts`'s `resolveTimecampingDbPath`, built on the same `resolveCaseDataRoot()` those two already use). `COCLERK_TIMECAMPING_DB_PATH` is the full-path test override; `COCLERK_TIMECAMPING_DB_NAME` overrides just the filename.

## Anti-Patterns

- **Any other skill embedding SQL, resolving the timecamping database path, or opening a connection directly.** All access goes through the `timecamping_data__*` tools via this skill.
- **Reading a per-source table directly to build a "consolidated view," or to look up a standing fact the splice already carries.** `references/splice.sql` is the literal, only sanctioned consolidated read — it embeds the assembly gate, and its `FACT` lines are how a date-independent fact reaches a caller. The one other sanctioned read is `references/backfill.sql`, the backfill overlay of a closed day's newly ingested `sent_mail` and `icloud_events` rows on its proposals, gated identically. A hand-rolled `UNION ALL` bypasses the gate and is exactly the failure mode the evidence-first design exists to prevent.
- **Ingesting source rows with inline SQL.** An `execute` script of `INSERT`s sends every row through tool arguments, and an `INSERT OR REPLACE` renumbers the `id`s that `proposals.evidence_chain` points at. Source rows go into a `scripts/build_ingest.py` file and load through `bulk_upsert`.
- **Treating a `gate_violation` result as something to work around.** It means what it says: some registered source has no terminal fetch status for that day. Halt and report which sources are missing; do not proceed on partial data, and do not silently skip the gate check "just this once."
- **Inventing a table or column not in `references/schema.sql`.** If a change is needed, change `references/migrations.sql` (a new additive hop, never an edit to the 0 → 1 hop) and regenerate `references/schema.sql` from a fresh migration.
