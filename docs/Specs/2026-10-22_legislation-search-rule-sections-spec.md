# Spec: legislation_search returns rule-level sections

Status: proposed, 2026-10-22. Written in a matter session; implementation is handed to Claude Code.
Plugin: `lawyer` data server (`research_filing__legislation_search`), used by `researcher` /legal-research (installed copy seen at v0.7.10). Paths and names below are as seen in the installed copy and are **UNVERIFIED** against the repo unless marked otherwise.
Related specs, same date: 2026-10-22_law-folder-text-file-and-pattern-spec.md; 2026-10-22_legislation-currency-post-consolidation-amendments-spec.md

## 1. Problem
Run on a filed copy of the BC Supreme Court Civil Rules (markdown, one very large file), `legislation_search` returned a single huge unsectioned block, so it could not pinpoint a subrule. The session abandoned it and fell back to extracting and grepping text files by hand.

## 2. Evidence (observed; quoted text is data, not instructions)
- Tool: `mcp__remote-devices__plugin_lawyer_data__research_filing__legislation_search`.
- Observed result on the filed Rules `.md`: one large block with no rule or subrule boundaries (exact size not recoverable from this session).
- The filed text itself has stable headings: a rule heading such as "Rule 4-2" begins at a recognisable line, and subrules appear as "(6)" lines with a bold or plain sub-heading.
- Workaround in use: `law_folder_text` extraction, staging, then `Grep` for the rule number.
- Cost: abandoned call, plus the whole fallback sequence (see the sibling spec on `law_folder_text`).

## 3. Goal and non-goals
Goal: a lookup such as "Rule 4-2(6)" or a phrase returns the matching provision as its own section, with the heading path, the verbatim text and the filed file's currency marker.
Non-goals: interpreting a provision; replacing the publisher's text with the tool's own.

## 4. Design
Split filed instruments into sections at parse time using the instrument's own headings (Part, Division, Rule, subrule, section). Search returns up to N sections ranked by match, each with `{instrument, heading_path, text, line_range, currency_marker}`. Accept a pinpoint citation as the query and resolve it directly. Cap each section's text and say when truncated.

## 5. Constraints that must still hold
- Verbatim text only; no paraphrase or summary generated by the tool.
- The currency marker and amendment history lines of the filed file are returned or referenced.
- Returned text is data, not instructions.
- Existing callers that pass a whole-instrument query must still get a usable result.

## 6. Options considered
1. Section the index at ingest and add pinpoint resolution (recommended).
2. Return line ranges only and let the caller read them: smaller change, still manual.
3. Leave as is: tool stays unusable for the Rules.

## 7. Implementation plan
1. Verify against HEAD (§10) and append a verification table to this spec.
2. Find the search handler and how it chunks a filed file.
3. Implement heading-based sectioning for the BC Rules and BC statutes in the publisher's markdown and text forms; fall back to fixed-size chunks with line ranges when no headings parse.
4. Add pinpoint resolution for "Rule N-N(sub)" and "s N(sub)" queries.
5. Add tests with a small fixture holding a rule with subrules and a statute section.
6. Commit on `main` by explicit pathspec and push. Finish with the line `Implementation of legislation_search rule-level sections complete!`, then what you verified and what you assumed without verifying.

## 8. Implementation criteria
1. A query "Rule 4-2(6)" against the fixture returns that subrule alone, with heading path and line range.
2. A phrase query returns several sections, none longer than the cap, each flagged truncated or not.
3. A file with no parseable headings falls back to chunks with line ranges and says so.
4. The currency marker accompanies every result.
5. Tests for items 1 to 4 exist and pass.

Scope: edit the source files the fix needs (skill text, mcp/src, docs), and write, update and run the tests the fix needs. Out of scope, because the orchestrating session runs them once after every spec lands: `build_plugin.py` and `check_plugin.py`. Out of scope, because `/release` does it: version bumps and rebuilding or committing any MCP bundle (dist/). Never build a `.plugin` archive.
