# Issue tracker: GitHub

Issues and specs for this repo live as GitHub issues. Use the `gh` CLI for all operations.

## Authentication

`gh` authenticates as Mharbulous via the Windows keyring, with no login step. A shell opened before `gh` was installed may not have it on PATH; invoke it by full path when `gh` alone is not found.

Call `gh` directly — there is no wrapper script and no token file. The keyring login carries the `gist`, `read:org`, `repo` and `workflow` scopes. **`GH_TOKEN` must not be set on this machine**: `gh` prefers it over the keyring login, so a stale value turns every call into `Bad credentials (HTTP 401)`. Never print, echo, or commit a token value.

Verify auth before reading or writing issues:

```powershell
gh auth status
```

### Windows PowerShell invocation safety

For a `gh` operation that reads stdin, pipe the payload into `gh` in the current process:

```powershell
$endpoint = "repos/Mharbulous/probanda-dev/issues/199"
$payload = @{ body = "Replacement issue body" } | ConvertTo-Json -Compress

$payload | gh api $endpoint --method PATCH --input - --silent
if ($LASTEXITCODE -ne 0) {
    throw "gh failed with exit code $LASTEXITCODE."
}
```

Never put a standalone `-` (including `--input -` and `--body-file -`) in the argument list of `powershell.exe -File <script>`. Windows PowerShell 5.1 can treat that token as an empty parameter name and fail before the script starts. Where a payload must cross a process boundary, write it to a temporary file and pass the path.

## Conventions

- **Create an issue**: `gh issue create --title "..." --body "..."`. Use a heredoc for multi-line bodies.
- **Read an issue**: `gh issue view <number> --json number,title,body,labels,comments`.
- **List issues**: `gh issue list --state open --json number,title,body,labels,comments --jq '[.[] | {number, title, body, labels: [.labels[].name], comments: [.comments[].body]}]'` with appropriate `--label` and `--state` filters.
- **Make an issue a sub-issue of a parent**: `gh issue create --parent <parent> ...`, or `gh issue edit <parent> --add-sub-issue <child>` afterwards (`gh` 2.94+). Older `gh`: `gh api --method POST repos/<owner>/<repo>/issues/<parent>/sub_issues -F sub_issue_id=<child-db-id>` (database id, as in **Blocking** below). Without sub-issues, put `Part of #<parent>` at the top of the child body.
- **Comment on an issue**: `gh issue comment <number> --body "..."`
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`
- **Close**: `gh issue close <number> --comment "..."`
- **Suggestion issues**: `/intake-suggestions` files each new Suggestion Box entry, paraphrased, with the labels `suggestion`, `needs-triage` and its lane label (**Implementer lock**), and records the issue number on it. `/triage-issue` opens it for review, which turns the suggestion's badge to Under Review, recommends a decline for each item that repeats an earlier suggestion ("Already suggested") or whose check already passes on `main` ("Already works as asked"), runs `fix-planner` and its red tests, and always leaves it `ready-for-human` with one open decision per item. Triage never approves, declines or closes a suggestion issue.
  - **Per-item approval.** Brahm decides each item, one at a time, through `/hitl-triage`: approved or declined, each with a reason of one plain line, at most 200 characters, that quotes none of the submitted text, and for a decline one category: `not enough detail`, `already works as asked`, `already suggested`, `outside what Probanda does`, `cost outweighs benefit` or `conflicts with how Probanda must work`. Each decision is written to that item in the Suggestion Box (`triage.mjs set-item`). An issue that covers suggestions merged by fingerprint takes the same decision and reason on the matching item of each.
  - **Then the labels.** An item left undecided keeps the issue at `ready-for-human`. Once every item is decided and any is approved, the skill posts a new `## Agent Brief` holding only the approved items and a `### Decisions` list of every item, and on Brahm's word relabels the issue from `ready-for-human` to `ready-for-agent`, which queues it. When every item is declined, it comments each item's reason and closes the issue as not planned instead. An item is built only when both the Suggestion Box and the latest brief approve it (`scripts/select_approved_items.py`), by `fix-maker`, one commit per item named `Suggestion <id> item <n>`.
- **Location labels**: `cloud` and `local` say where the work can run. Triage never adds `ready-for-agent` or `ready-for-human` without exactly one of them, so an issue with no location label is not ready. `.claude/commands/triage-issue.md` triages one issue unattended and sets them, and a cloud task runs it on every newly opened issue, then runs `.claude/commands/implement-suggestions.md` when it queued the issue (see **Implementer lock**). A nightly run of that task, with no issue number, sweeps up any open issue the event route missed, one with no state label and no brief (**Sweep** in that command). The Suggestion Box's save function starts a cloud task, with a daily schedule as backstop, that runs `.claude/commands/intake-suggestions.md`, which files each new Suggestion Box entry as a `suggestion` + `needs-triage` issue, so `/triage-issue` judges it like any other issue. The cloud implementer relabels any issue it cannot do from `cloud` to `local`, where the local implementer takes it (**Local implementer**), and a daily run of each is the backstop. A GitHub `issues.labeled` trigger on the implementer task starts it whenever a label is added to an issue that then carries `ready-for-agent` and `cloud` and not `local`, so relabelling a decided issue, or swapping `local` back to `cloud`, queues it at once. `/hitl-triage` claims a `ready-for-human` issue (**Claim** steps 1 to 3), suggestion or not, asks Brahm its open decisions, releases the claim, and relabels it on his word. A local session never takes a `cloud` issue unless one is named to it.
- **Withdrawn label**: `withdrawn` marks a suggestion issue whose sender withdrew the suggestion (the badge reads Withdrawn). `/intake-suggestions` adds it, posts one fixed comment saying only that the sender withdrew it, and closes the issue as not planned (`scripts/withdrawals.py` decides which). No queue takes an issue that carries it, whatever its other labels: `scripts/choose_issue.py` drops it in both the cloud and the local lane, `/triage-issue` and `/hitl-triage` skip it, and an implementer holding its claim, in either lane, discards its unpushed commits and releases the claim with the reason `withdrawn` before pushing anything, adding no label.

Infer the repo from `git remote -v` — `gh` does this automatically when run inside a clone.

## Pull requests as a triage surface

**PRs as a request surface: no.** _(Set to `yes` if this repo treats external PRs as feature requests; `/triage` reads this flag.)_

When set to `yes`, PRs run through the same labels and states as issues, using the `gh pr` equivalents:

- **Read a PR**: `gh pr view <number> --comments` and `gh pr diff <number>` for the diff.
- **List external PRs for triage**: `gh api --paginate 'repos/{owner}/{repo}/pulls?state=open' --jq '.[] | select(.author_association | IN("OWNER","MEMBER","COLLABORATOR") | not) | {number, title, author: .user.login, author_association, labels: [.labels[].name]}'`.
- **Comment / label / close**: `gh pr comment`, `gh pr edit --add-label`/`--remove-label`, `gh pr close`.

GitHub shares one number space across issues and PRs, so a bare `#42` may be either — resolve with `gh pr view 42` and fall back to `gh issue view 42`.

## Triage lock

**Lock issue: #61** (closed, never reopened). It keeps two bare `/triage` sweeps, or two `/triage-issue` sweeps, from running at once. Its operations reuse the claim comment and the paginated claim-comment read defined under **Claim** below, with its earliest-id-wins rule but a **30-minute** live window in place of 5 hours, and nothing else from that section: no assignment, no blocker gate, no release comment.

- **Take.** Read the lock issue's claim comments. If a live one exists, the lock is held: stop, and report `Triage lock held since <created_at>`. Otherwise post the fixed claim comment on #61, read again, and hold the lock only if your comment is the earliest live one. If it is not, delete your comment and stop the same way.
- **Refresh.** Post a new claim comment, then delete your old one. Your old comment stays live in between, so no other sweep can take the lock.
- **Release.** Delete your own claim comment (`gh api --method DELETE repos/Mharbulous/probanda-dev/issues/comments/<claim id>`), and nothing else.

## Implementer lock

**Lock issue: #189** (closed, never reopened). It keeps two runs of the same lane of `.claude/commands/implement-suggestions.md` from working at once, so their releases never collide on version numbers or built plugin files. The cloud run's Take, Refresh and Release are the **Triage lock** operations above, on #189 instead of #61, over the cloud route, with a **90-minute** live window. A run refreshes it before each issue it starts. The local implementer has its own lock on #189: the earliest live comment starting `Local lock stamp.` instead of `Claim stamp.`, with the same 90-minute window (`scripts/choose_issue.py lock --lane local`). Neither lane reads the other's stamp as its lock, so neither blocks the other, and the local implementer never deletes a `Claim stamp.` comment on #189.

The implement queue is every open `ready-for-agent` issue that does not carry `withdrawn`, in two location lanes: the cloud run takes the `cloud` issues not labelled `local`, and the local implementer takes the `local` ones. Each works its lane in the same order, lowest issue number first within each group: the maintainer lane (any issue with no lane label: everything opened on probanda-dev, by Brahm or a session working for him, and suggestions he approved by hand), then `lane:user` (Suggestion Box entries a practitioner wrote or confirmed, source `user` or `assisted`), then `lane:ai` (entries Probanda raised itself, source `llm`). `/intake-suggestions` sets the lane label, and `scripts/choose_issue.py` applies the rule for both lanes. Any session that leaves an issue in the cloud lane then runs `/implement-suggestions` with no issue number. A run that finds its lane's lock held stops at once: the holder works the lane until it is empty. The holder releases the lock and only then reads the queue once more, and takes the lock again if anything is left, so an issue queued while the holder was finishing is never stranded.

**Local implementer.** `/implement-suggestions local` works the `local` lane on Brahm's machine (**Local lane** in that command). A daily Windows scheduled task under his own account, "Probanda local implementer", registered by `scripts/local-implementer/register-local-implementer.ps1`, runs `run-local-implementer.ps1` in a dedicated clone, `%LOCALAPPDATA%\probanda-local-implementer\probanda-dev`, never the checkout Brahm and his sessions share or any worktree of it: `scripts/local_implementer_guard.py` stops the run anywhere else. Brahm may also run it there by hand. The script itself runs `npm ci --ignore-scripts` in `source/lawyer/mcp` from the committed lockfile before starting Claude Code, so the run never installs Node packages. It fast-forwards `main`, takes the same per-issue claim comments as the cloud run (**Claim**), builds approved items with `fix-maker`, commits by pathspec and pushes to `main`. Its `gh` writes pass their payload in a file, never `--input -` (**Windows PowerShell invocation safety**). An issue it cannot finish is handed back: it removes `ready-for-agent`, adds `ready-for-human`, leaves `local`, comments one line naming the gate item or check that failed, and releases its claim.

## Wayfinding operations

**Cloud sandbox route (Claude Code on the web, verified 2026-09-21 on map #759):** `gh` is absent there, and where present its `gh issue` and `gh pr` commands are refused (they use GraphQL). Use the GitHub MCP connector (`mcp__github__issue_write` with `parent_issue_number` creates a child as a sub-issue in one call; `issue_read`, `add_issue_comment`, `list_issues` cover the rest). For native blocking edges, which the connector lacks, a plain `curl -X POST https://api.github.com/repos/Mharbulous/probanda-dev/issues/<child>/dependencies/blocked_by -d '{"issue_id": <blocker database id>}'` succeeds: the sandbox's agent proxy carries the credential, so never look up, echo or pass a token yourself. Read the database id from `GET .../issues/<n>` (`.id`). **Claim in the cloud sandbox (verified 2026-09-25 on #1018):** the **Claim** operation below runs over the same `curl` route — `DELETE` then `POST .../issues/<n>/assignees` with body `{"assignees":["Mharbulous"]}` to stamp. The claim comments, which are also the Frontier query's liveness read, are read with `GET .../issues/<n>/comments?per_page=100&page=<k>`, starting at `k=1` and requesting the next page until a page returns fewer than 100 entries, then filtering every page's comments for a body starting `Claim stamp.` (the route has no `--paginate`, and a single page drops the newest comments on a ticket with more than 100), and written with `POST .../issues/<n>/comments`; the `POST` response's `.id` is the claim id (this comment route is unverified in the sandbox). Every write needs `-H Content-Type:application/json`; without it the API answers `415` and stamps nothing. A session refused at Claim step 3 withdraws its claim comment, and a releasing session deletes its own and any claim id it confirmed behind (see **Release**), with `curl -X DELETE https://api.github.com/repos/Mharbulous/probanda-dev/issues/comments/<claim id>` (unverified in the sandbox). Claim step 4's blocker read is `GET .../issues/<n>`, taking `.issue_dependencies_summary.blocked_by` and the `.body`'s `Blocked by:` line from the one response, then `GET .../issues/<m>` (`.state`) for each issue that line names (unverified in the sandbox).

Used by `/wayfinder`. The **map** is a single issue with **child** issues as tickets. A bare `/implement` (no ticket named) reuses the frontier and claim rules below — blocked-by, live-claim window, first-in-order — over `ready-for-agent` tickets generally, not just wayfinder map children. The closing ceremony (`.claude/skills/shared/closing-ceremony.md`), which fires at the end of every completed ticket in `/wayfinder`, `/triage` and `/implement`, reuses the same rules again, over both queues at once — every open map's children and every triage-ripe ticket. A change to those rules here updates all three consumers.

- **Map**: a single issue labelled `wayfinder:map`, holding the Notes / Decisions-so-far / Fog body. `gh issue create --label wayfinder:map`.
- **Child ticket**: an issue linked to the map as a GitHub sub-issue (`gh api --method POST .../issues/<map>/sub_issues -F sub_issue_id=<child-db-id>`; `-f` sends a string and 422s). Where sub-issues aren't enabled, add the child to a task list in the map body and put `Part of #<map>` at the top of the child body. Labels: `wayfinder:<type>` (`research`/`prototype`/`grilling`/`task`). Once claimed, the ticket is assigned to the driving dev.
- **Blocking**: GitHub's **native issue dependencies** — the canonical, UI-visible representation. Add an edge with `gh api --method POST repos/<owner>/<repo>/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`, where `<blocker-db-id>` is the blocker's numeric **database id** (`gh api repos/<owner>/<repo>/issues/<n> --jq .id`, _not_ the `#number` or `node_id`). GitHub reports `issue_dependencies_summary.blocked_by` (open blockers only — the live gate). Where dependencies aren't available, fall back to a `Blocked by: #<n>, #<n>` line at the top of the child body. A query that reads that line matches it at the start of any line, `(?im)^`, because an AI-written body opens with a disclaimer line and the blocker line comes after it, as with the **Brief read**. A start-of-body match missed #1337's blocker (#1435). A ticket is unblocked when every blocker is closed.
- **Frontier query**: list the map's open children (`gh issue list --state open`, scoped to the map's sub-issues / task list), drop any with an open blocker (`issue_dependencies_summary.blocked_by > 0`, or an open issue in the `Blocked by` line) or a **live claim**. A claim is live when the ticket has a claim comment under 5 hours old, read by the claim-comment read under **Claim**; a **stale** claim (every claim comment 5 hours old or more, ticket still open) is a dead session's leftover and does *not* drop the ticket — it's takeable again, and a ticket with no claim comment is unclaimed. Only a claim comment is a claim: the assignee field, an `assigned` event, and an assign or unassign in the GitHub UI are neither a claim nor a release. **`?per_page=100` is not optional** on any list read here. GitHub's default page is 30 entries, returned oldest first, so an unpaginated read keeps the oldest 30 and silently drops everything newer — on a busy ticket it can miss a recent claim entirely, or report a long-expired one as the latest, which reads as stale and makes a claimed ticket look free (confirmed 2026-09-22 on #285, with the event-log read this rule used then: 30 events returned of 63, the four newest days lost). A list longer than 100 needs `--paginate`, which applies `--jq` to each page separately and prints one result per page, so a `last` inside `--jq` silently breaks. `gh api` refuses `--slurp` alongside `--jq`, so select element by element inside `--jq` and reduce outside it. Take "now" from the system clock (`date -u`), never from a date stated in your context — the two can differ by a day across the UTC boundary, which silently moves every cutoff. First in map order wins. This query's claim data is **advisory**: a sweep takes minutes and ages as it runs, so the **Claim** below — read immediately before its own write — is the read that governs.
- **Ready-for-agent frontier**: the open `ready-for-agent` issues, oldest first, with both blocker signals, for a bare `/implement`'s ticket selection. A local session takes only `local` issues: add `,local` to the `labels` parameter. `gh issue list` omits `issue_dependencies_summary`, so use REST:

  ```bash
  gh api "repos/Mharbulous/probanda-dev/issues?labels=ready-for-agent&state=open&sort=created&direction=asc&per_page=100" \
    --jq '.[] | select(.pull_request == null) | {number, title, created_at, blocked_by: .issue_dependencies_summary.blocked_by, blocked_by_line: (((.body // "") | capture("(?im)^blocked by:[ ]*(?<refs>.*)")?.refs // "") | rtrimstr("\r"))}'
  ```
- **Dependents query**: list the open issues a just-closed issue was blocking — `gh api repos/<owner>/<repo>/issues/<n>/dependencies/blocking` (paginate like sub_issues; verified 2026-08-28 against a live edge). Run it after the close has landed, so each dependent's blocker count already reflects it. Each returned issue carries its own `issue_dependencies_summary` inline: a dependent is **dispatchable** when it is open, its `blocked_by == 0` (GitHub counts open blockers only — compare `total_blocked_by`, which counts closed ones too), and it has no live claim (the claim-liveness rule under **Frontier query**). Where dependencies aren't available, fall back to searching open issues whose `Blocked by:` line names `#<n>`; such an issue is dispatchable when every other issue named there is closed.
- **Brief read**: the one test for whether an issue carries an `## Agent Brief` comment. `gh api --paginate "repos/<owner>/<repo>/issues/<n>/comments?per_page=100" --jq '.[] | select(.body | test("(?m)^## Agent Brief")) | .id'` prints the id of every brief comment. The issue carries a brief when it prints at least one id. The match is anchored to the start of any line, because triage opens every comment it writes with the disclaimer line `> *This was generated by AI during triage.*` and the heading comes after it. A start-of-body match (`startswith`, or `^` without `(?m)`) therefore misses every triage brief (confirmed 2026-09-25 on #942, #987, #886 and #1132). A substring match (`contains`) is wrong the other way: it counts a comment that only names the heading inline, in prose or backticks, as a brief (#1141's closing comment). The Frontier query's `?per_page=100` rule applies unchanged, and this is the same paginated shape the **Claim** operation's comment read uses (the oldest-first trap is stated there). `--paginate` is safe here, unlike with `last`, because the filter selects comment by comment and each page prints its own matches.
- **Claim**: three steps — **read, stamp, confirm** — then a blocker **gate**. Parallel sessions run as the same tracker account, and neither the assignee field nor the `assigned` event log tells them apart: `--add-assignee @me` on an already-assigned ticket succeeds silently and writes no event, so two sessions whose remove-then-add stamps overlap by a few seconds leave a single `assigned` event that both read as their own (confirmed 2026-09-24 on #1006, twice: two closing ceremonies both took 20:04:06Z, then their two chips both took 21:53:39Z, and both chips worked the ticket). What does tell them apart is a **claim comment**. Every comment gets its own `id` from GitHub, even when two come from the same account in the same second, and ids rise in the order GitHub received them. That comment id is the session's **claim id**. The assignment is still stamped, as the marker a human sees in the GitHub UI; no query reads liveness from it.

  Read claim comments with `gh api --paginate "repos/<owner>/<repo>/issues/<n>/comments?per_page=100" --jq '.[] | select(.body | startswith("Claim stamp.")) | "\(.id) \(.created_at)"'`, which prints one `<id> <created_at>` line per claim comment. Sort the lines by `id` outside `--jq` (comment ids rise in the order GitHub received them). A claim comment is **live** when it is under 5 hours old. The comments read has the oldest-first trap stated under **Frontier query**: even at `?per_page=100`, an unpaginated read keeps the oldest 100 comments and drops the newest, which is where live claims sit (confirmed 2026-09-29 on #942, over 100 comments: the unpaginated read's last claim was `2026-09-28T19:10:40Z`, while a live claim at `2026-09-29T01:49:34Z` sat past the cut, and a session's own fresh claim can likewise be missing from its confirm read). `--paginate` applies `--jq` to each page separately, so `last`, array wrapping (`[...]`) or `sort` inside `--jq` silently breaks across pages: select comment by comment inside `--jq` and reduce outside it. The Frontier query's rules on `?per_page=100`, pagination and the clock apply unchanged.
  1. **Read.** Fresh-read the ticket's claim comments now — not from a scout's report and not from a frontier list taken minutes ago. If any live one is not this session's own, the ticket is held with reason `claimed`: stop here, and do **not** stamp.
  2. **Stamp.** `gh issue edit <n> --remove-assignee @me 2>/dev/null; gh issue edit <n> --add-assignee @me; gh issue comment <n> --body "Claim stamp. A session holds this ticket for 5 hours (docs/agents/issue-tracker.md, Claim)."` — the session's first writes. The remove-then-add leaves the ticket visibly assigned; the remove is a harmless no-op when the ticket was unassigned. The claim comment, not the stamp, starts the window. The comment body is fixed, word for word: no disclaimer line or other prefix goes before it, whatever a calling skill says about comments, because the read filter matches its start. `gh issue comment` prints the new comment's URL, ending `#issuecomment-<id>`: that id is this session's claim id. Then read the claim comments again.
  3. **Confirm.** From that read (the paginated read above, whose lines are sorted by `id`), list the live claim comments in `id` order. The session owns the ticket when the first is its own, or, for a chip, when the first is the claim id its ceremony handed it and the second is its own. Otherwise another session claimed first: withdraw your own claim comment, then stop and say so, and **do not unassign** (see **Release**). Withdraw by deleting the one comment whose id you recorded in step 2, `gh api --method DELETE repos/<owner>/<repo>/issues/comments/<claim id>`, and never any other comment. Left in place, that comment stays live for the full window and refuses the winner's chip at its step 1, although no session is working the ticket (observed on #987). Deleting it is safe because it is later than the winning claim, so removing it can never change which live claim is earliest. If the delete fails, say so in the stop line: the 5-hour window remains the backstop. A session refused at step 1 never stamped, so it has nothing to withdraw. Earliest wins, not latest — under "latest wins" two sessions claiming a few seconds apart could each read the other's later claim and both stop, whereas earliest wins gives the ticket to whichever claim GitHub recorded first, however the two sessions' reads interleave. A write that succeeds whether or not it was the first write proves nothing on its own; the read after the write is the claim.
  4. **Gate.** Once step 3 confirms ownership, fresh-read the ticket's open blockers from one `gh api repos/<owner>/<repo>/issues/<n>` response, by both signals under **Blocking**: `.issue_dependencies_summary.blocked_by` above 0, or a `Blocked by:` line in `.body` naming an issue still open (`gh issue view <m> --json state`). If either shows an open blocker, the ticket is held with reason `blocked`, which is distinct from `claimed`: run **Release** at once, with reason `blocked`, then stop. The gate runs after confirm rather than before stamp, so it is the read that follows the session's own write and also catches an edge wired while the session was claiming. It releases rather than just stopping, because a live claim comment would hold the blocked ticket for the full window, and the closing ceremony that closes its last blocker could not hand it forward. A session refused at step 1 or step 3 never reaches the gate. Calling skills report a `blocked` Claim as a held ticket and never restate this read.

  **What counts as your own.** A session owns the claim id it recorded in step 2, and nothing else. A chip's prompt carries the claim id its ceremony recorded. That id is not the chip's own: step 1 does not count it against the chip, and step 3 accepts it only as the one claim ahead of the chip's own. So when two sessions are handed the same id, whether from two chips or one chip launched twice, only the one whose own claim comes first after it proceeds. The other is refused at step 1 if the first has already stamped, or at step 3 if not, and at step 3 it withdraws its own claim comment. A session refused at step 1 or step 3 never deletes the ceremony's id. Only the session whose step 3 confirmed ownership behind that id deletes it, when it releases (see **Release**).

  Spawning a chip for a ticket claims it the same way, so an unclicked chip holds its ticket for the claim window and every sweep skips it until the window lapses, after which the ticket is takeable and re-spawnable again.
- **Release**: leave the assignment in place, delete your claim comments, and post one comment saying the ticket is released and why. Delete the one comment whose id you recorded at Claim step 2 and, when your Claim step 3 confirmed ownership behind a claim id a closing ceremony handed you, that handed id too: you are the only session working under it, so no other session relies on it. Delete each with the same call Claim step 3 uses to withdraw (`gh api --method DELETE repos/<owner>/<repo>/issues/comments/<claim id>`), and never any other comment: not a handed id you were refused behind, and not any claim a ceremony stamped on this or another ticket for a successor chip. The deletes must land before this session, or its closing ceremony, claims the same ticket again for a successor, so the successor's Claim finds the ceremony's new claim as the earliest live one. The release comment names each deleted claim id, so the thread keeps a record of the claim. If a delete fails, the release comment says so, and the 5-hour window is the backstop for that claim, as at Claim step 3. Never `--remove-assignee` outside a stamp: the account is shared, so unassigning strips any concurrent session's assignment along with your own. Once the claim comments are gone the ticket carries no live claim: a session that names it can Claim it straight away, and the Frontier and Dependents sweeps no longer skip it, so the closing ceremony of the session that closes its last blocker can hand it forward at once. A Claim step 4 `blocked` outcome is a release: its comment gives reason `blocked` and names each open blocker. A session refused at Claim step 3 is not releasing: it never owned the ticket, and it withdraws its claim comment as that step says. A human who unassigns a ticket in the GitHub UI does not free it either; only the deletes or the window do.
- **Resolve**: `gh issue comment <n> --body "<answer>"`, then `gh issue close <n>`, then append a context pointer (gist + link) to the map's Decisions-so-far.
- Read persisted `gh` JSON with `encoding='utf-8'` — Windows Python defaults to cp1252.
- **`GH_TOKEN` can go stale mid-session** (observed 2026-09-21 on #795: `gh api` calls succeeded for twenty minutes, then every call returned `Bad credentials (HTTP 401)`). `gh`'s own keyring login is the durable route, so run every tracker call as `env -u GH_TOKEN gh ...` — the same prefix already required for `git push`. Check with `env -u GH_TOKEN gh auth status`.
