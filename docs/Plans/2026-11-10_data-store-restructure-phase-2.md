# Phase 2: restructure the local stores to match the data pools

Status: the seven decisions were settled on 2026-11-10, after Phase 1 (`docs/Plans/2026-11-10_plugin-reorganization-phase-1.md`) landed. Nothing here is built. The Order section is next.

The pools, their scopes and the rules for them are in `docs/Plans/2026-11-10_data-pool-framework.md`. This plan does not restate them.

## Goal

Each data pool has one store and one gatekeeper skill, and a store's scope matches its pool's scope: a per-matter pool is stored per matter, a practice pool per practice. Rule 5 of the framework gives the reason: pools are kept apart by stores, so a tool that may read one pool cannot read another by accident.

The session is done when every row of the table below reads "none" in its gap column, or the developer has decided that the gap stays and the decision is recorded here.

What the table does not show:

- `main.sqlite` also holds data that no pool names: the matter's cast (`parties`, `witnesses`, `tribunal_members`, `participant_aliases` and their links to proceedings), the `matter_metadata` row, and `housekeeping_reviews`, the record of which files file-manager's review has seen. A split of `main.sqlite` (decision 6) has to place each of them.
- The practice board shows rows of kind `event` and `todo`, but `src/tools/practice/practice-board.ts` builds them from anchors, deadlines and tasks. They are not stored kinds.
- `time_pipeline.db`'s own header comment (`src/time-pipeline/backend.ts`) still names only `timeline`, `timesort` and `tedraft`. The `/time-pipeline-data` skill's namespace table is the full list: those three, plus `evidence` and `bill`.
- **`privileged.sqlite` is not read-isolated.** `matter_data__query` copies and attaches all three matter files on every read (`src/case/backend.ts`, `do_query`), so every holder of it (among them `research-agent`, `marshal-facts`, `migration-runner`, `scrivener` and `source-tracer`) can read client instructions. The "three-file firewall" guards write integrity, not reading. Whether those agents should read privileged material is the developer's question; decision 6's per-pool tools are where the answer would be enforced.
- `suggestions\suggestions.json` beside `probanda.json` (`src/suggestions/store.ts`) holds every suggestion this device sent or held. It is Probanda's own records (Account Information), outside the client pools, and stays outside `0. CASE DATA`.

Two facts shape everything below:

- **Three stores are legacy.** `COMMANDMENTS.md`'s Exception covers matter-data, drafting-data and timetracking-data. Each keeps typed tables, which Commandment 5 forbids, until it is converted. `practice.db` was converted on 2026-10-15 to one generic table (`docs/Plans/2026-10-14_practice-db-conversion.md`). No conversion plan exists for the other three.
- **Skills embed SQL against the legacy stores.** About 100 files in the `matter-data` skill and about 40 in `drafting-data` hold raw SQL, and `legal-research`, `apply-to-facts`, `draft` and `work` call the generic `query` or `execute` tools. A converted store has no SQL to embed, so converting one means rewriting those files to typed tools. This is the largest cost in the phase.

## Decisions for the developer

Each of these is the developer's to make before anything is built for it. Ask them one at a time, each with a worked example of what every option would produce and a "do nothing" option. Record each answer in this file under the decision.

1. **Events.** Move anchors and deadlines out of `practice.db` into a store in each matter's `0. CASE DATA` folder, or leave them practice-wide with their link to a matter. A per-matter store matches the pool's scope. It also means the morning briefing must open every matter's store to list what is due, where today it reads one file.
   **Decided 2026-11-10: the gap stays.** Anchors and deadlines stay in `practice.db`, each linked to its matter, and past events stay in each matter's `ProceduralHistory.md`. The briefing and practice board keep their single read of one file. Cloud exposure is the same in either store: an anchor's source excerpt, a deadline's source document, rule description and review note are hashed before anything leaves (`src/practice/ops.ts`). Order step 3 drops out. Gap recorded on review: framework rule 4 (a passed deadline stays linked to the event that answered it) cannot be met while past events live in `ProceduralHistory.md`, a file with no ids, and a deadline links only to its matter and anchor.
2. **`practice.db`.** Split it into one file per pool (practice records, billing, trust accounting), or keep one file and treat the item's kind as the pool boundary. Separate files make the boundary physical. One file keeps a time entry's link to its matter inside one store.
   **Decided 2026-11-10: one file; the item's kind is the pool boundary.** Every practice write is one cloud write applied in one local transaction from one sync stream (`src/practice/store.ts`). A split would need that stream routed by kind, or a second stream, and a partial sync between a matter and its billing records; billing reads the client, matter and contacts on almost every call anyway. The billing tools stay in `lawyer`'s `data` server (decision 6 states this as the sync-stream exception).
3. **Trust accounting.** Give it a ledger of dated entries with a sub-ledger per client, as a regulated trust account is kept, or keep the three balance fields on the matter item. Today no record shows how a balance was reached.
   **Decided 2026-11-10: the gap stays.** The regulated ledger is the firm's trust accounting system (UNITY® Accounting), and Probanda keeps only each matter's current balances, imported from its Trust Listing export by `retainer-tracking`, whose vision puts the transaction history out of scope. A second ledger in Probanda could disagree with the books of record. A dated snapshot per import was offered and declined: no skill needs a balance history today.
4. **Court calendar days and the rule overlay.** Move them from `practice.db` to the knowledge overlay, where the other know-how lives, or leave them.
   **Decided 2026-11-10: they are the law, and they stay in `practice.db`.** Neither is know-how: the rule overlay records a court-rule change and the calendar is a court's published sitting days, so the framework now lists both under the law. In `practice.db` a year's calendar is replaced in one write (`ingest_court_calendar_year`), and the overlay record is designed to be shared to legal-commons unchanged (`src/tools/practice/rule-overlay.ts`). Recorded on review: the overlay is the only `practice.db` payload sent to the cloud in clear, guarded mechanically only by the matter-code pattern and otherwise by `rule-update`'s rule that the matter is never written into a record; and keeping the law in `practice.db` means the one pool with no client data shares a file and a cloud rulebook with client pools, against rule 5. That gap stays. In the same decision the developer split the old know-how pool in two: know-how (true for any firm in the venue, and transferable) and institutional knowledge (true for this firm only, and Client Information). The table's two rows show where each sits today. Nothing moves now. Sorting the knowledge overlay between them is a precondition for ever sharing know-how.
5. **Timekeeping.** Merge `timecamping.db` and the three timekeeping namespaces of `time_pipeline.db` into one store when timetracking-data is converted, or keep two.
   **Decided 2026-11-10: merge.** The timetracking-data conversion moves `timecamping.db`'s data into `time_pipeline.db` as items whose `kind` is a value, never a namespace per former table, which would be a partition per kind (Commandment 5; ADR 0018 is the pattern). `time-pipeline-data` becomes the pool's one gatekeeper and absorbs `timecamping-data`'s list, and the `timecamping_data__*` tools are retired at that conversion (a minor bump). The conversion rewrites every read and write of `timecamping.db` anyway; on top of it, the seven-source assembly gate and the billing reads are relational, so each becomes a typed tool. Gap recorded on review: after this and decision 6, `time_pipeline.db` holds parts of three pools (timekeeping records; billing's `bill` and `tedraft`; institutional knowledge's description patterns), kept apart by tools, not files.
6. **`main.sqlite`.** Split evidence, the court record and work product into separate files when matter-data is converted, or keep one file for the matter's non-privileged data. They share many links (a fact to its source, a criterion to its facts).
   **Decided 2026-11-10, revised the same day after an independent review reached consensus.** A pool's seam is the typed tools a reader is granted, so every pool gets its own tool family at conversion. The framework decides which plugin owns a pool (whose skills write it); this decision decides which plugin's server serves its store. A pool is served by its owner's server, so the owner migrates and versions its own store, except where its records share one cloud sync stream with another pool's records: then that store's server serves both, and the owner writes through its typed tools. Billing's records in `practice.db` (time entries, invoices, invoice lines, payments, rates, adjustments) are that exception: one cloud write, one sync stream, and cloud rules linking entries to matters (a time entry inherits `billable` from its matter), so `billing` owns the pool and `lawyer` serves the store, and decision 2 stands. `billing` serves only the timekeeping store of decision 5, which already holds `bill` and `tedraft`, through a new tool family; `lawyer`'s `time_pipeline__*` family is retired at Order step 1 and `timecamping_data__*` at the timetracking-data conversion (retired, not renamed; a minor bump each). For `main.sqlite` the target is a `litigator` file and server for work product (and the court record if `litigator` owns it). Before that server key, a permanent name, is created, the matter-data conversion plan settles the court record's owner (the map places `e-file` there, and `matter-data`'s ingest may also write positions and sought orders), where the cast, `matter_metadata`, `housekeeping_reviews` (file-manager's run record) and `law.sqlite` (which work product links to) go, the by-id links across the boundary (checked on read, since two servers share no transaction), and the human ruling in `source/exception-rulings.json` that a new bundle's generic-store DDL lines need under `check_publishable.py --new-since`; the developer then confirms the split against those priced costs. "Two servers do not write one file" is a design rule, not a constraint of SQLite. The same reasoning applies to drafts, served today by `lawyer`'s `drafting_data__*` tools; the drafting-data conversion plan applies it.
7. **Correspondence with others.** Give it a store, or leave it in the mailbox.
   **Decided 2026-11-10: a derived correspondence store.** The originals are the matter's mail folder and its Correspondence folder (folder type 3), which holds scanned paper letters and the emails the folder's rules file there as `.eml` or `.msg` with a delivery code; paper never reaches the mailbox, and emails are not copied into the folder wholesale. A per-matter, local, generic store holds one entry per letter, email or attachment: its parties, date, subject, channel, body as lightly formatted text, and a pointer to its original, keyed by Message-ID or SHA-256, so a filed `.eml` and its mailbox copy are one entry. No parser reads Message-ID today (`src/correspondence/message.ts` reads from, to, cc, subject and sent), so the build adds one. It is rebuildable from the originals, which win when they disagree. Every field and every email body is built by code (message headers, the HTML or RTF body, a PDF's text layer, and the fields a filed scan's name encodes); only a scanned page's body text is read by a model, once per fingerprint, and kept, so a rebuild or a rename does not re-read it. A scan not yet named to the convention enters with its body text and a "not yet named" mark. Client correspondence (folder type 2) follows the same design under privileged communications, with its own tools; until matter-data is converted that leaves two stores for the one privileged pool, a gap recorded here. The store is built under its own plan (Order step 5).

## Constraints

- **No one-way doors (Commandment 8).** Every data move has a dry run that reports what would change, a backup taken before it runs, and a tested way back. The practice-db conversion is the pattern: it compared read snapshots before and after and found 0 differences before the old file was retired.
- **No new legacy store.** The Exception's list never grows, so any new store is generic from its first release: one table, no table or column per kind (Commandment 5).
- **Client Information stays on the user's machine (Commandment 3).** A rulebook that moves to the cloud sees only what the practice-db conversion already allows it to see.
- **No SQL or schema DDL is added to the repository.** `python scripts/check_publishable.py --new-since origin/main` must pass on every commit.
- **Version rule.** A store that an old copy of a plugin cannot read, or would damage, is a minor version bump (`CLAUDE.md`, "Releasing").
- **`matter_data__migrate` is called only by the `migration-runner` agent.**
- **Server keys and tool families are permanent names.** A new store gets a new tool family in the plugin that owns its pool after Phase 1. An existing family is not renamed.

## Out of scope

- Which plugin ships which skill: that is Phase 1.
- The design of the cloud rulebook beyond what the practice-db conversion set. **Open concern, raised by the developer on 2026-11-10:** the rulebook is Probanda's, not the firm's, and no record content leaves the machine, but every practice write sends metadata to Probanda's Cloud (counts of matters, entries, tasks and deadlines; each item's kind, state and tag values; which items link to which; when each write happened), and saving stops when the cloud is unreachable. Keeping the rules local would remove that, and would mean reclassifying the practice rulebook from Trade Secret to Shared Information under Commandment 4, which only the developer can do. Weigh it in its own session. Decision 6's billing choice keeps billing's records where either outcome can reach them.
- Any edit to `COMMANDMENTS.md`: only a person edits it. When a store complies, tell the developer it can leave the Exception.
