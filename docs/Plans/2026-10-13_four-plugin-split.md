Words used below. A *plugin* is one installable folder: a manifest (`plugin.json`), skills, agents, hooks and servers. A *marketplace* is the list (`.claude-plugin/marketplace.json`) a user installs plugins from. A *host* is the program that runs a plugin: the terminal (Claude Code), the desktop app, or Cowork. A *hook* is a small script the host runs before or after an event, and its *matcher* is the pattern that says which tool names or agent names make it run. A *server* is one of the three MCP programs the plugin starts (`data`, `canlii`, `commons`), and a *tool* is one function a server offers, named `mcp__plugin_<plugin>_<server>__<tool>`. The *roster* (`source/probanda/roster.json`) is the list of skills a plugin ships. The *bundle* is a server compiled into one file under `mcp/dist/`. The *install root* of a plugin is the folder the host unpacked it into. A *sibling* is another plugin's install root beside it.

## Goal

Replace the single plugin `probanda` with four plugins in the same marketplace `probanda`:

| Plugin | Role | Requires |
|---|---|---|
| `practice` | The base. Firm records, time, billing, filing, case data, and every part the other plugins share. | nothing |
| `research` | What the law is. | `practice` |
| `litigator` | Court work on a matter. | `practice`, `research` |
| `solicitor` | Reserved. Ships with no skills. | `practice` |

Decided by Brahm on 2026-10-13 and not open: the four names, `solicitor` empty for now, and `practice` as the plugin the others use.

Out of scope: renaming the public repository, the schema-split rebuild, and any change to what a skill does.

## Rules the end state obeys

1. **Prose points down only.** A skill, agent or hook in `practice` names nothing in another plugin. `research` names only `practice`. `litigator` names `practice` and `research`. One exception, decided by Brahm on 2026-10-13: a plugin may call into `research` without requiring it, because the call invites the user to install `research`. Such a call is ruled `invitation` in `source/layering.json` and says what happens when `research` is absent. A mention that only points the user elsewhere ("a deadline needs the `litigator` plugin") is allowed when it is worded as conditional and listed in the check's allowlist. This rule is about the text of skills, agents and hooks. The `data` server is exempt: it reads skill folders from every plugin (see decision 1), and its tool descriptions name skills in other plugins (`schema-gen.ts` lines 527 to 710 say "Skill: probanda:case-data" and the like).
2. **A hook ships with the work it guards.** A hook goes in the plugin whose skills or server it protects, and its script stays in that plugin's source: a skill folder of that plugin, or `source/<plugin>/hooks/` (where `commons-read-only.py` and `mail-send-gate.py` live). A hook that enforces a firm-wide rule, so it must run even when the guarded plugin is absent, goes in `practice`. No hook may fire in fewer situations after the split than before it. A matcher changes in the same commit as the name it matches. Example: `block-subagent-legal-research` matches the host tool `Skill`, but it guards only `/legal-research`, so it ships in `research`.
3. **One source, copies only in built output.** Skills stay in the flat `.claude/skills/` tree and under `public/`. A roster per plugin assigns them. `shared/` is copied whole into every plugin by the build and exists once in source. Two reasons it must be whole: every shipped SKILL.md tells the model to find `shared/x.md` at `${CLAUDE_SKILL_DIR}/../shared/x.md`, and the `data` server treats a folder as a plugin install only when `skills/shared/` exists in it (`repo-root.ts`, `installSkillsRoot`).
4. **Skill and agent names stay unique across the four plugins**, so a bare `/show-me` never becomes ambiguous.
5. **`main` is releasable after every commit.** Until the cutover commit, `main` still builds and ships the single `probanda` plugin, and `python scripts/build_plugin.py --check`, `python scripts/check_plugin.py` and `python -m pytest scripts/tests` pass.

## What the host documents say

From the Claude Code documentation, read on 2026-10-13 by a documentation agent, pages `code.claude.com/docs/en/plugins/*` and `claude.com/docs/plugins/*`. Each point is "documented" or "not documented". Where phase 0 tested a point, its result is in the phase 0 section and wins.

- Documented: `plugin.json` has a `dependencies` list. A bare name means a plugin in the same marketplace. Claude Code installs the dependencies with the plugin and refuses to enable a plugin whose dependency is missing. The Cowork build page lists dependencies as a Claude Code feature, not a Cowork one. (Phase 0: true for the terminal. claude.ai installs nothing extra and shows no warning. Cowork loads the plugin anyway.)
- Documented: a marketplace may list several plugins from one repository, each with its own `source` folder. A manifest with only `name`, `version` and `description` is valid. (Phase 0: confirmed on every host tested.)
- Documented: agents are named `<plugin>:<name>`, and a `SubagentStart` or `SubagentStop` matcher is a regular expression over that full name. Tools are named `mcp__plugin_<plugin>_<server>__<tool>`.
- Documented: removing a plugin from a marketplace does not uninstall it. The installed copy stays and reports "not found in marketplace" at session start, unless the marketplace sets `forceRemoveDeletedPlugins: true`, which uninstalls it at the next session start. Not documented for Cowork. (Phase 0: confirmed on the terminal.)
- Not documented: whether a skill in one plugin may call another plugin's tool or agent. (Phase 0: yes, on the terminal and in Cowork.)
- Not documented: where Cowork puts a plugin on disk, and whether a Cowork session can read a sibling plugin's folder. (Phase 0: the skills and hooks run in Cowork's Linux machine from `/root/.claude/plugins/synced/...`, and the servers run on the PC from the desktop app's store.)

## Decisions taken by default

Brahm can overturn any of these before the phase that uses it.

1. **Where the `data` server lives and how it finds skill folders (used in phase 3).** The server stays one program, in `practice`, keeping every tool name. It finds a skill folder that `practice` does not ship by looking at the plugins installed beside it, with no hook and no registration file. From its install root it lists the folders beside it, and the folders two levels up (for the `claude plugin install` layout, where the install root is `<marketplace>/<plugin>/<version>/`). A folder counts as a sibling when it holds `.claude-plugin/plugin.json` whose `name` is `research`, `litigator` or `solicitor`, and `skills/shared/`. Any other name is ignored, so a stale `probanda` beside the new plugins can never serve a file, and a folder whose name starts with `.` is skipped (`.staging/`). When one name has several copies (a `~g<N>` generation beside the old folder, or several versions in the cache), the copy with the highest `version` in its manifest wins, then the highest `~g<N>`, then the newest change time. Lookup order: own install, then the siblings, then the checkout chain that exists today. The result of `skill_source__read` and `skill_source__list` names the plugin and version the file came from. When no install holds `skills/<segment>/`, the error names the segment, lists every sibling found with its version, and says that the plugin holding that folder is not installed on this PC's copy (in Cowork, the desktop app's store), so the user should check for updates in the desktop app and restart.
   - Why this and not the first design. The first design had each plugin's `SessionStart` hook write its install root to a file the server reads. Phase 0 showed that in Cowork the hook runs inside the Linux machine while the server runs on the PC, so the hook would register a path the server cannot read.
   - Why this and not one server bundle per plugin. That would rename most tool names a second time and copy the bundle's 49 problem lines into each plugin, which `check_publishable.py --new-since` refuses. It stays the last resort.
   - Known limits, each with its handling. (a) The desktop store lags behind claude.ai, so in a Cowork session the skill text (from the Linux copy) and the server (from the PC store) can be different versions, and a sibling can be at another version than `practice` or absent. Nothing can fix that from inside the plugin. The error above, and the version in every result, make it visible. (b) On a machine with a checkout, the checkout chain can serve a file that no sibling holds, which would hide a missing sibling. Phase 6's check therefore reads `shipped_from` and the plugin named in the result. (c) The server reads from a sibling's folder and `knowledge__write` writes into one. Both are the same operations it runs on its own folder today, and a host replaces a plugin's folder on sync either way.
2. **Server keys.** `data`, `canlii` and `commons` keep their keys. Only the plugin part of each tool name changes.
3. **The old plugin.** `probanda` is removed from the marketplace in the cutover commit, and the marketplace sets `forceRemoveDeletedPlugins: true` so Claude Code uninstalls it at the next session start. Whether Cowork honours that flag is unknown, so phase 6 still has each machine check and uninstall by hand.
4. **Versions.** Each plugin starts at `0.2.0` and is versioned on its own from then on. The public plugins start at `0.0.1`, as the one public plugin does now. What to bump when `shared/` changes, which ships in all four, is open decision 2.
5. **Public plugin.** The five public skills follow the assignment: `legal-citation` to `research`, `litigation-fact-extractor` to `litigator`, `TLDR`, `proof-read` and `dyu` to `practice`. Publication waits for Brahm's express instruction, as always.
6. **Requires.** Each `plugin.json` declares its `dependencies` as the goal table says. Phase 0 showed what that buys: the terminal refuses to enable a plugin whose dependency is missing, claude.ai installs nothing extra and warns nobody, and Cowork loads the plugin with the missing plugin's tools and agents simply absent. No skill wording can cover a missing *lower* plugin, because the tools it would call do not exist. So each plugin's `README.md` and its marketplace `description` say what to install and in what order, and phase 6 installs the three by hand. The wording phase 4 added covers only a call *up* into a plugin that is not required (`task-prioritization` and `show-me` into `research`).
7. **Where the server source lives.** Settled by phase 2: `scripts/plugin_layout.py` maps each server key to a folder inside its plugin's source (`data` to `mcp`, `canlii` to `canlii-mcp`, `commons` to `commons-mcp`). At cutover `source/probanda/mcp/` moves to `source/practice/mcp/`, and `canlii-mcp/` and `commons-mcp/` to `source/research/`. The alternative, a neutral `source/servers/` folder, was not taken.

## Risks

- **The desktop store lags.** The desktop app and Cowork start the servers from a store that updates on its own schedule (0.1.6 while `main` was 0.1.9 on 2026-10-13). After cutover, a Cowork session can hold the new skills while the PC still runs the old `probanda` server, or `practice` without `litigator`. The symptom is a missing tool or the decision 1 error. The remedy is to wait for the store, check for updates in the desktop app and restart. No step in this plan can shorten that.
- **A dependency can be missing.** claude.ai installs nothing extra and shows no warning, and Cowork loads a plugin whose dependency is absent. Only the README, the marketplace descriptions and phase 6's install order guard against it.
- **Cutover is one large commit, and it rebuilds the data bundle.** The bundle rebuild is the step most likely to add a problem line or a machine path, so run `check_publishable.py --new-since` and `check_plugin.py`'s `bundle-no-host-path` before pushing.
- **The first sync after cutover.** A machine that syncs before `probanda` is uninstalled shows no duplicates, because the old plugin is gone from the marketplace, but its installed copy keeps running stale skills until the host removes it or Brahm does.
- **Two marketplaces, one name.** The development marketplace and the public one are both named `probanda`, and after phase 7 both list plugins named `practice`, `research`, `litigator` and `solicitor`. That is the situation today with one plugin. A machine that installs from both holds two plugins of one name, and the sibling lookup picks the higher version, which is the development one (0.2.0 and up against 0.0.1). Brahm's machines install only from the development marketplace.
- **Public approval.** Phase 7 changes every public path, so nothing can be published until Brahm re-approves the whole public tree.
